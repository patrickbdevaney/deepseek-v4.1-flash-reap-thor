# V4.1-1017 REAP CUDA server for Jetson Thor (s08)

This is a pure-CUDA inference server for DeepSeek-V4.1-Flash-1017 and its REAP arms on one Jetson AGX Thor (sm_110a, 128 GB unified memory).

It is a **copy** of `~/deepseek-v4-flash-0731-cuda` at commit `8b476b9`, adapted for V4.1. The 0731 repository was not modified. What changed and why is in `docs/V41_DELTA.md`. Expert formats are covered in `FORMAT_PROPOSAL.md`.

> **Status: compiles; nothing has run on the GPU.** The CPU gates below pass. Every GPU check is a step in `CHAIN_STEPS.sh`, which `ops/chain.sh` runs when it owns the GPU. Until `golden` passes for an arm, treat that arm's output as unverified.

## Build

```bash
scripts/build_v41.sh            # everything (-P4 objects): v41_decode, v41_server, gates, bench
scripts/build_v41.sh v41_decode # one target
```

The build needs CUDA 13 (sm_110a), liburing, and `-lcuda` (for stream memops).

## Run

```bash
build/v41_decode --ckpt $V41_WORK/thor/A192 --keepset $V41_WORK/s04/keepset.json --engram $V41_WORK/engram_rows \
    --chat "Hello" --n 128 [--repeat 3] [--consistency 8] [--no-graph] [--temp 0.6 --top-p 0.95 --seed 1] [--json out.json]
build/v41_server --ckpt ... --keepset ... --engram ... --port 8000      # OpenAI-compatible, SSE, DSML tool calls
```

**Inputs.**

- **Weights.** `--ckpt` takes a thor-v1 build (`ops/lib/thor_format.md`). It also accepts the HF source checkpoint, but at 384 experts that only fits layer-at-a-time, as the golden gate loads it.
- **Engram rows.** `--engram` names the directory holding `engram_L1.v41rows` and `engram_L14.v41rows`, written by `llamacpp/CHAIN_STEPS.sh rowfile`; this is the shared format in `llamacpp/ENGRAM_ROWFILE.md`.

**Safety.** **Never start either binary beside another model-loading process.** On Thor's unified memory that can hard-reboot the box. Use `CHAIN_STEPS.sh`, which checks this, detaches the process, and reclaims memory afterwards.

## What is in it

| addition | where |
|---|---|
| Engram row store | `src/engram_store.cpp`. Reads are io_uring O_DIRECT, aligned 1 KiB per row, into a `cudaHostRegister`ed arena. Completion is published through flag words that the captured decode graph waits on (`cuStreamWaitValue32`), so decode stays one graph launch per token. Hashing is in `src/engram_hash.cpp`; the gate+wkv kernel is in `kernels/v41/v41_engram.cu`. `tools/pack_engram_rows.py` converts FP8 rows to an optional 6-bit MXFP6 file, which is CUDA-only, lossy, and not in the shared spec. |
| CSA2 roles | KV sources {2,8,14,20}, index sources {2,8,…,36}, and reuse layers that read the source's caches. Layer 20 picks 2048 candidate blocks × 8 past 16,384 rows. The KV is packed FP4 (e2m1 + E4M3/E8M0 scales), which is exact to the reference: 0.87 GiB at 1M tokens. |
| encoder/decoder prefill | Decoder layers skip rows below `prompt_end − dec_span(L)`. That is exact, with 2414 rows at layer 21 (not 128; see `docs/V41_DELTA.md` §2). Prefix reuse respects the resulting floor. |
| router | sqrtsoftplus; the bias selects but does not weight; `bias_vl` on image rows; ×1.5; expert count read from the checkpoint |
| expert GEMV | thor-v1 Q2_K / Q3_K / Q4_K (bit-exact ggml decode), plus MXFP4 through the `cvt.e2m1x2` hardware path. One warp per output row, x reused across all R rows of an expert pair. LUT and trellis kernels are proposals only (`FORMAT_PROPOSAL.md`). |
| determinism | Fixed reduction orders and no atomics in any sum. Greedy decode is `--repeat`-checked, graph vs no-graph ids are compared, and decode-vs-prefill consistency is checked (`--consistency`). |
| DSML | `include/encoding_dsv41.h`: a line-for-line port of V4.1 `encoding/encoding.py` |

## Not verified (GPU; `CHAIN_STEPS.sh` order)

1. `units`: decoders, act_quant, the linears, the router and routed MoE on the GPU against the ops oracles.
2. `gemv_bench`: every format's GEMV bandwidth against a streaming read.
3. `golden_ref` + `golden`: per-layer cosine (isolated and chained) and teacher-forced argmax agreement against `model.py` (`tests/golden/ref_dump.py`). A second pass goes through the real row store.
4. `decode`: determinism, graph ≡ no-graph, decode-vs-prefill consistency, tok/s at short and 8K context.
5. `ctx1m`: a 1,048,576-token state allocation and decode after a 64K prefill.
6. `server`: health, an EOS-terminated chat turn, a parsed DSML tool call.

## Biggest risks

- **The forward has never run.** It is about 2,600 lines of new kernels and model code, held only to the reference by reading. Expect the first `golden` run to find bugs. It is designed to localise them to a layer, and the isolated stream to a single layer's arithmetic.
- **Graph capture of stream memops.** `cuStreamWaitValue32` inside a captured graph is supported by CUDA, but it is untested on Thor's driver. `--no-graph`, and an automatic fallback when capture fails, keep the server usable either way.
- **Speed.**
  - The indexer score grid is sized by `seqmax`: at 1M, decode launches about 32K CTAs per index layer, most of which exit at once.
  - Prefill Engram I/O is serial per 128-row chunk (about 46 ms of holes per chunk measured on sparse files; real rows will differ).
  - The bf16 head reads 1.3 GB per token.
  - K-quant lanes re-read shared scale bytes.

  These are known and listed so the bench numbers can be read against them. None of them is a correctness issue.
- **Thresholds.** The golden gate's cosine and agreement thresholds are judgment calls, stated in `tests/gate_v41_golden.cu`. The thor-arm comparison carries a known sub-bf16 difference: CUDA decodes K-quants in exact fp32, while `replay.py` rounds them to bf16.
