## BLOCKER 1: `convert` crashes because the master has no Engram shards 47/48

**Where:** `llamacpp/CHAIN_STEPS.sh:100` (convert) together with `ops/s05_surgery.py:166-168,219-220`, and the
fork's `conversion/base.py:247-266`.

**What happens:**
- s05 does not rehost shards 47/48. It does, however, keep their entries in the regenerated
  `model.safetensors.index.json`, so `layers.{1,14}.engram.{embed.weight,embed.scale,q_weight,k_weight,wkv.weight,wkv.scale}`
  still map to `model-0004{7,8}-of-00048.safetensors`.
- The master that `convert` gets is either the HF download (`$SEAW/master_REAP192`) or the local s05 dir. Neither
  one contains those two files.
- `ModelBase.index_tensors` builds `part_names` from the index's `weight_map` values and opens each one with
  `SafetensorsLocal(dir_model / part_name)`.
- Result: `FileNotFoundError` before any check runs. `die "convert"` writes chain.STOP.

**Evidence:** I reproduced it with the fork's real `ModelBase.index_tensors` on a synthetic master whose index
names a missing shard (`/tmp/claude-2002/audit-s09/idx.py`). It fails with
`FileNotFoundError: ... fm/model-00047-of-00048.safetensors`.

The tensors are also *needed*. The real shard 47/48 headers show that `engram.wkv.weight` [25600,6144] F8 + scale
and `engram.q_weight`/`k_weight` BF16 [4,5120] live there. `deepseek41.cpp` creates `engram_wkv/q/k` with flag 0
(required), so even a converter that skipped the missing files would produce a GGUF that does not load.
`convert_v41_reap.py` only drops `.engram.embed.`.

**Fix** (`llamacpp/CHAIN_STEPS.sh`, convert step, right after `mkdir -p $G/src`). The converter then indexes them;
the existing wrapper still drops the two tables, and wkv/q/k are converted.

```diff
   mkdir -p $G/src
+  # s05 does not rehost Engram shards 47/48, but the master's index still maps engram.{embed,wkv,q_weight,k_weight}
+  # to them and the converter opens every shard the index names (the tables are then dropped, wkv/q/k are kept).
+  SRCD=${V41_SRC:-$HOME/models/DeepSeek-V4.1-Flash-1017}
+  for s in model-00047-of-00048.safetensors model-00048-of-00048.safetensors; do
+    [ -e "$MASTER/$s" ] || ln -s "$(readlink -f "$SRCD/$s")" "$MASTER/$s" || die "link Engram shard $s into the master"
+  done
```

Notes on the fix:
- The master may be on the ntfs-3g Seagate. ntfs-3g supports symlinks.
- If you prefer not to write into the master dir: build a temp overlay dir of symlinks (all master files + 47/48)
  and pass that as the model dir. That also needs Fix C1, because the dir name selects the chat template.
- Add a test: a fake master whose index names a 47/48 shard that is absent.

## BLOCKER 2: the `kld` run exits 1 on a held-out row longer than `-c 8192`

**Where:** `ops/s09_teacher_eval.py:44-55` (prep) and `llamacpp/tools/v41-teacher-kld.cpp:115-118`.

**What happens:**
- prep keeps *every* held-out text row.
- The real corpus has one: row 506, bucket `longctx`, **58,789 tokens**. Checked against the real
  `rows.jsonl`/`types.npy`/`valid.npy`, using prep's own filter: 46 rows, 427,429 tokens, lengths up to 58,789.
- The tool runs at `-c 8192` and does `if (len > n_ctx) { ...; return 1; }`.
- Row 506 comes near the end of the visit order, so the run dies after hours of GPU work. Then
  `die "kld run L2"` writes chain.STOP. kl.f32 is only written at the end, so nothing is salvaged.

**Second defect, same lines: the pre-registered split is ignored.** `s10_gates.json` `gguf.split = "confirm"`,
and its `why` says the GGUF is scored "on the confirm split". prep uses both halves, including the screen rows that
s04 and s10-heal tuned on. That would publish GGUF numbers on rows used for tuning (see CORRUPT 2).

The confirm half has 22 text rows and 180,224 tokens, max 8,192. Restricting to it fixes both defects.

**Fix** (`ops/s09_teacher_eval.py`):

```diff
-    keep, n = [], 0
-    for r in rows:
-        if not r["heldout"]:
-            continue
+    from ops.lib import rowsets
+    spec_hash = json.loads((CORPUS / "manifest.json").read_text())["spec_hash"]
+    keep, n = [], 0
+    for r in rowsets.split_rows(rows, spec_hash, "confirm"):        # s10_gates.json gguf.split (pre-registered)
         s = slice(r["offset"], r["offset"] + r["length"])
         if (types[s] != -1).any() or not valid[s].all():
             continue
+        if r["length"] > 8192:     # v41-teacher-kld runs at -c 8192 and exits 1 on a longer row
+            print(f"prep: skipping row {r['row']} ({r['length']} tokens > ctx 8192)")
+            continue
```

Better still, pass the ctx as an argument shared with CHAIN_STEPS, and add `"split": "confirm"` to meta.json so
`summarize` can assert it. `$WORK/s09/teacher_eval/meta.json` does not exist yet, so no stale prep needs deleting.

## RISK 1: staging L2 to NVMe will very likely hit the disk guard (STOP)

**Where:** `ops/chain2.sh:214-218` (stage) and `:231-233` (src GGUF dropped only *after* the gate).

**Accounting:**
- `/` has 99 GiB free now (`df`, 936G disk).
- Moving the backbone frees about 279 GiB, giving about 378 GiB.
- The row files take about 189 GiB, leaving about 189 GiB.
- The source GGUF takes about 152 GiB, leaving about 37 GiB.
- Staging L2 needs about 101 + 25 GiB, so `need / ... "stage L2 to NVMe"` stops. This assumes chain1 does not
  free more NVMe than that, which I could not verify. Plus the served Thor build stays on NVMe.

The guard stops cleanly, so this is not corrupting, but it is an avoidable STOP.

**Fix:** drop the regenerable source before staging when space is short, and re-make it if L3 needs it. In
`ladder()` before the `need / ... stage` line:

```diff
     local sz=$(du -s -B1 -L "$SEAW/s09/$LV" | cut -f1)
+    if [ "$(free_gib /)" -lt $(( sz / GIB + 25 )) ]; then   # the source GGUF is regenerable (convert)
+      rm -f $G/src/V4.1-1017-REAP$NKEEP-src.gguf $L/done.s09_convert $L/done.c2_s09_convert_
+      log "dropped the source GGUF to make room for staging $LV"; fi
     need / $(( sz / GIB + 25 )) "stage $LV to NVMe"
```

At the top of `ladder()`, before `cpu s09 quant $LV`:

```diff
+    [ -f $G/src/V4.1-1017-REAP$NKEEP-src.gguf ] || { need / 170 "s09 source GGUF"; gpu s09 convert; }
```

## RISK 3: a crash in s09_gate is read as "L2 failed"

**Where:** `ops/chain2.sh:225,229`.

**What happens:**
- chain2 has no `set -o pipefail`, so `PASS=$(... | tail -1) || stop` takes `tail`'s status.
- If s09_gate crashes (missing file, prereg-lock mismatch in `gates.load`), PASS is empty and the run is treated as
  a gate FAIL. It then builds L3 (about 100 GiB quant + kld + smoke), fails again the same way, and publishes
  nothing, with no STOP.

```diff
-PASS=$($PY ops/s09_gate.py --levels L2 2>>$L/c2_s09_gate.log | tail -1) || stop "s09 gate"
+GOUT=$($PY ops/s09_gate.py --levels L2 2>>$L/c2_s09_gate.log) || stop "s09 gate"; PASS=$(tail -1 <<<"$GOUT")
```

Apply the same change at line 229 with `--levels L2 L3`.

## RISK 6: the published GGUF card's recipe fails for users

**Where:** `ops/cards/gguf.md.tmpl:20-36`, `llamacpp/build.sh:5`.

1. **`config.json` is missing.** Step 3 downloads only `model.safetensors.index.json` + shards 47/48. Step 4 then
   runs `s09_engram_rowfile.py build` without `--layers`, and `main()` reads `env.SRC/"config.json"`
   (`ops/s09_engram_rowfile.py:218`), which raises `FileNotFoundError`.

   ```diff
   -.venv/bin/hf download {{ base.repo }} model.safetensors.index.json model-00047-of-00048.safetensors \
   +.venv/bin/hf download {{ base.repo }} config.json model.safetensors.index.json model-00047-of-00048.safetensors \
   ```

2. **The clone URL is not public.** Step 1 clones `https://github.com/patrickbdevaney/deepseek-v4.1-flash-reap-thor`,
   which returns **HTTP 404** to an anonymous GET today (private or absent). chain2 makes the GGUF repo public
   automatically, so the card would go out pointing at a repo nobody can clone. Either make the GitHub repo public
   before chain2 reaches `s12_gguf`, or gate the card's recipe on it. This is an owner decision.

3. **`build.sh` hard-codes Thor.** It sets `-DCMAKE_CUDA_ARCHITECTURES=110 -DGGML_NATIVE=ON`, while the card says
   "a CUDA GPU". On any other GPU the binary has no kernels.

   ```diff
   -cmake ... -DCMAKE_CUDA_ARCHITECTURES=110 \
   +cmake ... -DCMAKE_CUDA_ARCHITECTURES=${CUDA_ARCH:-110} \
   ```

   Also add one card line: `CUDA_ARCH=<sm> llamacpp/build.sh`.

## RISK 7: `convert` reads a ~150 GB master from ntfs-3g through mmap page faults

**Where:** `ops/chain2.sh:169-176`. The master is downloaded to the Seagate, and the converter's `SafetensorsLocal`
reads through `np.memmap`. This repo's own measurement (`ops/lib/engram_rows.py:74-76`) is about 8 MB/s for page
faults over this FUSE mount, which would mean on the order of 5 hours or more for convert.

It is not a crash, and NVMe probably cannot hold the master + src + rows at once. Expect it and budget for it.
**Unverified:** the real throughput depends on readahead.

## NITs

- **Header dtype fields unchecked.** `deepseek41-engram-rowstore.h:71-74` does not check `value_dtype == 1` /
  `scale_dtype == 1`. `LLAMA_ENGRAM_ALIGN` is not checked to be a power of two: `off & ~(align-1)` is wrong for,
  say, 1000. Suggested: `if (align & (align-1)) throw ...`.
- **Pad key name.** Fork `conversion/deepseek.py:1366` reads `hparams.get("engram_pad_id", 2)`, but the HF config
  key is `engram_pad_token_id` (=2). It is correct only because the default equals the value.
- **Size estimate counts 1-D norms as Q8_0.** `ops/s09_gguf_ladder.py:102` rule `\.(attn_|indexer)` matches 1-D
  `attn_norm`/indexer norms, so `plan` sizes them as Q8_0. llama-quantize never quantizes 1-D tensors
  (`llama-quant.cpp:292`), so only `predicted_bytes` is slightly high.
- **README ladder wording.** `llamacpp/README.md` lists L2 as "IQ2_S / IQ3_XXS mix". The code ladder is IQ2_XS..IQ3_S,
  and with uniform scores it yields 33×IQ2_S, 29×IQ3_XXS, 18×IQ3_S (protected) at 2.847 bpw (my synthetic run).
- **Local paths go public.** `gguf_manifest.json` (uploaded publicly) embeds absolute local paths
  (`/media/patrickd/Seagate Portable Drive/...`, `/home/patrickd/...`) in `files[].path`. Strip them to basenames
  in `gguf_context`.
- **Smoke parallelism.** smoke launches `llama-server` without `-np 1`, so the default auto-parallel splits the
  8192 ctx into slots. It is harmless for a one-turn smoke, but `-np 1` matches the served recipe.
- **Comment slightly wrong.** In `deepseek41.cpp` `set_input`, the comment "multipliers under 2^37" is wrong
  (they reach about 2^46.4). The products still fit by construction (bound = int64_max // vocab), so there is no
  overflow.

1. **Fork state.**
   - `llamacpp/llama.cpp` is on branch `v41-thor` with a clean working tree.

   - `build-thor/bin` (04:14) is newer than every patched source (latest 03:46); `v41-teacher-kld` is built.
2. **Row-file layout, byte for byte.**
   - Writer `struct "<IIQIIIIIQ"` @8, the reader's `memcpy` offsets (8/12/16/24/28/32/44) and ENGRAM_ROWFILE.md all
     agree: 264 B rows, `data_off` 4096, sha/name/revision regions.
   - Real shard 47/48 headers: `embed.weight` F8_E4M3 [384006168|384016682, 256], `embed.scale` F8_E8M0 [n, 8],

     → C++ `deepseek41_engram_rowstore::gather` vs torch `ParallelEngramEmbedding.forward`
     (fp32 × 2^(e-127) → bf16 RNE). **0 mismatches of 19,712 values** at both `ALIGN=4096` and `512`, O_DIRECT
     active, including the last row (short read at EOF).
3. **Reader I/O.** The reader uses `open(O_RDONLY|O_DIRECT)` + aligned `pread` (buffered fallback), 16 threads,
   never mmap. With the env var set, `engram_embd` is never created/read (`TENSOR_SKIP` if present). The bucket
   coverage check uses the row file's `n_rows`, and key_len and layer_id are checked.
4. **Hashing vs `inference/engram.py`.**
   - Multipliers (`default_rng(10007*layer)`, `*2+1`) match.
   - Primes match: shared `seen` set, restart at `engram_vocab_size-1` per n-gram size, and trial-division
     primality is correct for about 16M.
   - Offsets (per-layer cumsum over ngram-major, head-minor) match.
   - `pad = token_map[pad]` matches.
   - XOR rolling, `% prime + offset`, column order `(s-1)*n_heads+h` and the start-of-sequence blocking all match.
   - The compressed token-map function is identical to the reference.
5. **Patch 0004.**
   - The KV name is `%s.reap.routed_gain`; the converter writes `deepseek41.reap.routed_gain` as a FLOAT32 array.
     The loader `get_arr<std::vector<float>>` instantiation exists and type-checks FLOAT32.
   - Length and finiteness are checked.
   - Applied exactly once per layer (the only `build_moe_ffn` in deepseek41.cpp), to `moe_out` only, before
     `ggml_add(moe_out, ffn_shexp)`; the shared expert is not scaled. Absent key or all 1.0 leaves the graph unchanged.
   - The ladder verifies the gain survives quantize; the manifest and s12 cross-check it against
     `s10/heal/decision.json`.

   - `n_routed_experts` (192) is read from `text_config`; the top-level config has no conflicting key.
