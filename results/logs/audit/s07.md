## BLOCKER-1: `thor.json` is never written at create, so the first `thor` / `thor-trellis` layer unit dies

**Where.** `ops/lib/thor_format.py:45-47` (create branch), `ops/s07_quant.py:614` (parent creates) and `ops/s07_quant.py:651` (the unit re-opens).

**What happens.**
- `Build(create=True)` only builds `self.m` in memory. Nothing calls `save()` until the first `write_file`.
- `cmd_thor` creates the Build, then runs the embed unit and then layer 0 as **subprocesses** (`orchestrate.run_unit` → `subprocess.run`).
- The layer unit opens `TF.Build(build_dir(...), keepset_sha256=fp, n_routed_experts=n_keep)` without `create`. That raises `FileNotFoundError(.../thor/A192/thor.json)` before any replay work, so the unit exits with rc=1 and `chain.sh` writes STOP.
- A re-run hits the same error forever. `thor-trellis` has the identical path.
- `thor-b` is not affected: it runs in-process and its first `write_file` saves.

**Evidence.** `t_build.py` prints `thor.json exists after create=True: False`. A child process doing exactly what `unit()` does fails with the same `FileNotFoundError` traceback.

**Fix** (`ops/lib/thor_format.py`):
```diff
         elif create:
             self.root.mkdir(parents=True, exist_ok=True)
             self.m = {"format": FORMAT, **meta, "files": {}, "tensors": {}, "complete": False}
+            self.save()                      # units open the manifest from other processes
```

## BLOCKER-2: the parent's stale manifest overwrites every layer entry, so `finish_build` can never succeed

**Where.** `ops/s07_quant.py:631-632` (`write_globals(b)` and `finish_build(b, n_keep)` on the `b` created at line 614), and `thor_format.py:55-68`.

**What happens.**
1. The 40 layer units each write `layer-NN.safetensors` and save `thor.json` with that file's entries, from their own processes.
2. The parent's `b.m` still holds the empty manifest from before the units ran. `write_globals` → `b.write_file("globals.safetensors", …)` → `self.save()` rewrites `thor.json` with only the globals, vision and mtp entries. All 40 layer entries are deleted.
3. `finish_build` then sees `b.has(layer-NN) == False` for every layer and raises `SystemExit("build incomplete, missing layers [0, …, 39]")`.
4. On a re-run, the replay ledger marks every layer done, so no unit re-writes its entry. The layer files are on disk but the manifest no longer lists them, so the stage fails forever.
5. Recovery would mean deleting `thor_replay` ledger entries and redoing roughly 20+ GPU-hours of GPTQ.

The code already avoids this exact staleness for the replay ledger (`replay.Run(V["replay"]).led.done(...)` is re-read inside the loop at line 628), but not for the Build.

**Evidence.** `t_build.py`, with BLOCKER-1 patched by hand:
- `on disk after unit: ['layer-00.safetensors']`
- `on disk after write_globals: ['globals.safetensors']`
- `finish_build sees layer-00: False`

**Fix** (`ops/s07_quant.py`, `cmd_thor`):
```diff
     for L in range(N_LAYERS):
         if not replay.Run(V["replay"]).led.done(f"{V['stream']}/L{L}"):
             orchestrate.run_unit(me, ["unit", "layer", "--layer", str(L), *common], stage=STAGE, gpu=True,
                                  min_avail_gib=a.min_avail_gib)
+    b = TF.Build(build_dir(n_keep, "A" + V["suffix"]), keepset_sha256=fp, n_routed_experts=n_keep)   # units rewrote thor.json
     write_globals(b)
     finish_build(b, n_keep)
```

## CORRUPT-1: `expert_bytes` / `expert_bpw` count the 3 MTP layers' 128 experts as well

**Where.** `ops/lib/thor_format.py:77-79`. The filter `".ffn.experts." in n` also matches `mtp.{0,1,2}.ffn.experts.N.w{1,2,3}.{weight,scale}`, which `write_globals` copies into `mtp-*.safetensors`.

**Size of the error** (from the headers, `mtp.py`): MTP expert bytes are 7,219,445,760 B (6.72 GiB). The arm-A budget is 89.65 GiB, which is 2.8333 bpw. With the MTP bytes included, `thor.json` reports:
- `expert_bytes` = budget + 6.72 GiB;
- `expert_bpw` = **3.046 instead of 2.833**.

The arm-B build has the same problem: it reports about 4.57 bpw instead of 4.25.

**Consequences.**
- **(a) Wrong numbers on the published cards.** `s12_publish.py:110` puts `tj["expert_bpw"]` and `tj["expert_bytes"]` into the Thor card.
- **(b) The pre-registered trellis sub-arm can never be adopted.**
  - `plan_kt` (s07:375) takes `budget = tj["expert_bytes"]` = KQ routed + MTP.
  - `allocate` spends that budget on routed experts only (`expert_bytes()` in s07 has no MTP term). The KT routed experts therefore get about 7.2 GB, or 7.5%, more than the K-quant ones, so the comparison is no longer at matched bytes.
  - The finished KT build then reports KT routed + MTP ≈ KQ routed + 2×MTP, which is greater than KQ routed + MTP.
  - `gates.trellis` (`gates.py:139`) therefore always fails with "not a matched-bytes comparison", after GPU-hours of KT encoding.

**Fix** (`ops/lib/thor_format.py`):
```diff
     def expert_bytes(self) -> int:
+        """routed experts of the decoder layers only (the MTP/DSpark layers' 128 experts are copied unchanged)."""
         return sum(np.prod(t["stored_shape"]) * np.dtype(st_io.DT[t["dtype"]]).itemsize
-                   for n, t in self.m["tensors"].items() if ".ffn.experts." in n)
+                   for n, t in self.m["tensors"].items() if n.startswith("layers.") and ".ffn.experts." in n)
```

## CORRUPT-2 (if loaded by vLLM / ModelOpt): w1 and w3 get independent `weight_scale_2`, but the fused w13 path keeps only w1's

**Where.** `ops/s07_quant.py:116`, which calls `G.mxfp4_to_nvfp4` once per projection, and `ops/lib/ggml_quants.py:334`, where `emax` is taken per tensor.

**What happens.**
- `weight_scale_2 = 2^(emax-135)` uses each tensor's own largest E8M0 exponent, so w1 and w3 of the same expert generally differ by a power of two.
- vLLM's ModelOpt NVFP4 MoE fuses them (local checkout `~/vllm/vllm/model_executor/layers/quantization/modelopt.py:1543-1551`):
  ```
  if self.moe.is_act_and_mul and not torch.allclose(layer.w13_weight_scale_2[:, 0], layer.w13_weight_scale_2[:, 1]):
      logger.warning_once("w1_weight_scale_2 must match w3_weight_scale_2. Accuracy may be affected.")
  w13_weight_scale_2 = layer.w13_weight_scale_2[:, 0].contiguous()
  ```
- So every expert whose w3 `emax` differs from its w1 `emax` has its `up` projection scaled by 2^Δ: silently wrong output, with only a one-time warning.
- ModelOpt itself unifies the gate/up amax for this reason.
- Nothing in the pipeline loads the files: the s10 `nvfp4` gate measures the in-memory `healed_A` function. s12 can still make the repo public when that gate passes.

**Fix.** Use one shared `emax` per expert for w1 and w3. The repack stays lossless as long as both tensors fit the 17-octave window, and the `lossy_blocks` check still guards that.

## RISK-1: the NVFP4 repo cannot be loaded as written; the gate never tests the files

**Where.** `ops/s07_quant.py:197-210`.

**Why no loader can read it.**
- `config.json` keeps `quantization_config = {quant_method: fp8, scale_fmt: ue8m0, expert_dtype: fp4}`.
- vLLM reads `config.json`'s `quantization_config` first and only falls back to `hf_quant_config.json` when it is absent (`~/vllm/vllm/transformers_utils/config.py:781-790`). The new `hf_quant_config.json` is therefore ignored, and the experts would be loaded as MXFP4 even though they now carry `weight_scale`, `weight_scale_2` and `input_scale` instead of `.scale`.
- The model.py reference expects I8 weights plus E8M0 `.scale`, so it cannot load the experts either.
- Even with MIXED_PRECISION applied:
  - the MTP experts (shards 44-46 copied verbatim, MXFP4) are not listed in `quantized_layers`, so they would be treated as unquantized;
  - the dense block-32 ue8m0 FP8 is not expressible as ModelOpt `FP8`, which is per-tensor.

**Consequence.** The card says "loader compatibility UNVERIFIED", but s12 can flip the repo public on the s10 `nvfp4` gate, which never loads these bytes.

**Proposed change.** Record that no loader has been verified, and make s12 keep the repo private until a load test sets the flag.
```diff
     env.atomic_json(OUT / f"manifest_nvfp4_REAP{n_keep}.json", {
-        "keepset_sha256": fp, "repo": up.repo, "private": True, "heal_gains": gains, "quantized_tensors": len(quantized),
+        "keepset_sha256": fp, "repo": up.repo, "private": True, "heal_gains": gains, "quantized_tensors": len(quantized),
+        "loader_verified": False,     # s12: never make public while False (config.json still declares fp8/ue8m0)
```
In `ops/s12_publish.py`, the nvfp4 branch at about line 268 should then publish public only if `m.get("loader_verified")` is true.

## RISK-3: one unrepresentable block anywhere aborts the whole HARD nvfp4 step (unverified against real scales)

**Where.** `s07_quant.py:117-118`.

**What happens.** The repack is lossless only when every nonzero block of a tensor lies within 17 octaves of that tensor's largest exponent. I verified that the detection is exact: an 18-octave spread is caught (31 lossy blocks), and a 17-octave spread is exact (`t_quant.py`). A single outlier block in any of 192 × 3 × 40 tensors makes the step fatal for the chain.

**Not checked.** The docstring's "nvidia reports zero such blocks in 1017" is not verified. I did not read the E8M0 scales, because they are weights and out of bounds for this audit. CORRUPT-2's joint w1/w3 `emax` makes this slightly stricter.

**Suggested change.** Before s07 runs, do a CPU pre-flight that reads only the `*.experts.*.scale` tensors and codes (about 3% of the expert bytes) and counts blocks with `emax - e > 17`. Alternatively, have `nvfp4` write a per-tensor report and stop after the full pass rather than at the first bad tensor, so a single fix-up decision covers all of them.

## RISK-5 / NIT: the dense overlay has no consumer in the V4.1 runtime

- `cuda/src/v41_*` never loads an overlay. `nvfp4_load_overlay` exists only in the legacy `engine.cu` / `decode.cu`, which expect `tools/requant_dense_nvfp4.py`'s format.
- `s12_publish.py` does not ship `thor/overlay_nvfp4`.

## NITs

- **`thor_format.md:6, 75` is stale.** It says the s09 GGUF writer copies Thor expert bytes. In fact s09 and `llamacpp/convert_v41_reap.py` never read a Thor build (no `thor` reference in either); chain2 converts from the master.
- **Stale manifest metadata.** `Build(create=True)` on an existing `thor.json` silently keeps the old `alloc` and `heal` fields. If `alloc.json` or the heal decision changes between attempts, the remaining layers use the new values while `thor.json` reports the old ones. Compare `b.m["alloc"]` with `alloc["alloc"]` and refuse on a mismatch.
- **The nvfp4 small-file ledger has no content hash** (`led.finish(f"small/{rel}")`). If an `hf_quant_config.json` or `config.json` change happens after a partial run, it is never re-uploaded. Add `sha256=S5.sha256_file(p)` and re-upload when it differs.
- **No source re-verification.** `thor`, `thor-b`, `plan` and `overlay` read `env.SRC` without re-checking sha256. s05 verified it, and chain2 moves the source only later. `engram_items` reads shards 47/48 through Seagate symlinks, so layers 1 and 14 crash if the USB disk is unmounted.
- **Overlay RTN can zero blocks silently.** It zeroes any 16-block whose `amax/6/g` rounds below e4m3's smallest subnormal (`_e4m3_round` gives 0). Acceptable only because the s10 overlay gate measures it.
- **NVFP4 subnormal block scales.** NVFP4 block scales with `k ∈ {-9, -8, -7}` are e4m3 subnormals (bytes 0x01, 0x02, 0x04). ModelOpt and the PTX ue4m3 scale format should accept them, but I have not verified that against a kernel.
- **Duplicated globals.** Each Thor build (A, A-kt, B) carries a full copy of globals, vision and mtp (about 10.7 GiB). Hard-linking from A would save disk in the trellis and B steps.

## What I checked and found correct

**MXFP4 → NVFP4 math** (`t_quant.py`, against `ml_dtypes`):
- `e8m0` = 2^(e-127) matches `float8_e8m0fnu` bit for bit for e = 0..254, and 0xFF is refused.
- `e4m3_decode` matches `float8_e4m3fn` on all 254 non-NaN codes.
- `e4m3_pow2(k)` is exact for k ∈ [-9, 8], including the subnormals 2^-7..2^-9.
- One E8M0 32-block becomes two identical e4m3 16-block scales 2^(e-emax+8) (`np.repeat(…, 2, axis=1)`, in the right order), and the global scale is 2^(emax-135)·gain.
- Dequant equals the source × gain **bit-exactly** for e ∈ [110,127], [100,117] and [1,18], with gains 1.0, 0.937 and 1.13.
- The packed E2M1 bytes are unchanged.
- −0 code blocks (nibble 8) are treated as zero and do not set `emax`.
- Underflow detection is exact at 17 vs 18 octaves.

**Heal gain is applied exactly once everywhere:**
- NVFP4: w2 `weight_scale_2` only.
- Thor A: `W2 * gain` before GPTQ/LDLQ (s07:538), with no gain on w13.
- Replay: phase B and the s10 `thorA` / `thorA_overlay` arms use `ArmLayer(gain=1.0)`, and the replay arm dict has no `gain` key.
- CUDA: `k_combine` multiplies by `heal_gain` only if the optional tensor `ffn.heal_gain` exists, and s07 never writes it.
- Thor B ships unhealed by design.

**Routing weight placement is consistent.**
- The reference `Expert.forward` applies `weights * silu(gate)*up` before w2.
- The CUDA `swiglu(act, …, wp)` applies the routing weight before `act_quant_fp8` and w2.
- s07's w2 Hessian is built from `fake_act_quant(w · mid)` of the **quantized** w1/w3, which is exactly what FQExpert and CUDA feed w2.
- The NVFP4 w2 `input_scale` uses the s06 `amax_mid_ungated`, which is correct for loaders that apply the weight after w2.

**K-quant bytes:**
- `pack_q2k`, `pack_q3k` and `pack_q4k` + `G.dequant` match llama.cpp's own `gguf-py` `quants.dequantize` bit for bit for Q2_K, Q3_K and Q4_K. The test included all-zero and all-positive blocks.
- I also checked by hand against ggml's `block_q*_K` field order, the `get_scale_min_k4` packing, the Q3_K hmask/scales packing and the qs interleave.
- Row bytes: 1680 / 2200 / 2880 for in = 5120; 756 / 990 / 1296 for in = 2304. CUDA `bind_experts` checks the same stride.

**GPTQ** (`t_gptq.py`, CPU):
- The bytes written equal the values GPTQ believed it rounded to (max |d| = 0), for all three types.
- A diagonal (fallback) Hessian reproduces imatrix-weighted RTN byte-identically.
- The error-feedback formula and the lazy block update match Frantar et al.
- The existing tests `test_gptq_cpu`, `test_post` (18/18) and `test_pure` (17/17) pass.

**KT:**
- The rotated Hessian `R H Rᵀ` is built correctly from `rotate_t`.
- The LDLQ update `E·U_gg⁻¹·U_g,rest` is correct, and un-rotation is `sign ⊙ FWHT/16`.
- `KT.row_bytes`, `kt_scale` and `rht_sign` sizes match CUDA `bind_experts`.
- `kt_viterbi`'s C ABI matches `kt.viterbi_cuda`, and `cuda/build/libkt_viterbi.so` exists.

**Tensor names and dtypes** against the real headers (shards 1-5, 23, 43, 44, 47):
- Experts are `layers.L.ffn.experts.E.w{1,2,3}.weight` (I8 [out, in/2]) + `.scale` (F8_E8M0 [out, in/32]). `EXPERT` matches them and does not match `mtp.*`.
- Dims are 5120 / 2304. Both are multiples of 256 and of 128.
- Dense scales are 32×32 E8M0.
- The gate is BF16 [384, 5120]; bias and `bias_vl` are F32 [384].

**s03 / s06 bank fields used by s07 exist with the expected shapes.** s03 `L0.npz` has `amax_in` [384], `x2_in` [384, 5120], `x2_mid` [384, 2304], `n_tok` [384] and `sum` [9, 384]. The s06 bank is written in keep order with `keep`, `amax_mid_ungated`, `x2_in`, `x2_mid` and `n_tok`.
