# Per-expert mixed-precision quantization: can heterogeneous expert bit-widths within a layer actually be deployed on Jetson AGX Thor?

Scope note (2026-10-17): primary sources read directly (arXiv HTML/PDF, GitHub READMEs and source, local checkouts of llama.cpp `465e49b9c` 2026-09-07, vLLM 0.16.0 at `/home/patrickd/nvfp4-quantize/.../vllm`, our CUDA server at `~/glm-5.3-flash-cuda-server`). "pt" = absolute benchmark points. **The deliverable table (shipped format+kernel vs fake-quant) is in KQ1.** Existing notes in `extreme_quantization.md` KQ2 already summarise MxMoE/MoPEQ/GEMQ/BitsMoE/AlphaQ at abstract level; this file goes to the full-text tables and the runtime code, and corrects one premise: the "+20–25 pt" headline compares mixed-2.54-bit against uniform-2.0-bit, not matched bits.

## KQ1. For each method: allocation rule, bit grid, gain vs uniform at MATCHED bits, largest model, and shipped format+kernel vs fake-quant

### Takeaway
Only four of the named methods ship anything executable, and none of them ships a format a stock runtime loads: MC-MoE (HQQ dequant per expert), GEMQ (HQQ packing + fused Triton decode kernel, 1/2/3-bit), AlphaQ (same HQQ-prefill/Triton-decode backend, per-linear not per-expert) and BitsMoE (vLLM 0.11.0 adapter + runtime kernels, checkpoints released, quantizer NOT released). MxMoE ships generated mixed-precision GroupGEMM micro-kernels for RTX 4090 only (microbenchmark, no end-to-end runtime); MoPEQ is file-size-only fake-quant; EAC-MoE is not per-expert mixed precision at all. At matched average bits the per-expert gain is model-dependent: +0.3 to +3 pt on Mixtral (8 experts), +0.8 pt on Qwen3-30B-A3B, +6 to +13 pt on Qwen1.5-MoE (60 experts); the +25 pt figure is MC-MoE's 2.54-bit mix versus uniform 2.0-bit GPTQ.

### Cited Findings

**MC-MoE / PMQ (ICLR 2025, TPAMI 2026; arXiv 2410.06270)**
- Allocation: integer program minimising Σ_i Σ_j φ_i^α · w_i^β · (ε_{i,j} x_{ij})^γ where φ_i = activation frequency n_i/N, w_i = activation-weighted routing score, ε_{i,j} = Frobenius output change when expert i is quantised to j bits; constraints: average bits per MoE block = target, one width per expert, at least one 2-bit and one 3-bit expert per block. Solve time ~1 s. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- Bit grid for experts **{1, 2, 3}**; attention and gating fixed at 4-bit (adds ≤0.05 avg bits); 4-bit experts never tested. Base quantiser GPTQ (OmniQuant as alternative), 128×2048 C4 calibration. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- Mixtral-8x7B, 8-task zero-shot average (FP16 = 71.29): uniform GPTQ 2.00-bit 42.67; BSP 2.54-bit 49.07; Hessian-allocated 2.54-bit 67.18; PMQ 2.54-bit **67.50**; PMQ 2.05-bit 63.25; PMQ 1.57-bit 54.49. MMLU 5-shot (FP16 70.60): uniform 2-bit 34.05, PMQ 2.54-bit 61.19. Mixtral-8x22B (FP16 76.33): uniform 2-bit 50.44, PMQ 2.54-bit 72.08, PMQ 2.05-bit 67.94. **The +25 pt is 2.54-bit mixed vs 2.00-bit uniform; the paper's own 2.54-bit Hessian baseline is within 0.3 pt of PMQ.** — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- Largest model: Mixtral 8x22B. Repo supports only Mixtral 8x7B and 8x22B. — [GitHub Aaronhuang-778/Mixture-Compressor-MoE](https://github.com/Aaronhuang-778/Mixture-Compressor-MoE)
- Shipped: `main.py --eval_ppl` is fake-quant; `--pack --save` writes a packed model loaded by `inference.load_quantized_model`; storage/dequant via HQQ with a modified 1-bit storage path; downstream LM-harness accuracy is measured on fake-quantised models. 2.54-bit Mixtral-8x7B: 38 tok/s on one A100 vs 23 tok/s FP16 on two A100s; ~52 tok/s on RTX 3090; 112.6 GB → 20.7 GB peak. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2); [repo README](https://github.com/Aaronhuang-778/Mixture-Compressor-MoE)
- Follow-up MC# (Oct 2025, arXiv 2510.10962) extends to DeepSeek-VL2: 6.2× weight reduction at ~2.57 bits with 1.7% drop on five multimodal benchmarks. — [MC#](https://arxiv.org/html/2510.10962v1)

**MxMoE (ICML 2025; arXiv 2505.05799)**
- Granularity is per **linear block** (gate/up/down inside each expert), not per expert; the paper shows linear-level beats expert-level (DeepSeek-V2-Lite W5A5 ppl 6.11 vs 6.32; Qwen1.5-MoE 6.95 vs 6.98). Objective min L^r · T^(1−r) under a memory budget via ILP; L = output perturbation on 128×4096 WikiText2 sequences, T = profiled per-tile time on the target GPU; r = 1 for weight-only. Scheme set includes W2A16, W4A16, W8A8, W4A4, FP8. — [MxMoE](https://arxiv.org/html/2505.05799v1)
- Weight-only Wikitext2 ppl / avg accuracy, GPTQ → MxMoE at 2.25 bit: DeepSeek-V2-Lite 8.49/58.04 → 7.01/62.04 (+4.0 pt); Qwen1.5-MoE 11.19/49.07 → 8.79/55.39 (+6.3); Qwen2-MoE 7.98/58.58 → 7.57/64.57 (+6.0); Mixtral-8x7B 5.69/67.56 → 5.63/67.89 (+0.3). At 3.25 bit the gaps are ≤0.2 pt and GPTQ is better on Qwen2-MoE (71.57 vs 71.05). — [MxMoE](https://arxiv.org/html/2505.05799v1)
- Kernel: one auto-generated fused kernel that horizontally fuses CTA-level micro-kernels (one per scheme) with a precision-aware tile scheduler; a unified runtime-dispatch kernel was rejected because branch checks block loop unrolling. Throughput 1.6–2.7× over FP16 at 512 tokens (memory-bound), 3–3.4× at 8192 tokens; **no batch-1 decode number**. Hardware RTX 4090; README: "mainly test on RTX-4090", "cannot fully utilize the performance of hopper and later GPU architectures"; performance path is a per-layer GroupGEMM microbenchmark (`run_mxmoe_gg.py`), no end-to-end runtime; accuracy and kernel paths are separate commands. Largest model Qwen2-MoE-Instruct (106.9 GB). — [MxMoE](https://arxiv.org/html/2505.05799v1); [GitHub cat538/MxMoE](https://github.com/cat538/MxMoE)

**GEMQ (ICML 2026; arXiv 2605.23078)**
- Allocation: binary LP minimising summed estimated task-loss increase (Taylor/Gauss-Newton with diagonal Fisher on MoE-layer output), global across layers so experts are comparable model-wide; each layer must keep ≥1 high-bit expert; **no activation-frequency term**. Router fine-tuning: experts and attention frozen, router only, AdamW 1e-4, one epoch, ~59 s on Mixtral; routers <0.04% of params. Progressive pipeline reuses the previous quantised model for importance. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- Bit grid **{1, 2, 3}** for experts, attention 4-bit; budgets 3.0 / 2.5 / 2.0 / 1.5 bits-per-expert; GPTQ asym group 128. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- Mixtral-8x7B Table 1 (WT2 ppl / C4 ppl / 0-shot avg; FP16 3.84/7.40/70.97): **2.5 bpe: uniform GPTQ 6.10/10.35/65.49; PMQ 5.10/9.21/64.34; GEMQ 5.03/9.02/65.13** — i.e. at matched 2.5 bits the mixed methods LOSE 0.4–1.2 pt of zero-shot average to uniform while winning ~1 ppl. 2.0 bpe: uniform 6.29/11.73/55.72; PMQ 60.38; GEMQ 59.98 (+4.3 pt). 1.5 bpe: uniform 10.67/25.39/47.45; PMQ 51.78; GEMQ 52.00. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- Models: DeepSeek-V2-Lite, Qwen1.5-MoE-A2.7B, Qwen3-30B-A3B, Mixtral-8x7B (largest, 46.7B). Peak quantisation memory 191.2 GB (vs 31.8 GB for PMQ) — the limitations section says this may exceed one GPU for very large models. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- Shipped: HQQ bit-packing for storage; "Efficient low-bit MoE triton kernels for **real** quantized inference" (1/2/3-bit dequant + grouped GEMM); real vs fake ppl gap 0.06% (DSV2-Lite) / 0.03% (OLMoE); decoding fully fused, **prefill loops over hit experts in Python** (launch-bound). Decode batch 1, H100-80GB: DSV2-Lite FP16 159.4 tok/s → 2.5-bit 229.8 tok/s (1.4×) / 1.5-bit 248.4; Mixtral 2.5-bit 82.5 tok/s at 17.8 GB. ILP solver HiGHS default, Gurobi optional. — [GEMQ repo](https://github.com/jndeng/GEMQ); [GEMQ](https://arxiv.org/html/2605.23078v1)

**BitsMoE (arXiv 2606.00079, June 2026)**
- Method: SVD of the concatenated expert weights per layer into a shared basis (kept 8-bit, Marlin W8A16) plus expert-specific spectral components; the components (not whole experts) are the allocation unit; ILP per projection type, pooled across all layers and experts; cost = spectral energy α² × activation-dependent importance β × bit distortion. Grid **{16, 8, 6, 4, 3, 2, 1, 0}** (components can be dropped). Spectral energy alone gives 26.48% avg; full cost model 64.29%. — [BitsMoE (alphaxiv full text)](https://www.alphaxiv.org/abs/2606.00079.md)
- Qwen3-30B-A3B-Base at 2 bits, 7-task avg: BitsMoE 64.29 vs GEMQ 61.49, MoEQuant 58.33, MxMoE 45.86, MiLo 44.70, GPTQ 42.65. No 2.5-bit results (range 1.4–2.0). Largest model Qwen3-Next-80B-A3B in the paper; released checkpoints also include Qwen3-235B-A22B at 1.6-bit. — [BitsMoE](https://www.alphaxiv.org/abs/2606.00079.md); [BitsMoE repo](https://github.com/zjiayu064/BitsMoE)
- Throughput: A6000; GPTQ baseline on the Triton backend "because Marlin and ExLlamaV2 do not support 2-bit GPTQ" — 6.46× (30B) / 8.71× (80B) is against a slow baseline. — [BitsMoE](https://www.alphaxiv.org/abs/2606.00079.md)
- Shipped: repo is "currently inference-only"; "runtime kernels, model patching logic, and 2-bit and 1.6-bit checkpoints" released; quantisation pipeline "coming soon"; vLLM adapter pinned to `vllm==0.11.0`, CUDA 12.8, GCC ≥12; checkpoints for DeepSeek-V2-Lite, Qwen3-30B-A3B-Base, Qwen3-Next-80B, Qwen3-235B. — [BitsMoE repo](https://github.com/zjiayu064/BitsMoE)

**MoPEQ (arXiv 2509.02512, Sept 2025)**
- Allocation: per-expert Hessian trace (Hutchinson), summed over gate/up/down, Frobenius-norm proxy loss so no calibration data; k-means into three clusters, highest-importance cluster gets the highest width; grid **{2, 3, 4}**; layer-wise vs model-wide pooling, model-wide wins 63 vs 42 task/model combinations. — [MoPEQ](https://arxiv.org/html/2509.02512v1)
- Models: DeepSeek-VL2-Tiny/Small/base and MolmoE-1B (VLM MoEs); e.g. DeepSeek-VL2 base Hessian model-wise 10.485 GB → MME-P 1623.4 vs uniform 4-bit 14.353 GB → 1614.6; no matched-size uniform row. Hessian beats frequency on 7 of 9 tasks on DeepSeek-VL2-Base. — [MoPEQ](https://arxiv.org/html/2509.02512v1)
- Shipped: AutoRound/SignRound quantiser; the paper states existing frameworks such as vLLM lack mixed-precision support for VLM-MoEs, reports model FILE sizes, and lists hardware performance as future work — **fake-quant / file-size only, no kernel**. — [MoPEQ](https://arxiv.org/html/2509.02512v1)

**AlphaQ (ICLR 2026; arXiv 2606.04980)**
- Allocation unit is the **individual linear layer** (up/gate/down projection inside an expert), not the expert: "we apply mixed-precision quantization at layer granularity: each layer is assigned a bit-width from {1,2,3,4}"; §4.4 reports layer-wise beats expert-wise in every setting. Signal: PL_Alpha_Hill tail exponent of each layer's weight spectrum (heavier tail → more bits), cost η = (ᾱ/α_l)^γ · Var(W_l) · 2^(−2b); ILP (multiple-choice knapsack, PuLP) under a global budget; global beats block-wise (Mixtral 2.5-bit ppl 5.17 vs 5.81). GPTQ asym g128, 128 WikiText2 samples for the quantiser; calibration-free claim applies only to allocation. Attention and router uniform 4-bit. — [AlphaQ HTML](https://arxiv.org/html/2606.04980v1); [AlphaQ (alphaxiv)](https://www.alphaxiv.org/abs/2606.04980.md)
- Table 1 at 2.5 avg bits (WT2 ppl / 5-task avg): Mixtral-8x7B uniform 6.16/67.86, PMQ 5.32/70.38, AlphaQ 5.17/70.76; DeepSeekV2-Lite uniform 8.14/65.15, PMQ 6.95/65.75, AlphaQ 6.64/66.74; Qwen1.5-MoE uniform 10.36/51.99, PMQ 9.01/62.18, AlphaQ 8.14/65.17; **Qwen3-30B-A3B uniform 10.29/68.76, PMQ 10.94/65.88 (worse than uniform), AlphaQ 9.27/69.56 (+0.8 pt)**. — [AlphaQ HTML](https://arxiv.org/html/2606.04980v1)
- Shipped: "reuse the PMQ-style HQQ backend for dequantization in the prefill stage ... and implement fused Triton kernels ... in the decode stage of MoE expert layers"; Mixtral 96.8 GB → 13.4 GB measured on A40; code at Superone77/AlphaQ (contents unverified). Whether layers of different widths run in separate kernels is in Appendix A.11, not read. — [AlphaQ (alphaxiv)](https://www.alphaxiv.org/abs/2606.04980.md)

**EAC-MoE (ACL 2025; arXiv 2508.01625)**
- Not per-expert mixed precision. Experts are uniform within a setting; the "2.5-bit" setting is 3-bit experts in the first half of layers and 2-bit in the second half; MHSA 4-bit, router full precision. QESC = GPTQ + layer-by-layer router calibration with a TopK-MSE loss; PESF = dynamic prefill-only pruning of experts selected less than α× average. Mixtral WT2 ppl / 8-task avg: 2.06-bit GPTQ 5.51/62.56 → QESC 5.09/66.31; 2.54-bit 4.74/68.65 → 4.54/69.61; 3.03-bit 4.16/68.92 → 4.14/72.21 (FP 3.84/72.64). Storage via BitBLAS; speedups measured as context latency at batch 4 × 512 tokens (1.64× avg). Models Mixtral-8x7B, Phi-3.5-MoE, DeepSeek-MoE-16B, Qwen1.5-MoE. — [EAC-MoE](https://arxiv.org/html/2508.01625v1)

**Other precedents found**
- DynaExq (arXiv 2511.15015, Nov 2025): runtime hot/cold tiers (FP16 vs INT4 on Qwen3-30B; INT4 vs INT2 on Qwen3-80B), AutoRound quantiser, EMA of router probabilities as hotness, two memory pools with fixed-size blocks, PyTorch/HF implementation, no kernel library named. Six-benchmark average: Qwen3-80B INT4 77.74, INT2 72.65, DynaExq-A6000 76.68 (+4.03 over INT2), DynaExq-5090 73.88; Qwen3-30B FP16 65.96, INT4 64.72, DynaExq-A6000 65.15. "Typically retain more than 85% of INT2 throughput". No static-mixed baseline, no code link found. — [DynaExq](https://arxiv.org/html/2511.15015v1)
- Chowdhury et al. (ICLR 2026, "Efficient Quantization of MoE with Theoretical Generalization Guarantees"): bits assigned by each expert's change in router L2 norm during training (smaller change → higher precision) plus intra-neuron variance; Switch Transformer and Mixtral; abstract gives no numbers, grid, or kernel statement. — [mlanthology abstract](https://mlanthology.org/iclr/2026/chowdhury2026iclr-efficient/)

### Inferences
- **Deployability ranking of the shipped artefacts**: GEMQ (HQQ pack + fused Triton 1/2/3-bit decode kernel, real==fake verified) is the only method whose released code could in principle run a per-expert mixed layer end to end; BitsMoE runs in vLLM 0.11.0 but only for its own SVD-factored format and only for checkpoints its authors made (quantiser unreleased); MxMoE's kernels are a 4090 microbenchmark; MC-MoE's HQQ path is dequant-then-matmul per expert (works trivially with heterogeneous experts because each expert is its own Linear, but is not a bandwidth-efficient decode kernel). None targets aarch64 or sm_110.
- **The matched-bit gain tracks routing skew / expert count, not the method.** Mixtral (8 experts, balanced) gains 0.3–3 pt; Qwen3-30B (128 experts) +0.8 pt (and PMQ loses 2.9 pt); Qwen1.5-MoE (60 experts, known skewed) +6 to +13 pt. GEMQ's own Table 1 shows zero-shot parity-or-worse vs uniform at 2.5 bpe on Mixtral. The literature's "second-best lever" status rests on fine-grained small MoEs; on GLM-5.3-Flash (288 → 144 experts, top-8) the expected matched-bit gain is between the Qwen3-30B and Qwen1.5-MoE cases and cannot be assumed to be +20 pt. **[extrapolation]**
- All seven methods pin attention at 4-bit and never demote dense/shared/attention — consistent with the "bimodal" observation in the assignment: the protected-tensor rule is universal, and the per-expert allocation is layered on top of it, not a substitute for it.

### Gaps
- GEMQ's "uniform" 2.5-bpe row is not defined in the text read (likely a 2/3-bit layer split as in EAC-MoE); the comparison is therefore between two different mixes, not against a true single-width baseline.
- AlphaQ Appendix A.11 (runtime details, whether mixed widths use separate kernels) was not read. MxMoE's repo configs show only W4A4/W8A8; whether the released generator emits W2A16/W3A16 kernels is unverified.
- No per-expert mixed-precision result exists on any model ≥107 GB except BitsMoE's 235B checkpoint (its own format) and llama.cpp tensor-level mixes; no result on a sigmoid/noaux_tc router (DeepSeek-V3/GLM-5 family).

## KQ2. Which on-disk formats can represent per-EXPERT (not per-tensor-type) bit allocation?

### Takeaway
GGUF cannot: all routed experts of a layer are one 3-D `ffn_{gate,up,down}_exps` tensor with one `ggml_type`, `--tensor-type` binds a type to a whole tensor by name regex, and llama.cpp's own history (PR #4927, 2024) records that mixed types among a layer's experts produced garbage because "it is assumed all experts use the same quantization". EXL3 and HF safetensors (compressed-tensors, our NVFP4 checkpoint) store each expert as its own tensor, so the *file* can carry heterogeneous per-expert formats; the constraint moves to the runtime (KQ3). No llama.cpp issue or PR proposing per-expert types or splitting the fused tensors was found.

- The MXFP4_MOE ftype selects by `tensor->ne[2] > 1` ("MoE tensors -> MXFP4, other tensors -> Q8_0", with a note that MLA projection tensors are also 3-D) — confirming the routed experts are the 3-D tensors. — local `src/llama-quant.cpp` lines 478–490

### Inferences
- GGUF per-expert mixing would require either (a) splitting `ffn_*_exps` back into per-expert 2-D tensors plus a new `mul_mat_id` that takes a per-expert type table, or (b) two fused tensors per projection (KQ5). Neither exists; (a) was explicitly removed in 2024 (#6387) for performance, so upstream acceptance is unlikely. **[inference]**
- What tensor-level mixing CAN express — per layer × per projection (gate/up/down) × per class (dense, shared, attention, embed, output) — is exactly what Collaborative Compression used to get 130 GB ≈ 230 GB; that result is evidence that **protecting the non-expert tensors and choosing per-layer expert types** captures most of the deployable gain at 671B scale, since routed experts there were never raised above the base type. The per-expert residual is unmeasured at that scale. **[inference]**
- For a safetensors-based pipeline (compressed-tensors / our server) the file format is a non-issue: per-expert tensors can already hold different `weight_packed` encodings; what is missing is a `quantization_config` vocabulary for it and a runtime that honours it (KQ3).

### Gaps
- Whether any GGUF-side proposal exists in discussions/PRs beyond the top-5 of 931 API hits was not exhaustively checked (the `gh` CLI is not installed locally).
- Whether exllamav3's converter assigns a shared `qgroup` to experts somewhere outside `linear.py`/`allocation.py` (e.g. in the model definitions) was not verified; the default is per-tensor.

## KQ3. Which RUNTIMES execute a layer whose experts have different bit-widths without falling to the slowest path?

### Takeaway
None of the stock runtimes do. llama.cpp's `ggml_cuda_mul_mat_id` dispatches on `src0->type` once per tensor (MMVQ templated on type at small batch, MMQ, MMF, or a sorting fallback that syncs the stream and disables CUDA graphs); vLLM's compressed-tensors `get_moe_method` reads the scheme of expert 0 only and applies it to the whole `FusedMoE`, with WNA16/Marlin limited to {4, 8} bits; exllamav3's fused bszN kernel takes a single `K` per projection, so mixed-K experts would need its per-expert fallback loop; the only working heterogeneous paths are per-expert dequant loops (MC-MoE/HQQ, DynaExq/HF) and the method-specific Triton kernels (GEMQ, AlphaQ) or MxMoE's horizontally-fused kernel. A hand-written grouped GEMV at batch 1 is per-expert anyway, which is why our own server is the realistic target.

### Inferences
- **vLLM silently mis-serves a per-expert mixed checkpoint rather than erroring**: because only `experts.0.*` is consulted, a compressed-tensors config whose `targets` give expert 7 a different scheme would load expert 0's scheme for all experts and then fail (or corrupt) at weight-load time when expert 7's packed shapes mismatch. Per-expert heterogeneity in vLLM is therefore "unsupported → error or garbage", not "fallback". **[inference from the code]**
- For llama.cpp a two-type layer is impossible without a new graph node; the only expressible split is two separate `ffn_*_exps` tensors (KQ5), each with its own uniform type, which costs one extra `mul_mat_id` launch per projection and leaves CUDA graphs intact as long as both stay inside the MMVQ batch limit.
- In our server, heterogeneity is a warp-uniform branch on a per-expert format tag (the slot is `blockIdx.y`, so a whole block sees one expert): zero extra launches, no divergence; the cost is instruction count in a kernel that is already instruction-bound, so the cold tier's unpack must be as cheap as the FP4→FP8 hardware path or it will cost time per byte (cf. the earlier finding that INT2 "is a net decode LOSS on Thor (no hardware datapath)" in [[reap-criterion-and-corpus-audit]]). **[inference]**
- exllamav3 is the only third-party runtime where the FORMAT already supports per-expert bpw; making its kernel honour mixed K is a contained change (pointer tables already exist; `K` would move from the MultiLinear to the per-expert entry), but it is an unported aarch64/sm_110 stack with no evidence of ever running on Thor.

- Not measured: what exllamav3 actually does if a recipe assigns different K to experts of one layer (it may assert at load, or run the slow path); not tested because exllamav3 is not built on Thor.
- Not checked: SGLang's fused-MoE quant config code; expected to mirror vLLM (single scheme per layer) but unverified.

## KQ4. Decode cost of heterogeneity on a bandwidth-bound device

### Takeaway
Bytes-per-token is what a bandwidth-bound decoder pays, and per-expert mixing changes it by the routing-frequency-weighted average of the expert widths, not the memory-weighted average: demoting cold experts saves resident memory (the Thor fit constraint) while barely reducing decode bytes, and promoting hot experts raises decode bytes. Kernel-level overhead ranges from ~0 (warp-uniform format tag in a grouped GEMV, or one extra `mul_mat_id` launch per projection for a two-tensor split) to large (per-expert Python loops, Triton dequant kernels that reach only 1.4× over FP16 at 2.5 bits on H100).

### Cited Findings
- GEMQ decode, batch 1, H100: DeepSeek-V2-Lite FP16 159.4 tok/s → 2.5-bit 229.8 tok/s (1.4×) → 1.5-bit 248.4 tok/s, against a 6.4× byte reduction — the Triton dequant path captures ~22% of the byte saving. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- MC-MoE: 2.54-bit Mixtral-8x7B 38 tok/s (one A100) vs FP16 23 tok/s (two A100s); 48–60% per-token latency reduction. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- MxMoE: 1.6–2.7× over FP16 in the memory-bound (512-token) regime on RTX 4090; no batch-1 number. — [MxMoE](https://arxiv.org/html/2505.05799v1)
- BitsMoE 6.46×/8.71× decode is versus 2-bit GPTQ on the Triton backend because "Marlin and ExLlamaV2 do not support 2-bit GPTQ". — [BitsMoE](https://www.alphaxiv.org/abs/2606.00079.md)
- DynaExq retains "more than 85% of INT2 throughput" with mixed tiers on PyTorch/HF. — [DynaExq](https://arxiv.org/html/2511.15015v1)
- FlexMoE (per-expert *widths*, the analogous heterogeneity): naive per-expert slicing on SGLang ran at 0.85–0.94× of unpruned; a width-bucketed batched-GEMM kernel recovered 1.12–1.47×. — [FlexMoE, as recorded in expert_width_slimming.md](https://arxiv.org/html/2606.27866v1)
- Thor measured: streaming read 235–247 GB/s in-process; our MoE phase at 82% of achievable; decode 11.86 tok/s at B_tok 9.762 G/token; CUDA graphs gave nothing ("wall exceeds the dprof kernel total by only 0.4%"); each expert triple ~4.7 MB at NVFP4, 86 distinct experts ≈ 400 MB per layer at M=16 (not an L2 working set). — [[glm53-decode-gap-profile]], [[glm53-nvfp4-dense-overlay]], local `OPTIMIZATION_LOG.md` #11–#12
- The small-batch cost cliff in llama.cpp (`op_offload_min_batch_size=32`) and the measured finding that activation traffic (4 B of x per weight) is the binding term in our gemv — any format change must be judged on bytes of weight AND activation per output row. — [[llamacpp-small-batch-offload-cliff]], [[glm53-activation-traffic-finding]]

### Inferences
- **Byte model.** Let f_e be the routing share of expert e and b_e its bytes/weight. Decode expert bytes/token ∝ Σ_slots b_{e(slot)} ≈ 8·E·Σ_e f_e b_e / 8 = Σ_e (8 f_e) b_e; memory ∝ Σ_e b_e. Demoting the coldest half of the experts from 0.5625 B/w (NVFP4) to ~0.30 B/w (2-bit + scales) cuts memory by ~23% but cuts decode bytes only by 23% × (routing share of that half), which on a load-balanced router is ≈ 23% × 0.5 ≈ 12% and on a skewed router much less. Conversely a hot/cold split that puts hot experts at 4-bit and cold at 2-bit has decode cost ≈ that of uniform 4-bit. **On Thor the value of per-expert mixing is memory, i.e. fewer experts pruned at the same envelope — not tok/s.** **[estimate]**
- Dispatch overhead for a two-tensor split in llama.cpp: 3 extra `mul_mat_id` launches per MoE layer × 42 layers ≈ 126 launches/token; at ~5–10 µs each that is 0.6–1.3 ms on an ~85 ms step (<2%), provided both tensors stay on the MMVQ path (no stream sync). **[estimate]**
- Dispatch overhead in our server: none (per-slot descriptor already resolved per warp). Per-byte cost depends entirely on the cold tier's unpack instruction count; a 2-bit codebook/trellis tier that needs a shared-memory LUT would hit the same conflicted-LDS wall the e4m3 LUT hit. **[inference]**

### Gaps
- No published batch-1 decode measurement of a per-expert mixed layer on any bandwidth-bound edge device; all numbers are H100/A100/4090/A6000 and most are against weak baselines.
- Our server's exact routed-expert share of B_tok at decode was not recomputed here (the 0.5945 G figure in `moe.cu` comments is per layer at M=16 context and should be re-derived before pricing a tier split).

## KQ5. A practical two-tier scheme (hot group at high precision, cold group at low precision as two expert tensors with a router remap)

### Takeaway
No runtime supports "two expert groups per layer" by configuration: vLLM's shared-expert machinery is a single always-on expert (not routed), expert-parallel grouping partitions by rank at one dtype, and llama.cpp's graph has one `ffn_*_exps` triple per layer. The only runtime precedent for hot/cold tiers is DynaExq, implemented as two memory pools in PyTorch/HF with AutoRound weights. A static two-tier split is therefore a model-code patch in every stack (two `FusedMoE`/two `mul_mat_id` triples fed by one router whose top-k ids are partitioned by group with per-group zero-weight padding) — cheapest in our own server, where it is a format tag per expert rather than a second group.

### Cited Findings
- DynaExq: hotness = EMA of router probabilities; per-layer high-precision resident set under a budget; promotions/demotions applied asynchronously; two dedicated memory pools with fixed-size blocks per format; +4.03 pt over static INT2 on Qwen3-80B (A6000); no static mixed baseline; no code release found. — [DynaExq](https://arxiv.org/html/2511.15015v1)
- vLLM compressed-tensors: one `weight_quant` per `FusedMoE`/`RoutedExperts` module; `ignore` only un-quantises whole modules. — local `compressed_tensors_moe.py` lines 125–160; [vllm compressed_tensors.py](https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors.py)
- llama.cpp: `mul_mat_id` consumes one `src0` (all experts) plus `ids`; the fused-FFN pattern matcher expects `MUL_MAT_ID, MUL_MAT_ID, GLU` triples (`mul_mat_id_glu_ops`). — local `ggml-cuda.cu` lines 1686–1745, 3190–3209
- Our server: `k_route` produces `sel[KS]`/`wts[KS]` per token, `N_ROUTED_EXPERT = 144` is a compile-time constant, and the expert kernels take the `Nvfp4Mat* experts` table plus `sel`. — local `kernels/moe.cu` lines 51–52, 156, 244–246, 670–683; [[reap-criterion-and-corpus-audit]]
- Non-uniform per-layer expert COUNTS were already rejected as unshippable for the same reason (single scalar `num_local_experts` read by transformers, vLLM, GGUF converter and `glm5_config.h`). — [[reap-criterion-and-corpus-audit]]
- Collaborative Compression's deployable mix on llama.cpp is per-layer: routed experts of chosen layers at IQ1_S, the rest at IQ1_M, all non-expert tensors protected. — [arXiv 2509.25689](https://arxiv.org/html/2509.25689v1)

### Inferences
- **Router remap for a static split.** Keep the router unchanged (E logits, top-k over all E). Partition experts into H (hot) and C (cold) by a permutation P; after top-k, map each selected id to (group, local index). In vLLM/SGLang this is a patched model class running two `FusedMoE` layers (`num_experts=|H|` and `|C|`) on the same hidden states with `topk_ids` rewritten per group and `topk_weights` zeroed for ids outside the group (fused_moe tolerates zero weights but still gathers those rows, so the padding costs one extra expert read per non-member slot unless ids are compacted) — a correctness-safe but ~2× gather-overhead patch. In llama.cpp it is two `ffn_*_exps` triples in `build_moe_ffn` with the same masking. In our server it is simpler: a per-expert `fmt` field in `Nvfp4Mat`, branch per warp. **[design inference, no precedent]**
- The "shared experts" machinery is not a route: shared experts are unrouted and summed with weight 1 (slot 8 in our kernel), so they cannot host a second routed group without a router change.
- Because the cold group is by construction rarely routed, the two-tier scheme's decode cost is set by the hot tier; its benefit is purely resident memory, which on the Thor envelope converts to a lower prune ratio (the 14:1 pruning-vs-quant damage ratio measured locally makes that conversion the entire motivation). **[inference]**

### Gaps
- No paper or repo implements a static two-group split in vLLM, SGLang or llama.cpp; the remap above is a design, not a citation.
- Whether vLLM's `fused_moe` kernels accept out-of-range (padded) `topk_ids` safely was not verified in code.

## KQ6. How the bit allocation is chosen, and what our banked per-expert saliency enables offline

### Takeaway
The field has moved away from routing frequency: MoPEQ (Hessian trace, no calibration) beats frequency on 7/9 tasks, GEMQ drops the frequency term for a global Fisher/Taylor loss, AlphaQ (weight-spectrum alpha, calibration-free) beats PMQ everywhere and shows PMQ's frequency-driven allocation underperforming uniform on Qwen3-30B and shifting with the calibration domain; BitsMoE's ablation shows a spectral term alone is useless (26.5% vs 64.3%) without an activation-importance factor. Our banked saliency gives routing counts, gate mass and gated-output norms (MC-MoE's φ and w), but not the per-expert quantisation error ε_{i,j} or Hessian trace that the stronger allocators use — both are computable offline from the weights alone.

### Cited Findings
- MC-MoE's signals: φ_i (frequency), w_i (activation-weighted routing score), ε_{i,j} (output Frobenius change at j bits); hyper-parameters α, β, γ hand-tuned; its 2.54-bit Hessian-allocated baseline scored 67.18 vs PMQ 67.50. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- GEMQ: no frequency term; importance = global Taylor/Gauss-Newton loss estimate with diagonal Fisher; argues layer-wise estimates ignore quantisation-induced router shift; router fine-tune 59 s. — [GEMQ](https://arxiv.org/html/2605.23078v1)
- MoPEQ: Hessian trace (Hutchinson) with Frobenius proxy, no calibration; load-balancing losses make frequency less informative; Hessian beats frequency on 7 of 9 tasks (DeepSeek-VL2-Base); hybrid frequency-sensitivity score mixed. — [MoPEQ](https://arxiv.org/html/2509.02512v1)
- AlphaQ: calibration-free Hill-estimator alpha per linear; Appendix A.1 Fig. 6 shows activation frequencies and the resulting PMQ allocations on Mixtral change with calibration domain (C4 / MATH / GitHub-Code); OLMoE 3-bit: AlphaQ avg 28.86 vs best PMQ variant 27.69; Qwen3-30B 2.5-bit PMQ 65.88 < uniform 68.76 < AlphaQ 69.56. — [AlphaQ HTML](https://arxiv.org/html/2606.04980v1)
- BitsMoE ablation: spectral energy α² alone 26.48% vs full cost model (α² × activation importance β × distortion) 64.29%. — [BitsMoE](https://www.alphaxiv.org/abs/2606.00079.md)
- Chowdhury et al.: allocate by the expert's router-L2-norm change during training (small change → "less frequent but critical features" → more bits) and intra-neuron variance. — [mlanthology](https://mlanthology.org/iclr/2026/chowdhury2026iclr-efficient/)
- EAC-MoE: quantisation biases expert selection ("expert-shift"), fixed by router calibration with a TopK-MSE loss; GEMQ's router fine-tune addresses the same effect. — [EAC-MoE](https://arxiv.org/html/2508.01625v1); [GEMQ](https://arxiv.org/html/2605.23078v1)
- Our banked artefacts (`~/glm-5.3-reap/artifacts/saliency/*.pt`, 42 layers): per-expert, per-bucket `norm_sum/norm_sq_by_bucket` (gate-free output norms), `gate_sum/gate_sq`, `sq_by_bucket`, routed-token counts, and `out_sum[288,4096]` (gated output-vector sum); REAP saliency = mean over routed tokens of g_j‖f_j‖; the "mass" variant (drop 1/N_j) was a strict Pareto win for pruning; FP8 teacher logits are banked for the eval token set. — [[reap-criterion-and-corpus-audit]]
- Routing on frontier MoEs is skewed within layers (top quarter of experts carries 37–53% of routing; 5–29% of experts "cold") and 50% least-frequent pruning collapses code on Kimi-K2/Qwen3-Coder-480B — rare experts are not dead. — [expert_redundancy_mask_search.md: MoE-Sieve](https://arxiv.org/html/2603.24044)

### Inferences
- Mapping of our bank onto the allocators: counts → φ_i (MC-MoE); gate mass × output norm → w_i / REAP saliency; `out_sum` and per-bucket norms → a domain-stratified importance β (BitsMoE) and the MoPEQ/GEMQ "importance" denominators. Missing: ε_{i,j} (needs a fake-quant pass per expert per width on the weights plus representative expert INPUTS — we bank outputs, not inputs) and Hessian trace (weights only, Hutchinson on W^T W per projection — cheap on CPU for 144 × 42 × 3 matrices). AlphaQ's alpha needs weights only and is the cheapest signal to add. **[inference]**
- Given the evidence that frequency-driven allocation can underperform uniform (AlphaQ Table 1) and that pruning already consumed the frequency signal (KQ7), the allocator for a post-REAP checkpoint should be sensitivity-based (Hessian/alpha/ε) with routing mass only as a tie-breaker or as the decode-cost weight in the objective (MxMoE's T term). **[recommendation]**

### Gaps
- No paper compares REAP-style gated-output saliency against Hessian/alpha as a bit-allocation signal.
- No allocator has been evaluated on a sigmoid + noaux_tc router with bias-selected experts, where "routing frequency" and "routing weight" are decoupled ([[noaux-tc-router-formula]]).

## KQ7. Interaction with pruning: after REAP-50, does mixed precision still buy anything?

### Takeaway
No paper quantises per-expert after a static expert prune; the closest combinations are MC-MoE (static mixed quant + dynamic pruning), EAC-MoE (uniform quant + frequency pruning) and Collaborative Compression (25% static prune + tensor-level quant). The matched-bit gains that are large (+6–13 pt) occur on skewed, many-expert models, and the gains that are small (+0.3–3 pt) occur where routing is balanced — consistent with much of the gain coming from the cold tail that REAP-50 has already removed. The survivors still have a wide routing-mass spread in our bank, and the sensitivity-based allocators claim gains unrelated to frequency, so a residual gain is plausible but unmeasured; its value on Thor is memory to prune less, not accuracy per se.

### Cited Findings
- MC-MoE combines PMQ with Online Dynamic Pruning (ODP) for a further ~15% activated-parameter reduction and 1.6–1.9× speedup, not a static prune. — [MC-MoE v2](https://arxiv.org/html/2410.06270v2)
- EAC-MoE's PESF prunes experts selected less than α× average, prefill only. — [EAC-MoE](https://arxiv.org/html/2508.01625v1)
- Collaborative Compression: prune 25% (0.5·frequency + 0.5·mean routing score), top-k 8→6, then tensor-level llama.cpp mix; no prune-only or quant-only ablation. — [arXiv 2509.25689](https://arxiv.org/html/2509.25689v1)
- Matched-bit gain by model (AlphaQ Table 1, 2.5 bit, AlphaQ − uniform): Mixtral +2.9, DeepSeekV2-Lite +1.6, Qwen1.5-MoE +13.2, Qwen3-30B +0.8; (MxMoE 2.25 bit, MxMoE − GPTQ): Mixtral +0.3, DSV2-Lite +4.0, Qwen1.5-MoE +6.3, Qwen2-MoE +6.0. — [AlphaQ HTML](https://arxiv.org/html/2606.04980v1); [MxMoE](https://arxiv.org/html/2505.05799v1)
- Local: REAP50 = +21.0% ppl; one GGUF width step (Q4_K_S → Q3_K_M) = +1.46%; NVFP4 = +1.56%; "pruning is ~14x more damaging per unit of compression than quantization"; 753B fits Thor at REAP50 only if quant reaches ~2.2 bits. — [[reap-criterion-and-corpus-audit]]; [[glm53-753b-thor-envelope]]
- Local: under the shipped mask, retained saliency mass by domain ranges 0.4865 (general) to 0.7466 (agentic) — survivors are far from uniformly "hot" by domain. — [[reap-criterion-and-corpus-audit]]

### Inferences
- The right framing for Thor is the fit equation: at a fixed ~110 GB envelope, every 0.1 B/w saved on the cold half of the survivors is ~5% more experts kept, and pruning damage is 14× quantisation damage per byte. A two-tier NVFP4 (hot) / ~2.2-bit (cold) survivor set would let the 753B model land nearer REAP-45 than REAP-50, which is where the accuracy actually comes from. **[extrapolation from local measurements]**
- Because the allocator and the pruner would consume the same banked statistics, a joint objective (choose keep-set AND per-expert width under one byte budget) is the natural formulation; the MC-MoE IP and the local min-plus DP are both solvable in seconds. No paper does this. **[inference]**

### Gaps
- No measurement anywhere of per-expert mixed precision applied to a REAP/HOPE-pruned checkpoint; the residual gain on survivors is unknown and must be measured locally (fake-quant on banked eval tokens would suffice for a first pass).
- Per-domain effects of demoting experts are unreported in every paper (all report aggregate averages); our per-bucket bank is the only instrument for that.
