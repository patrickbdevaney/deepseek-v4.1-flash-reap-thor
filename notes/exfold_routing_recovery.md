# ExFold and routing-level, gradient-free recovery for expert-pruned MoEs

Research date: 2026-10-17. Scope: arXiv 2608.24938 (ExFold) and the family of "fold the deleted expert's gate mass onto a retained expert with a least-squares scalar" methods, assessed as the candidate healing step for pushing expert pruning past 50% on a 763B-1T model that must fit a 122 GiB envelope.

**Headline correction to the brief.** ExFold is NOT a healing method for a permanently pruned checkpoint. It is a training-free *serving-acceleration* method: all experts stay resident, the original router is kept, and for each token (prefill) or each batch (decode) a *budgeted subset* of the experts the router actually selected is executed while the rest are folded onto executed ones. The widely quoted "REAP-D64 61.50 -> ExFold-D64 68.75 (original 69.04)" row compares a permanently pruned 64-expert pool (REAP) against a *dynamic per-batch* 64-expert pool chosen fresh every decode step from the batch's routed experts, with all 128 experts still in memory. It is therefore not evidence that a 50%-pruned checkpoint can be healed to 68.75, and the "ExFold-D32 = 68.97 at a 25% pool" row is not evidence that 75% permanent pruning is recoverable. Details and the parts of ExFold that *do* transfer to our setting are below.

## KQ1. Exact ExFold algorithm (target mapping, gate-mass fold, least-squares scalar, granularity)

### Takeaway
ExFold fits one closed-form scalar per *directed (source, target) expert pair, per MoE layer*, by weighted least squares on calibration tokens where the two experts were *co-routed in the same token's top-k*; the target for an omitted expert is the executed expert with the lowest normalised reconstruction loss, and the fold is a pure rewrite of the token's router weights (w_t += w_s * S[s,t]) before the fused MoE kernel. The router and expert weights are untouched.

### Cited Findings
- Problem framing: "ExFold treats both phases as one budgeted output-approximation problem. It runs a constrained set of experts and folds the contributions of excluded experts into retained ones using calibrated scalar projectors, which are fit on unlabeled data." Prefill = token-level Top-K folding; decode = batch-level expert-pool folding. — [arXiv abs 2608.24938](https://arxiv.org/abs/2608.24938)
- Scalar projector objective (Eq. 7): P* = argmin_P sum_i w_i ||u_i - v_i P||^2 + lambda Omega(P), with u_i = E_s(x_i) (omitted/source expert output), v_i = E_t(x_i) (target expert output), w_i = ||u_i||_2. Closed form for P = sI (Eq. 8): s*_{s->t} = sum_i w_i <v_i,u_i> / (sum_i w_i ||v_i||^2 + lambda), lambda = 1e-3; scalars clipped to [-4, 4]. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Granularity: "a separate scalar per ordered (source, target) pair, per MoE layer" (the "pairwise" / "expert scalar" variant, 6.00 MiB of state for Qwen3-30B). — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Pair loss (Eq. 9, normalised reconstruction loss): l(s->t) = sum_i w_i ||u_i - s v_i||^2 / sum_i w_i ||u_i||^2 (+eps). Target rule (Eq. 12): pi(s) = argmin_{t in B} l_{s->t}, where B is the *budget set that is actually executed* (the token's own top-K_pre in prefill; the batch pool in decode) — not the global retained set. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Unobserved pairs: "unobserved pairs get loss 1e30 so that an observed target is preferred whenever one exists." — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Per-token fold (Eq. 4 / Eq. 13): y_hat = sum_{t in S_K and B} a_t E_t(x) + sum_{s in O} a_s * s*_{s->t_s} * E_{t_s}(x); in prefill the omitted routes are merged into target router weights: w~_{i,t} = w_{i,t} + sum_{s: pi(s)=t} w_{i,s} * S_{s->t}. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Budget set definitions: prefill B_pre(x_i) = TopK_{e in S_K(x_i)} (w_{i,e} * h_e, K_pre) (Eq. 10), where h_e is a cached per-expert mean output norm; decode B_dec(X_q) = TopK over the union of routed experts in the batch of (sum_i w_{i,e} h_e, D) (Eq. 11); a *static* decode pool chosen once from calibration norms, B_dec^static = TopK_e(h_e, D), is defined (Eq. 22, Appendix B) but has no reported quality results. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Retained-expert ranking ablation (Table 5, avg): prefill S_i 79.36 / H_i 74.42 / S_i x H_i 80.11; decode-D64 S_i 78.55 / H_i 78.74 / S_i x H_i 79.74 — i.e. router score times norm is the best ranking for which experts to execute. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- What the calibration code actually accumulates (exfold/qwen3/calibration.py, class PairwiseScalarStats): `update(expert_ids [tokens, top_k], expert_outputs [tokens, top_k, hidden])` — **only the routed top-k outputs are passed in; the file never evaluates all E experts**; pairs are formed only between different experts within the same token's top-k; three float64 E x E accumulators indexed [source, target]: dot += w_s <u_s,u_t>, target_sq_norm += w_s ||u_t||^2, source_sq_norm += w_s ||u_s||^2, with w_s = ||u_s||_2; plus per-expert expert_norm_sum/count (the h_e estimate; missing experts get the median). `finalize()`: s = dot/(target_sq_norm + ridge), clamp to [-4,4], residual = source_sq - 2 s dot + s^2 target_sq (clamped at 0), loss = residual/source_sq_norm; unobserved pairs loss = 1e30, coefficient 0; diagonal coefficient 1.0. Returns two [E,E] float32 tensors (coefficient, loss). — [calibration.py](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/exfold/qwen3/calibration.py) (fetched from https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/exfold/qwen3/calibration.py)
- Calibration forward (exfold/qwen3/model_patch.py): `prepare_qwen3_moe()` monkey-patches Qwen3MoeSparseMoeBlock.forward with `calibration_forward`, which runs standard softmax/top-k (+ optional norm_topk_prob renormalisation), runs the experts, then `self.exfold_stats.update(expert_ids, expert_outputs)`. — [model_patch.py](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/exfold/qwen3/model_patch.py)
- Serve-time: "folding changes neither expert parameters nor the original router"; "Both transformations modify only router metadata before the existing fused MoE kernel." — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Similarity diagnostics: on Qwen3, mean cosine across observed directed off-diagonal pairs rises 0.449 -> 0.613 after scalar alignment; on GLM-4.5-Air the symmetric-entry mean rises 0.899 -> 0.932. Common-input diagnostic (Qwen3): median normalised loss over directed off-diagonal pairs 0.407, 79.9% of pairs below 0.5. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)

### Inferences
- The scalar is fit on tokens where *both* experts were in the same token's top-k, so the fit distribution is exactly the "co-activation" distribution; a deleted expert that rarely co-routes with any retained expert gets either an unobserved (loss 1e30, coefficient 0 = pure drop) or a poorly-sampled scalar. This is the mechanism by which recovery quality must degrade as the retained set shrinks (see KQ3).
- Because the target is restricted to experts *already executed for that token/batch*, ExFold adds zero expert compute; a permanent-pruning port must choose between (a) target restricted to retained experts in the token's top-k (no extra compute, but often no observed candidate), or (b) target = argmin over the whole retained set (adds up to k extra expert executions per token when the target is not already active).
- The "median best-pair loss 0.407" means that even the best scalar fold leaves ~40% of a typical source expert's output energy unexplained; the fold roughly halves the dropped-expert error energy relative to dropping (loss 1.0), which is consistent with it being an improvement but not a substitute for the expert.

### Gaps
- The serve-time routing-transform source (kernels.py, vllm_patch.py) was not readable through the GitHub tree view; tie handling and the exact remap kernel are inferred from the paper's equations, not verified in code.
- No per-layer distribution of best-pair loss is given in the text (only a Figure 14 heat map and the pooled median), so the fraction of (deleted, retained) pairs that fall into the "unobserved" bucket at any given pruning ratio cannot be quoted.

## KQ2. Full results: models, ratios, benchmarks, baselines, projector ablation

### Inferences
- The two rows that matter for *permanent* pruning are REAP-D64 (50% pool, 61.50) and REAP-D32 (25% pool, 22.25): the REAP-D32 collapse is the actual datum on 75% permanent pruning of Qwen3-30B under REAP, and ExFold offers no row in which a 25% *static* pool is healed.
- The ExFold-D64/D32 rows are only comparable to REAP-D64/D32 in *decode expert traffic per step*, not in memory. For a 1T model that must lose ~60-70% of its expert bytes, ExFold's decode mode is irrelevant to the fit problem; its prefill mode (P4: execute 4 of the routed 8, fold the rest) is a compute saving only.
- The projector ablation is the one part that transfers cleanly: pairwise scalar > layer scalar > global scalar on tasks (avg of the seven task columns: ~72.2 / ~70.7 / ~69.7, computed from Table 3), so a per-(deleted, retained) scalar is worth more than the per-expert static scale of our v1/v2 method, and diagonal/low-rank buy only perplexity.

### Gaps
- Batch size used for the decode-quality rows is not stated; if the OpenCompass runs used high concurrency, the D32 pool was shared by many tokens and the "folded" fraction per token is unknown. I could not resolve this from the paper or README.
- GLM-4.5-Air parameter count and the GLM calibration corpus composition beyond "16 sequences of at most 1,024 tokens" are not stated.

## KQ3. Extension past 50%: data at 60-75% and what the error model predicts

### Takeaway
No source reports a routing-level fold healing a *permanently* pruned model beyond 50%; the only >50% permanent-pruning data points found (REAP-D32 on Qwen3-30B: 22.25 vs 69.04; Half-the-Experts REAP 25%-keep: Qwen3.6 HumanEval+ 0.787 vs 0.890, Gemma-4 0.000 vs 0.927) show a cliff between 37.5% and 25% keep, and ExFold's own error model (best-pair normalised loss, median 0.407 even with the full 128-expert candidate set, sentinel 1e30 for never-co-routed pairs) predicts that fold quality degrades as the retained candidate set shrinks because the fold is restricted to co-routed, observed pairs.

### Cited Findings
- ExFold's dynamic 25% pool: Qwen3-30B ExFold-D32 68.97 vs original 69.04; DeepSeek-V4-Flash ExFold-D64 (25% pool) 72.54 vs 72.68; Qwen3.5-35B ExFold-D64 (25%) 76.75 vs 75.30 — **all with every expert resident and the pool re-chosen per batch**. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- The only >50% permanent-pruning rows in ExFold: Qwen3-30B REAP-D32 (25% kept) avg 22.25; GLM P4+D32 and other D32 rows are ExFold dynamic. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Paper on budget shrinkage: "recovering omitted expert contributions becomes increasingly important when the active expert pool is aggressively constrained"; no explicit error analysis across D=32 vs D=64 and no explanation of the REAP-D32 collapse. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Half the Experts, Qwen3.6-35B-A3B REAP frontier (coding-heavy calibration, Q8_0, greedy pass@1; Keep / Params / Ppl code / Ppl gen / HE+ / MBPP+): base 36.0B 5.38/5.20/0.890/0.772; 75% 27.0B 5.42/5.80/0.890/0.759; 50% 19.0B 5.49/12.00/0.896/0.728; **37.5% 15.0B 5.89/30.99/0.860/0.733; 25% 10.9B 5.45/30.92/0.787/0.659**. "Recovery thus comes entirely from re-routing and from the shared, always-on pathway." — [arXiv 2607.16721 PDF](https://arxiv.org/pdf/2607.16721)

### Inferences (extrapolations, marked)
- **Extrapolation:** The fold error for a deleted expert s is min_{t in retained} l_{s->t}, where l is the normalised residual after the best scalar. With the full 128-expert candidate set the median pairwise l is 0.407 (Qwen3-30B). As the retained set shrinks from 50% to 25-30%, the minimum over fewer candidates can only rise, and the number of *observed* (co-routed) candidates falls faster than linearly because co-routing requires both experts in a token's top-8. Expect the fraction of deleted experts that fall back to "coefficient 0 / drop" to grow super-linearly past 50%.
- **Extrapolation:** The REAP-D32 collapse (22.25) on a 128-expert, top-8 model is consistent with routing mass retention falling below ~65% in the worst layers (the 2609.04575 numbers) and with the Half-the-Experts cliff at 25% keep; a scalar fold that recovers ~60% of the dropped energy per deleted expert would, at best, move a 25%-keep model partway toward the 37.5%-keep point, not to the original.
- **Extrapolation:** Half the Experts' recovery result is the closest measured analogue to "routing-level healing at 75% removal": with experts frozen and only the router + shared path re-trained, it recovers ~52% of the HumanEval+ gap and most of the perplexity gap. A gradient-free fold should be expected to recover less than this, since it cannot re-route (it only redistributes mass along fixed targets).

### Gaps
- No paper reports any gradient-free fold/redistribution healing at 60-75% removal on any model; the extrapolations above are mine, not measured.
- ExFold gives no per-layer count of observed vs unobserved pairs, so the drop-out rate of the fold at smaller retained sets cannot be quantified from published data.

## KQ4. Composition with HOPE selection, per-domain protection, and iterative prune->fold->prune

### Takeaway
ExFold is mask-agnostic by construction (the pair statistics are computed for every co-routed pair in the full model, and the fold is a post-hoc lookup restricted to whatever set is executed), so it composes with any selection (HOPE, REAP, RAZOR, protect_frac) without refitting; but nothing in the literature tests fold+HOPE or an iterative schedule, and the fold statistics must be collected on the *unpruned* model's routing, so re-folding after a second prune would reuse stale co-routing statistics.

### Cited Findings
- ExFold fits scalars for all co-routed pairs of the full model and then selects the target "with the smallest calibrated reconstruction loss" among the executed set B at serve time (Eq. 12); "Unlike static expert merging, folding changes neither expert parameters nor the original router." — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- ExFold's retained-set ranking (Eq. 10/11, Table 5) is its own S_i x H_i criterion, not REAP saliency; REAP appears only as a baseline. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- HOPE: "REAP, a first-order method, is a special case of HOPE that ignores interaction terms"; at 50% pruning average rank 1.58/5 vs REAP 2.42; no mention of post-prune recovery, re-routing or folding. — [arXiv 2609.18916](https://arxiv.org/abs/2609.18916)
- RAZOR scores "how replaceable each expert is", using the residual that accounts for survivor reweighting and the router-promoted replacement: delta_i = ||w_i r_i - w_r r_r||_2 / (1 - w_i + w_r), aggregated by RMS over tokens routed to i; pure selection, "without gradients, subset search, or recovery training". vs REAP overall avg: GLM-4.7-Flash 25% 44.5 vs 42.4, 50% 40.1 vs 34.5; Qwen3.6-35B-A3B 25% 62.1 vs 59.8, 50% 58.7 vs 55.7. Code github.com/nick7nlp/Razor. — [arXiv 2609.30465v2](https://arxiv.org/html/2609.30465v2)
- MoRA couples selection (learned router bias, 1000 iterations on C4, biases discarded) with recovery (proxy expert chosen by weighted R^2 >= 0.4 on a held-out split, channel-wise affine a (.) f_j(h) + b by weighted ridge regression, 2 d_o parameters per pruned expert); recovery ablation at 50% on Qwen3-30B: 65.83 with vs 65.30 without the affine approximation (dense 73.10); DeepSeek-V2-Lite 54.40 vs 54.02; Moonlight-16B 55.36 vs 54.82. — [arXiv 2610.00367](https://arxiv.org/html/2610.00367)
- Half the Experts: "the selection strategy that achieves this flips between the two models" — REAP beats routing mass by 2.4 points on Qwen3.6 where routing mass later collapses; routing mass beats REAP by 12.8 points (CI [+6.7, +18.9]) on Gemma-4. — [arXiv 2607.16721 PDF](https://arxiv.org/pdf/2607.16721)
- 2609.04575: how the dropped gate mass is renormalised is itself a large lever: Qwen3.6-35B MMLU (baseline 81.65) with k1=4 active, renormalising by the top-4 mass costs -4.65 points, renormalising by the top-16 mass costs -0.35 (p=0.66); removing renormalisation entirely at k1=6 costs 27.45 points; on Gemma-4 a global scalar gain alpha=0.80 cut the MMLU loss to -1.30 (p=0.079). — [arXiv 2609.04575](https://arxiv.org/html/2609.04575v1)

### Inferences
- A HOPE (or RAZOR) mask plus an ExFold-style pairwise fold is a straightforward composition: run one calibration pass on the full model collecting the E x E accumulators per layer, choose the mask by any criterion, then for each deleted s pick t = argmin over retained of l_{s->t}. No paper has measured this.
- RAZOR's score is the natural *selection* complement to a fold: it already models "what the router promotes after deletion", and a fold changes exactly that promotion; a fold-aware selection would replace w_r r_r in RAZOR's residual with s*_{s->t} w_s r_t. Untested.
- Per-domain protection (protect_frac) is orthogonal: it constrains the mask, and the fold runs on whatever mask results. One caveat from Table 4: the fold's scalars inherit the calibration mix (MIXED 73.00 vs MATH 71.10), so a domain-protected mask should be paired with fold statistics from the same balanced corpus.
- Iterative prune->fold->prune: the fold statistics are co-routing statistics of the *original* model; after the first prune the token's top-k changes (promotion), so a second round would need a fresh pass on the pruned+folded model. The pass is cheap relative to a fine-tune (forward only), so iteration is feasible but not validated anywhere.
- MoRA's +0.5 point from its affine recovery at 50% (on zero-shot MC tasks) is a sobering comparison to ExFold's apparent +7: the former is a true permanent-pruning healing number, the latter is a dynamic-pool number.

### Gaps
- No measurement of fold + HOPE, fold + protect_frac, or iterative fold exists in any source found.
- No source quantifies how much of ExFold's gain is the pairwise target choice vs the scalar vs the dynamic pool (the Pith reviewer makes the same complaint).

## KQ5. Serve-time requirement and runtime support (vLLM, llama.cpp, custom CUDA server)

### Takeaway
ExFold needs the full original router plus a per-layer [E,E] scalar matrix and an argmin-target lookup applied to the top-k ids/weights before the fused MoE kernel; the reference implementation is a vLLM 0.10.2/0.11.0/0.26.0 patch (Triton kernel for Qwen3, CUDA for DeepSeek-V4) under Apache-2.0, nothing exists for llama.cpp, and a custom server that already keeps the full router can implement the fold as an O(k) per-token remap on router metadata.

### Cited Findings
- Reference stack: Qwen3 quality/prefill vLLM 0.10.2 V0 TP4 on 4x H800; Qwen3 decode vLLM 0.11.0 V1 TP1; DeepSeek-V4 vLLM 0.26.0 V1 + CUDA Graph TP8; "Routing is transformed before the fused MoE operator, so only the transformed routes and weights are sent to it and omitted expert outputs are never materialized"; Qwen3 uses Triton kernels + vLLM patch, DeepSeek-V4 uses CUDA kernels + vLLM patch; budgets via PREFILL_BUDGET / DECODE_BUDGET env vars; licence Apache-2.0. — [ExFold README](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/README.md); [ExFold repo](https://github.com/Time-Rune/ExFold-MoE)
- State: pairwise scalar table is 6.00 MiB for Qwen3-30B (48 layers x 128 x 128); diagonal variant 316.7 MiB and "must act on the hidden vector online" (unfused); low-rank 2.44-4.87 GiB. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Supported architectures in the repo: only exfold/qwen3 and exfold/deepseek_v4 (no GLM, no MLA-specific code, no mention of KDA). — [ExFold repo](https://github.com/Time-Rune/ExFold-MoE)
- SlimWise (a competing phase-decoupled pruning design) on ExFold: methods that fold excluded experts into retained ones "keep the full expert pool in memory, so they lack the memory savings from pruning under PD disaggregation." SlimWise's own colocated mode keeps "the full router and expert pool resident" and applies "a masked router during decode," costing ~0.5 ms per decode step. — [arXiv 2609.34117](https://arxiv.org/html/2609.34117)
- SERE (ICLR 2026, arXiv 2602.07616): re-routes tokens bound for secondary experts to the most similar primary expert at decode, "custom CUDA kernel that plugs into vLLM with a single-line change", up to 2.0x decode speedup; code JL-Cheng/SERE. In ExFold's Table 1, SERE-K4 scores 64.15 and SERE-K2 50.65 (vs ExFold-D64 68.75, D32 68.97). — [SERE arXiv](https://arxiv.org/html/2602.07616v1); [ICLR poster](https://iclr.cc/virtual/2026/poster/10011142); [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- llama.cpp: a web search for pruned-expert router remapping / gate folding in llama.cpp returned no llama.cpp material at all; the only related items are model cards describing router-row deletion with softmax renormalisation over survivors (e.g. Local-Axiom-AI OLMoE prune, 0xSero Qwen-3.5 REAP card: "router logit weights are renormalized to sum to 1 after pruning"). — [search results](https://huggingface.co/Local-Axiom-AI/llama-1B-5B); [gitcode mirror of Qwen-3.5-28B-A3B-REAP README](https://gitcode.com/hf_mirrors/0xSero/Qwen-3.5-28B-A3B-REAP/blob/main/README.md)
- Half the Experts shows the standard GGUF path: pruning is "an index-select on the leading dimension of two tensors per layer plus a row slice of the router matrix", and "restricting a softmax to survivors and renormalizing over the selected top-k commute"; artifacts served by llama.cpp on a 119 GB unified-memory device. — [arXiv 2607.16721 PDF](https://arxiv.org/pdf/2607.16721)
- MoRA serve-time: retained experts stay loaded, "the original top-k routing is unchanged", affine maps add ~0.012 GiB for Qwen3 at 25% and <=0.0005% FLOPs. — [arXiv 2610.00367](https://arxiv.org/html/2610.00367)

### Inferences
- For a permanently pruned checkpoint the serve-time recipe is: keep the full E-way router rows (e.g. 288 logits), run the model's native top-k (+ bias/renorm) on the full logits, then for each selected deleted expert s: if target T[s] is already in the token's selected retained set, w_T += w_s * S[s]; otherwise either add T[s] as an extra active expert with weight w_s * S[s] (compute cost up to +k expert evaluations per token) or drop. Memory cost is one int16 target vector + one fp16 scalar vector per deleted expert per layer (for a 288-expert, ~60-layer model with 200 deleted per layer: ~60 x 200 x 4 B = 48 KB), negligible.
- vLLM: ExFold's patch is on top of specific vLLM versions and the fused_moe topk metadata path; porting the per-token remap to a pruned checkpoint is a small change in the router -> fused_moe handoff, but nothing is published for pruned checkpoints, and the Thor stack's vLLM would need its own patch.
- llama.cpp: no implementation exists; the GGUF format has no slot for a fold table and the MoE graph takes top-k over the router matrix's rows. Implementing it would need (a) keeping the full router tensor while expert tensors are pruned (today the loader expects n_expert rows to match), (b) an id-remap + weight-fold op between the top-k and the mul_mat_id. This is a patch, not a config change.
- The custom CUDA server (which already retains the full router) is the lowest-friction target: the fold is a per-token O(k) table lookup on the host or in the routing kernel, with no new weights to stream.

### Gaps
- Could not read the serve-time Triton/CUDA kernel source (kernels.py / vllm_patch.py) through the GitHub tree page; the remap behaviour is inferred from the paper's Eq. 13 and the README statement.
- No public llama.cpp or vLLM issue/PR implementing a fold table for *pruned* checkpoints was found.

## KQ6. Related methods and how they compare

### Takeaway
The closest true "healing a permanently pruned model" relatives are MoRA (channel-wise affine proxy; +0.5 avg at 50%), Router-KD (gradient router-only distillation; consistent gains across six compression methods at 37.5% removal), and the Half-the-Experts self-distillation with frozen experts (recovers ~52% of the HumanEval+ gap at 75% removal); SERE/MoDES/SlimWise are, like ExFold, serving-time methods that keep all experts resident; REAP, HOPE, RAZOR, MAESTRO and the 2606.15716 unified scoring are selection methods with no recovery step.

### Cited Findings
- REAP (ICLR 2026, Cerebras): saliency S_j = (1/|X_j|) sum_{x in X_j} g_j(x) ||f_j(x)||_2 conditional on routed tokens; merging error bound ~ E[(g_i+g_j)^2] Var[r(x)] G_ij ("irreducible for any constant alpha"); pruning error bounded by g_j(x)(||f_j|| + ||f_i||) with survivors renormalised g_k/(1-g_j); 25% and 50% only; calibration 1,024 x 2,048 tokens (~2.1M) for <=110B, 12,228 samples up to 16,384 tokens for >=110B; 50% results: Qwen3-Coder-480B non-agentic code 0.619 (0.636), SWE-Bench-Verified 0.522 (0.540), BFCL 0.674 (0.690), MC 0.692 (0.750); Kimi-K2 (1T) code 0.624 (0.631), SWE-Bench-Verified 0.576 (0.554), BFCL 0.564 (0.666), MC 0.643 (0.780). — [arXiv 2510.13999v3](https://arxiv.org/html/2510.13999v3)
- HOPE (2609.18916): second-order objective minimising an upper bound on pruning error; REAP is HOPE with interaction terms dropped; three models up to 122B; largest gains at high pruning rates and agentic workloads; no recovery component. — [arXiv 2609.18916](https://arxiv.org/abs/2609.18916)
- MAESTRO (2607.08601): models expert activation sequences as ergodic Markov chains and ranks by stationary distribution; beats REAP by ~1.26% (25%) and 3.60% (50%) on GPT-OSS-20B, ~1.29% / 3.49% on Qwen3-30B; uniform per-layer pruning retained more than unconstrained global pruning; selection only. — [arXiv 2607.08601](https://arxiv.org/pdf/2607.08601) (abstract/secondary coverage; full PDF not parsed)
- 2606.15716 (unified scoring): exact removal delta Delta_{j,t} = g_{j,t} f_{j,t} + rho_{j,t}, where rho collects gate renormalisation on survivors and the promoted replacement; all practical scores drop rho; family S_j(b,alpha,beta) = (1/N_j^b) sum_t 1[j in E_t] g^alpha ||f||^beta; recommends gate-free, routed-token-averaged scores (MAN/MSAN) for task-agnostic pruning; 0.5M calibration tokens; 25%/50% only; no compensation step. — [arXiv 2606.15716](https://arxiv.org/html/2606.15716)
- Router-KD "Is Retraining-Free Enough? The Necessity of Router Calibration" (2603.02217): trains only router weights (0.04% of Qwen3-30B-A3B) to match the original model's next-token distribution with temperature-scaled KL on C4; ~2 h on Qwen3, ~40 min on Mixtral; improves most benchmarks across REAP, CFES, MoBE, TD-MoE, HC-SMoE, M-SMoE at 62.5% retention; "No recovery when compression causes near-zero collapse." — [arXiv 2603.02217](https://arxiv.org/html/2603.02217v1)
- MoRA (2610.00367): see KQ4; Qwen3-30B 50%: 65.83 vs best baseline 59.40 (MoNE), dense 73.10; no REAP comparison; code "will be released". — [arXiv 2610.00367](https://arxiv.org/html/2610.00367)
- SlimMoE (2506.18349): expert *slimming* (intra-expert) plus multi-stage distillation with 400B tokens; Phi-3.5-MoE 41.9B -> 7.6B / 3.8B; not a routing-level method. — [arXiv 2506.18349](https://arxiv.org/abs/2506.18349)
- SlimWise (2609.34117): full pool for prefill, pruned pool for decode reusing the prefill KV cache; distils only shared expert, routers and norms (0.42% of Qwen3.6 params) on ~100M tokens / 8,000 steps; ratios 25/50/75%; Qwen3.6 REAP-50 SlimWise+Distill vs baseline roughly flat on GSM8K (0.962), -1.4 MATH-500, -0.8 HE+, -2.3 MBPP+; decode throughput 1.65-2.39x at 75% (disaggregated). — [arXiv 2609.34117](https://arxiv.org/html/2609.34117)
- Half the Experts (2607.16721): selection-criterion ranking does not transfer across families; perplexity can rank a broken model above an intact one (random-pruned Qwen ppl 4.82 vs base 5.38 while losing 57.9 pass@1 points); pruning beats quantising the full model only below 3 bits/weight. — [arXiv 2607.16721 PDF](https://arxiv.org/pdf/2607.16721)

### Inferences
- Ranking of gradient-free recovery strength, by measured deltas on permanently pruned models: MoRA affine (+0.3 to +0.5 avg at 25-50%) is the only measured one; ExFold's scalar fold on a static pool is unmeasured. Gradient-light recovery (Router-KD; Half-the-Experts router+shared-path LoRA; SlimWise router/shared/norm distillation) is measured and recovers roughly half the gap at 75% removal — this is the realistic ceiling to benchmark any fold against.
- REAP's merging bound explains why a *per-token* fold (gate mass redirected with the token's own w_s) should beat *static* merging: the fold keeps r(x) per token instead of fixing alpha, so the Var[r(x)] term vanishes; what remains is the per-pair residual G-type term, which ExFold's l_{s->t} measures directly.

### Gaps
- MAESTRO's full PDF body was not parsed (numbers are from abstract/secondary coverage).
- No head-to-head of ExFold vs MoRA vs Router-KD on the same pruned checkpoint exists.

## KQ7. Can the fold be fit from banked calibration statistics? Calibration composition and bias

### Takeaway
No: the fold needs, per layer, the cross inner products <u_s, u_t> of two experts' *outputs on the same token* for co-routed pairs, which neither router score caches (top-40 logits per token) nor REAP saliency accumulators (g * ||f|| per expert) contain; a new forward pass is required, but it is forward-only, needs only the top-k (or top-40) experts per token, is layer-streamable, and ExFold used only ~131k (Qwen3) / ~16k (GLM) tokens, with the mixed corpus outperforming single-domain corpora by 0.3-1.9 points.

### Cited Findings
- Required accumulators (from calibration.py): dot[s,t] = sum w_s <u_s,u_t>, target_sq_norm[s,t] = sum w_s ||u_t||^2, source_sq_norm[s,t] = sum w_s ||u_s||^2, over tokens where s and t are both in the token's top-k; plus per-expert mean output norm. Expert outputs are the unweighted E(x). — [calibration.py](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/exfold/qwen3/calibration.py)
- Calibration data: Qwen3 "32 unlabeled sequences of at most 4096 tokens" (<= 131,072 tokens) from the chat, code and STEM portions of the NVIDIA Nemotron Post-Training Dataset; GLM-4.5-Air "16-sequence capture of at most 1,024 tokens each"; DeepSeek-V4-Flash 64 unlabeled inputs (56 general/code/math + 8 benchmark inputs, "transductive, benchmark-aware"). Forward activations only, no labels or gradients. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938); [ExFold README](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/README.md)
- Calibration-corpus sensitivity (Table 4, ExFold-P4 avg): GPQA 72.10, MATH 71.10, CODE 71.62, PRETRAIN 72.75, MIXED 73.00. — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- REAP's saliency is the mean over routed tokens of g_j(x) ||f_j(x)||_2 — a per-expert scalar, not a pairwise quantity. — [arXiv 2510.13999v3](https://arxiv.org/html/2510.13999v3)
- MoRA fits its affine maps on 64 x 1024 C4 tokens and scores proxy fidelity on a *separate* 64 x 1024 held-out split (q = max(0, R^2) >= 0.4 to accept a proxy). — [arXiv 2610.00367](https://arxiv.org/html/2610.00367)
- Half the Experts calibration: 2,047 chat samples, 70/30 coding-to-general, 3.15M tokens; teacher responses for recovery generated from the same prompts. — [arXiv 2607.16721 PDF](https://arxiv.org/pdf/2607.16721)

### Inferences
- Our banked assets: per-layer saliency accumulators give h_e (expert norms) directly; router caches (top-40 scores per token) give the co-routing structure and the gate weights w_s, but not u_s, u_t. The missing quantity is the [E,E] dot/target_sq_norm/source_sq_norm triple, which requires executing the relevant experts on the calibration hidden states. Cost: a forward pass that executes the token's top-k (ExFold) or top-40 (richer pair coverage, 5x the expert FLOPs) experts per layer — far cheaper than any fine-tune and compatible with layer-by-layer streaming because the pair statistics are local to a layer given its input hidden states.
- Using the cached top-40 instead of top-8 as the co-routing window would expand the observed-pair set substantially (fewer 1e30 sentinels at high pruning ratios), at the cost of fitting scalars on a distribution that includes tokens where s had low gate mass; weighting by w_i = ||u_i|| (ExFold) or by the gate (REAP-style) is a design choice; ExFold's Table 4 shows the fold inherits calibration composition bias (1.9 points between MATH and MIXED), so the per-domain balanced corpus already built for REAP/HOPE should be reused.
- Token budget: ExFold's 131k tokens are ~16x fewer than REAP's 2.1M; the statistics are E x E per layer (288 x 288 x 3 x 8 B = ~2 MB per layer), trivially small.

### Gaps
- No source reports how the fold degrades with calibration size (no calibration-size ablation in ExFold) or whether held-out validation of the scalars (as in MoRA's R^2 gate) matters for the fold.

## KQ8. Code, licence, architectures, feasibility on 122 GiB

### Takeaway
ExFold's code (github.com/Time-Rune/ExFold-MoE, Apache-2.0, ~9 commits) supports only Qwen3-MoE and DeepSeek-V4-Flash via version-pinned vLLM patches on multi-H800 setups; calibration is a monkey-patched HF MoE block forward that accumulates per-layer [E,E] statistics (layer-local, hence streamable in principle), but no layer-streaming, GLM/KDA, or single-device path exists.

### Cited Findings
- Repo: public, 9 commits, 10 stars, 0 forks; Apache-2.0; directories exfold/qwen3 (calibration.py, kernels.py, model_patch.py, vllm_patch.py) and exfold/deepseek_v4; artifacts/ with final calibration matrices and SHA256SUMS; scripts/validate_artifacts.py checks "hashes, shapes, finite values, and per-layer best-pair loss distributions". — [ExFold repo](https://github.com/Time-Rune/ExFold-MoE); [ExFold qwen3 dir](https://github.com/Time-Rune/ExFold-MoE/tree/main/exfold/qwen3)
- Requirements: Linux, Python 3.10+, CUDA 12.8+, "NVIDIA H800 GPUs for reproducing the paper's latency numbers"; Qwen3 quality on 4x H800 TP4; DeepSeek-V4 quality on 8 GPUs TP8. Calibration commands, memory needs and streaming are not documented. — [ExFold README](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/README.md)
- Largest model demonstrated: DeepSeek-V4-Flash, 284B total / 13B active, 256 routed experts, Top-6 (dynamic pool, all experts resident). — [arXiv html 2608.24938](https://arxiv.org/html/2608.24938)
- Largest *permanently pruned* models in the related literature: REAP on Kimi-K2 (1T) and Qwen3-Coder-480B at 50%; RAZOR on DeepSeek-V4-Flash-0731 at 25/50%; HOPE up to 122B. — [arXiv 2510.13999v3](https://arxiv.org/html/2510.13999v3); [arXiv 2609.30465v2](https://arxiv.org/html/2609.30465v2); [arXiv 2609.18916](https://arxiv.org/abs/2609.18916)
- Calibration statistics are per-layer E x E float64 accumulators fed from the MoE block's own top-k outputs (no dense all-expert evaluation). — [calibration.py](https://raw.githubusercontent.com/Time-Rune/ExFold-MoE/main/exfold/qwen3/calibration.py)

### Inferences
- Nothing in the method is architecture-specific: it needs only (router top-k ids, weights, expert outputs) per MoE layer. Porting the *calibration* to a DeepSeek-style MLA MoE or GLM-5 KDA model is a matter of hooking the MoE block; the attention type is irrelevant. The serve-time side must be re-implemented per runtime (our CUDA server is the natural home).
- On 122 GiB for a 763B-1T model, the calibration pass must be layer-streamed exactly as the existing REAP/HOPE saliency pass is; the fold accumulators add ~2 MB per layer and the expert evaluations are the same ones the saliency pass already performs (top-k outputs), so the fold statistics can be folded into the *next* saliency/HOPE pass at essentially zero extra cost — but not recovered from the already-banked outputs of the previous pass.

### Gaps
- The DeepSeek-V4 calibration/serve code was not read; whether its CUDA kernel assumes DeepSeek-V4's specific router (sigmoid + bias, grouped top-k) is unknown.
- No single-GPU / unified-memory run of ExFold calibration is documented anywhere.
