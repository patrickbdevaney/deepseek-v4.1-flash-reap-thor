# Structural removal levers beyond expert pruning, and the Thor memory-budget model

Scope: layer/block pruning, attention-head pruning, dropping MTP heads / vision towers / auxiliary modules, shared-expert removal, KV-cache bytes per token (MLA / DSA / KDA / GQA, with FP8/FP4 KV), measured runtime overhead on Jetson AGX Thor, and a worked memory budget for landing a model at <=117 GiB. Target models: `deepseek-ai/DeepSeek-V4.1-Flash` and `XiaomiMiMo/MiMo-V2.6-Pro-RL`; GLM-5.3-Flash REAP50 (already served on this box) is used as the calibration point.

Conventions: GiB = 2^30 bytes, GB = 10^9 bytes. 117 GiB = 125.63 GB. Every byte figure shows its arithmetic. "[LOCAL]" marks numbers measured on this Thor and recorded in local files; "[DERIVED]" marks arithmetic from config.json/safetensors headers; "[EXTRAPOLATION]" marks anything not measured.

Primary measurements made for this note (2026-10-17): `config.json` and `model.safetensors.index.json` of `XiaomiMiMo/MiMo-V2.6-Pro-RL` were downloaded and all 130 shard headers were range-read and summed by component (script: `/tmp/claude-2002/-home-patrickd/3952824c-51a0-4b40-aa8e-a0ab/scratchpad/scripts/mimo_pro_scan.py`, output: `/tmp/claude-2002/-home-patrickd/3952824c-51a0-4b40-aa8e-acf3b3b02ab9/scratchpad/mimo_pro/scan.out`). The DeepSeek-V4.1-Flash header scan already existed locally (`/home/patrickd/glm-5.3-reap/artifacts/research/v41_flash_header_scan.log`, summarised in `/home/patrickd/glm-5.3-reap/notes/BASE_MODEL_SURVEY_2026-09-10.md`).

## Key question 1: Layer / block pruning for MoE (ShortGPT, LaCo, SLEB, Block Influence, angular distance) — how many of N layers can go at <=5% degradation, and does position matter?

### Takeaway
On the only MoE models where whole-layer removal has been measured head-to-head (Mixtral-8x7B, DeepSeek-MoE-16B), dropping 12-25% of layers costs 2-7 points of average benchmark accuracy one-shot, and Block Drop/Layer Drop at 25% beats Expert Drop at the same byte saving on Mixtral; but for reasoning models, removing even one layer collapses long-chain (test-time-scaling) performance and SFT does not recover it. No published layer-pruning results exist for DeepSeek-V3/V4, Kimi-K2, Qwen3-MoE-235B, GLM-5 or any 500B-1T MoE.

### Cited Findings
- ShortGPT scores each layer by Block Influence (how much the layer changes its input, i.e. input-output similarity), deletes the lowest-scoring layers, and the 2025 Findings-of-ACL version adds a generative variant (ShortGPT-gen); the authors state it can be combined with quantization — [ShortGPT (arXiv 2403.03853)](https://arxiv.org/abs/2403.03853v3); [ACL Findings 2025 version](https://preview.aclanthology.org/credits/2025.findings-acl.1035)
- "Towards Efficient Mixture of Experts: A Holistic Study of Compression Techniques" (He et al., TMLR) defines Layer Drop (remove entire MoE sublayers) and Block Drop (remove whole transformer blocks). Mixtral-8x7B, 4-task average 64.6: L4/32 -> 62.4 (-2.2), L8/32 -> 57.6 (-7.0), B4/32 -> 61.2 (-3.4), B8/32 -> 50.0 (-14.6). Mixtral 8-task average 71.5 at 87.7 GB: L8/32 -> 67.0 at 66.6 GB (1.19x speedup); B5/32 -> 68.6 at 74.1 GB (1.17x). DeepSeek-MoE-16B 61.8 at 30.8 GB: L4/28 -> 55.3 at 26.6 GB; B4/28 -> 56.3 at 26.4 GB. With SFT the DeepSeek-MoE drops recover to 62.3 (L4/28) and 62.7 (B4/28) vs 63.3 for the SFT'd baseline. Combined recipes: Mixtral L8/32 + AWQ = 6.05x speedup, 20.0 GB, avg 66.1; B5/32 + AWQ = 5.94x, 21.9 GB, avg 68.0; Expert Trimming E2/8 + AWQ = 5.28x, 20.1 GB, avg 64.8 (the text and Table 3 disagree on whether 6.05x belongs to Layer Drop or Block Drop) — [arXiv 2406.02500v3](https://arxiv.org/html/2406.02500v3)
- STUN (Structured-Then-UNstructured) reports Mixtral-8x7B at 25% sparsity, 8-task average: unpruned 71.5, Layer Drop 70.0, Expert Drop 66.0, STUN 70.7; Layer Drop is notably worse on ARC-C (47.7) but holds MMLU (67.3) — [STUN (arXiv 2409.06211)](https://arxiv.org/pdf/2409.06211)
- Attention Drop ("What Matters in Transformers? Not All Attention is Needed"): many attention sublayers are near-identity to their inputs; Llama-2-70B gets a 48.4% speedup with a 2.4% performance drop by pruning half of its attention layers; joint attention+MLP dropping does better than either alone at high sparsity; on Llama-2-13B a secondary write-up reports KV cache halved from 52 GB to 26 GB — [arXiv 2406.15786](https://arxiv.org/html/2406.15786v6); [secondary](https://bdtechtalks.substack.com/p/it-turns-out-that-attention-is-not)
- "Attend First, Consolidate Later": skipping attention in top layers is robust on some tasks but "on math exercises, skipping attention led to chance-level performance in all cases" — [arXiv 2409.03621](https://arxiv.org/pdf/2409.03621)
- "When Fewer Layers Break More Chains" (Qwen3-8B, s1.1-7B; ShortGPT, Reverse-order, LaCo): "pruning even one or two layers can severely impair test-time scaling", AIME24 "performance collapses after pruning a single layer and drops to near zero once" ~10% of layers are removed; knowledge-intensive and shallow-reasoning tasks stay stable; "all SFT settings fail to restore the sequential test-time scaling". LoRA-recovered AIME24 on Qwen3-8B: ShortGPT 1 layer 0.433, 2 layers 0.200; Reverse-order 1 layer 0.600, 2 layers 0.567; LaCo 0.267 / 0.167 — [arXiv 2510.22228](https://arxiv.org/html/2510.22228)
- Qwen3-8B "is comparatively more resilient than s1.1-7B: after pruning one layer, it largely preserves sequential scaling. However, pruning two or three layers completely collapses sequential scaling" — [arXiv 2510.22228 (PDF)](https://arxiv.org/pdf/2510.22228)
- Nemotron-Labs-3-Puzzle-75B-A9B (NVIDIA, 2026): Puzzle NAS compresses Nemotron-3-Super (120.7B total / 12.8B active) to 75.3B / 9.3B by shrinking routed-expert intermediate size per layer (1280-2688) and pruning Mamba layers uniformly; attention layers were deliberately left untouched "since Nemotron-3-Super is already very kv-cache efficient"; recovery needs distillation + RL; reported costs Arena-Hard-V2 -4.2 and SWE-Bench -2.6 — [arXiv 2607.04371](https://arxiv.org/pdf/2607.04371); [DEV summary](https://dev.to/pneumetron/nvidia-unveils-nemotron-labs-3-puzzle-75b-a9b-nvfp4-a-deployment-optimized-hybrid-moe-llm-2k0)
- MoE-I2 prunes experts with a layer-aware non-uniform ratio, then low-rank-decomposes the survivors (Qwen1.5-MoE-A2.7B, DeepSeek-V2-Lite, Mixtral-8x7B); DiEP (NeurIPS 2025) learns per-layer pruning rates and keeps ~92% of Mixtral-8x7B performance with half the experts — [MoE-I2](https://aclanthology.org/2024.findings-emnlp.612.pdf); [DiEP](https://proceedings.nips.cc/paper_files/paper/2025/hash/511c7fd69db9f1ce7492a57285975849-Abstract-Conference.html)

### Inferences
- Byte value of one layer on the two targets [DERIVED from header scans]: MiMo-V2.6-Pro = 531.35 GB / 69 MoE layers = 7.70 GB of experts + 25.77 GB / 70 = 0.37 GB of attention = ~8.07 GB per block; DeepSeek-V4.1-Flash = 288.8 GB / 40 = 7.22 GB experts + 5.6/40 = 0.14 GB attention = ~7.36 GB per block. Dropping 8 of 40 V4.1 blocks (the Mixtral L8/32 ratio, -4.5 pts avg on the 8-task set) saves ~59 GB; dropping 14 of 69 MiMo-Pro blocks (20%) saves ~113 GB.
- The <=5% line, read from the only MoE data: ~12% of blocks (B4/32 Mixtral, -3.4) or ~25% of attention-only sublayers; Layer Drop at 25% on Mixtral (-1.5 on STUN's 8 tasks, -4.5 on He et al.'s) is at the edge. Those are 47B-class models; nothing supports extrapolating the ratio to a 1T model, and the test-time-scaling result says a reasoning/agentic model is the worst case. [EXTRAPOLATION]
- Position: both He et al. (importance scored per layer, dropped layers cluster in the middle/late stack) and ShortGPT's Block-Influence ranking remove middle-to-late layers; the first and last blocks are never low-BI. Reverse-order (deepest layers) was the least damaging of the three methods for test-time scaling in 2510.22228, which argues for scoring on a generative/long-CoT calibration set rather than BI alone. [INFERENCE from the cited tables]
- On a bandwidth-bound decoder (Thor), dropping a block also removes its per-token read (experts top-k + attention) and its KV, so layer dropping is the one structural lever that improves decode speed as well as fit; expert pruning only improves fit.

### Gaps
- No measured layer/block pruning on DeepSeek-V3/V4, Kimi-K2, Qwen3-MoE-235B, GLM-5.x or any >100B MoE was found in 2025-2026 arXiv searches ("layer pruning MoE DeepSeek-V3 ShortGPT", "depth pruning MoE layer drop block drop Mixtral"). The largest MoE with numbers is Mixtral-8x22B (expert pruning only).
- LaCo and SLEB per-model numbers were not retrieved (only named in 2510.22228 as baselines); angular-distance ("Unreasonable Ineffectiveness of the Deeper Layers") numbers are dense-only and were not fetched.
- The ShortGPT paper's own accuracy tables were not retrieved in this pass (search snippets gave method only).

## Key question 2: Attention-head / KV-head pruning on MLA, DSA and GQA models

### Takeaway
KV-head pruning has only been demonstrated on MHA->GQA conversion of 7B dense models (up to 87.5% of KV heads removed with fine-tuning); nothing exists for MLA, and on MLA there is one latent "KV head" so the lever does not even apply to the cache. On the two targets the attention weights are 1-5% of bytes, so head pruning buys almost nothing in weights; its only payoff is KV bytes on GQA models at >=128k context.

### Cited Findings
- "Align Attention Heads Before Merging Them" (Findings of EMNLP 2025): Procrustes alignment + L0 pruning "can compress up to 87.5% of KV heads in LLaMA2-7B and 75% in Sheared-LLaMA-1.3B with acceptable degradation" (requires fine-tuning) — [arXiv 2412.20677](https://arxiv.org/abs/2412.20677v2); [ACL page](https://preview.aclanthology.org/dashboard/2025.findings-emnlp.467)
- Structured dropout (Fan et al. 2019): dropping whole attention sublayers works better than dropping individual heads — [arXiv 1909.11556](https://arxiv.org/pdf/1909.11556)
- TransMLA: MLA is strictly more expressive than GQA at equal KV-cache size; converts GQA models to MLA — [arXiv 2502.07864](https://arxiv.org/html/2502.07864v2)
- Head-aware KV methods (HeadKV, KVzap) allocate per-head eviction budgets or prune along the token axis instead of removing heads; KVzap (NVIDIA, Jan 2026) notes GQA/MLA compress the head/latent axes but nothing adopted compresses the T-axis — [KVzap (arXiv 2601.07891)](https://arxiv.org/html/2601.07891)
- DeepSeek-V4.1-Flash attention: 64 heads, head_dim 512, `num_key_value_heads: 1`, q_lora_rank 1280, o_lora_rank 1024 (o_groups 8), qk_rope_head_dim 64, sliding_window 128, indexer `index_n_heads 32, index_head_dim 128, index_topk 512` — [HF config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)
- MiMo-V2.6-Pro attention: 128 query heads, 8 KV heads, head_dim 192, v_head_dim 128, same for SWA layers; `qkv_proj` is F8_E4M3 [27136, 6144] (= 128x192 + 8x192 + 8x128) and `o_proj` is BF16 [6144, 16384] (201.3 MB/layer) on all 70 layers because `o_proj` is in `ignored_layers` — [LOCAL header scan](file:///tmp/claude-2002/-home-patrickd/3952824c-51a0-4b40-aa8e-acf3b3b02ab9/scratchpad/mimo_pro/scan.out); [HF config](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Pro-RL/raw/main/config.json)
- On GLM-5.3-Flash, NVFP4-quantising `o_proj` + MLA projections cost -0.0055 top-1 vs -0.0023 for KDA q/k/v; "the MLA projections are low-rank factorisations where error in a compressed latent is amplified on expansion" — [LOCAL DECODE_MEMORY_MODEL.md](file:///home/patrickd/glm-5.3-reap/research/DECODE_MEMORY_MODEL.md)

### Inferences
- MiMo-V2.6-Pro [DERIVED]: K/V projection weights per layer = 8x(192+128)x6144 = 15.7M params x 1 B (FP8) = 15.7 MB; x70 = 1.1 GB. Halving KV heads (8 -> 4) saves ~0.55 GB of weights but halves GA-layer KV: 51,200 -> 25,600 B/token BF16 (see Q5), i.e. 3.1 GiB at 128k. Pruning query heads attacks the BF16 `o_proj` (14.09 GB total) and the Q part of `qkv_proj` (24576/27136 of 11.67 GB = 10.6 GB); 25% query-head pruning would save ~6.2 GB, which is less than the 10.1 GB that simply NVFP4-overlaying `o_proj` saves (14.09 -> ~3.96 GB at 0.5625 B/w) with the locally measured small cost.
- DeepSeek-V4.1-Flash: "attention + other" is 5.6 GB of 510.3 GB (1.1%); the KV latent is a single 512-channel vector per token, so there are no KV heads to prune and query-head pruning saves at most a few GB. Head pruning is not a lever on this model.
- Because the MLA latent is already the compressed object, any "head pruning" on MLA/DSA models reduces to (a) dropping whole attention sublayers (Q1, Attention Drop) or (b) KV quantisation (Q5).

### Gaps
- No paper prunes heads on top of MLA (searched "attention head pruning MLA"); no KV-head pruning results on any model >13B or on any MoE.
- The MiMo-V2.6-Pro `o_proj` BF16 choice (ignored_layers) was not explained by Xiaomi; whether it is a sensitivity finding or a kernel limitation is unknown.

## Key question 3: MTP heads, vision towers, auxiliary modules — droppable for text-only serving, and how many bytes in V4.1-Flash and MiMo-V2.6-Pro?

### Takeaway
MTP/DSpark heads, vision and audio towers are architecturally droppable for text-only serving (DeepSeek discards MTP at inference unless used for speculation) and they are small: 8.7 GB on V4.1-Flash, 4.5 GB on MiMo-V2.6-Pro. The one auxiliary module that is not small is V4.1-Flash's Engram (203.1 GB, 39.8% of the checkpoint), whose only documented mitigation is host-RAM offload, which on Thor is the same pool.

### Cited Findings
- DeepSeek-V3 model card: "The total size of DeepSeek-V3 models on HuggingFace is 685B, which includes 671B of the Main Model weights and 14B of the Multi-Token Prediction (MTP) Module weights" — [HF DeepSeek-V3-Base](https://huggingface.co/deepseek-ai/DeepSeek-V3-Base); MTP modules are discarded at inference but can be used for speculative decoding — [gonzoml write-up](https://gonzoml.substack.com/p/deepseek-v3-technical-details)
- DeepSeek-V4.1-Flash byte breakdown (48 shard headers summed, 96,085 tensors): routed experts 288.8 GB (56.6%); Engram 203.1 GB (39.8%, 12 tensors); MTP/DSpark heads 7.9 GB (1.6%, 2,401 tensors); attention+other 5.6 GB; embed+lm_head 2.6 GB; shared expert 1.4 GB; vision tower 0.8 GB; total 510.3 GB. Config: 40 layers, hidden 5120, 384 experts top-6, moe_intermediate 2304, `expert_dtype: "fp4"`, `num_nextn_predict_layers 3`, `dspark_block_size 5`, `dspark_target_layer_ids [37,38,39]`, `dspark_n_routed_experts 128`, Engram at layers [1,14], `engram_num_embeddings [384006168, 384016682]`, head_dim 256, 8 heads — [LOCAL BASE_MODEL_SURVEY_2026-09-10.md](file:///home/patrickd/glm-5.3-reap/notes/BASE_MODEL_SURVEY_2026-09-10.md); [HF config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)
- V4.1-Flash paper: 552B backbone + 196B Engram parameters split evenly across the two modules; at inference Engram embeddings are prefetched "from host memory via background RDMA transfers" while during RL rollouts the tables "remain resident in GPU memory"; DSpark drafter = three transformer blocks with a 128-token sliding window, one pass yields five draft positions plus a Markov head and a confidence head; "MTP is omitted during backbone pre-training" — [arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- SGLang's documented Engram mitigation is `SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1` (host-RAM table); on Thor "host" is the same LPDDR pool — [LOCAL thor-base-model-shortlist](file:///home/patrickd/.claude/projects/-home-patrickd/memory/thor-base-model-shortlist.md)
- MiMo-V2.6-Pro-RL byte breakdown (130 shard headers, 160,040 tensors, index `total_size` 566,027,990,784 B = 566.03 GB = 527.15 GiB, `save_format: mxfp4`): routed experts 531.35 GB (93.9%, U8); attention 25.77 GB (4.6%); embed+lm_head 3.75 GB; **MTP 2.46 GB** (48 tensors, `model.mtp.layers.{0,1,2}`); **vision 1.48 GB** (364 tensors, `visual.*`); **audio 0.59 GB** (95 tensors, `audio_encoder.*` + `speech_embeddings.*`); routers 0.33 GB; dense MLP (layer 0) 0.30 GB. By dtype: U8 531.35 GB, BF16 21.29 GB, F8_E4M3 13.38 GB — [LOCAL scan.out](file:///tmp/claude-2002/-home-patrickd/3952824c-51a0-4b40-aa8e-acf3b3b02ab9/scratchpad/mimo_pro/scan.out)
- MiMo-V2.6-Pro config: 70 layers, hidden 6144, 384 routed experts top-8, `n_shared_experts: None`, moe_intermediate 2048, dense `intermediate_size 16384`, `moe_layer_freq` = [0,1,1,...] (layer 0 dense), `hybrid_layer_pattern` zeros (global attention) at [0,7,15,23,31,39,47,55,62,69] = 10 GA + 60 SWA (window 128), vocab 152,576, max_position 1,048,576, vision_config depth 28 / hidden 1280 / 32 heads / out 6144, audio 6 local layers; `num_nextn_predict_layers` is absent from config.json (the checkpoint nevertheless ships 3 MTP layers) — [HF config.json](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Pro-RL/raw/main/config.json)
- A third-party spec page claims "5 multi-token prediction heads" for MiMo-V2.6-Pro; the checkpoint has 3 (`model.mtp.layers.0..2`) — [apxml](https://apxml.com/models/mimo-v2-6-pro-rl) contradicted by [LOCAL scan.out](file:///tmp/claude-2002/-home-patrickd/3952824c-51a0-4b40-aa8e-acf3b3b02ab9/scratchpad/mimo_pro/scan.out)
- MiMo-V2.6-Flash (sibling, measured 2026-09-23): `num_nextn_predict_layers: 3` plus a separate 5-layer SWA DFlash drafter in `dflash/`; audio tower 0.47 GB; vision tower ~1.4 GB (681M) — [LOCAL MIMO_V26_FLASH_SURVEY](file:///home/patrickd/glm-5.3-reap/notes/MIMO_V26_FLASH_SURVEY_2026-09-23.md)
- For text decode the vision tower (1.05 GiB) and embedding table (1.18 GiB) are not on the hot path on GLM-5.3-Flash; keeping them there "is moving 2.2 GiB/token for nothing" — [LOCAL DECODE_MEMORY_MODEL.md](file:///home/patrickd/glm-5.3-reap/research/DECODE_MEMORY_MODEL.md)
- On Thor, GLM-5.3-Flash's native MTP head gives 58.5% acceptance at depth 3 but speculative decoding was a net slowdown; DFlash on Qwen3.6-35B-A3B gave mean acceptance length 4.5-7.9 and 36-69 tok/s accepted throughput — [LOCAL glm53-mtp-serving-path](file:///home/patrickd/.claude/projects/-home-patrickd/memory/glm53-mtp-serving-path.md); [LOCAL serve-fanative.log](file:///home/patrickd/dflash-setup/serve-fanative.log)

### Inferences
- MiMo-V2.6-Pro MTP blocks are dense, not MoE [DERIVED]: 48 tensors / 3 layers = 16 per layer; 2.46 GB / 3 = 0.82 GB each = qkv FP8 (0.167 GB) + o_proj BF16 (0.201 GB) + eh_proj BF16 12288x6144x2 B (0.151 GB) + dense MLP 3x6144x16384 at 1 B (0.302 GB) = 0.82 GB. So keeping MTP for speculation costs only 2.46 GB and no expert reads.
- V4.1-Flash: the DSpark head includes its own 128-expert MoE (`dspark_n_routed_experts 128`), which is why it is 7.9 GB; the REAP pipeline prunes only backbone experts, so the head would be carried unpruned.
- Text-only savings [DERIVED]: V4.1-Flash 0.8 (vision) + 7.9 (MTP/DSpark) = 8.7 GB (1.7%); MiMo-V2.6-Pro 1.48 + 0.59 + 2.46 = 4.53 GB (0.8%). These are rounding errors against the expert mass (288.8 GB and 531.35 GB) and should be taken only after the decision on speculation is made, because on Thor's bandwidth-bound decode a working drafter is worth 2-3x throughput (local DFlash numbers) while 2.5-8 GB of weights is ~1 context-length step.
- Engram is the real auxiliary-module question: 203.1 GB = 189.2 GiB, larger than the entire Thor envelope. Nothing published measures the model with Engram removed; the paper's RL-time note ("remain resident in GPU memory") implies the designers never ran without it. Treat "drop Engram" as an unvalidated lever with unknown cost, not a free 203 GB. [INFERENCE]

### Gaps
- No ablation of V4.1-Flash without Engram, without DSpark, or text-only was found (paper HTML sections 2-3 were not fully read; the fetched portions had no component ablations).
- MiMo-V2.6-Pro's own vision/audio bytes are measured here but no Xiaomi statement on text-only serving was found.

## Key question 4: Shared experts — prunable/mergeable, or load-bearing?

### Takeaway
Shared experts are load-bearing and tiny: DeepSeekMoE's own ablation raises Pile loss from 1.808 to 2.414 (+33.5%) when the shared expert is disabled, and they hold 0.3% of V4.1-Flash's bytes (1.4 GB); MiMo-V2.6-Pro has none. Never prune them; the only published "removal" (CD-MoE) replaces an entire MoE layer with a dense condensation and loses ~10%.

### Cited Findings
- DeepSeekMoE: disabling the shared expert (and activating one more routed expert to hold compute constant) raises Pile loss "from 1.808 to 2.414", which "highlights the crucial function of the shared expert"; the model is also "more sensitive to the disabling of top routed experts" than GShard, read as lower parameter redundancy — [arXiv 2401.06066](https://arxiv.org/html/2401.06066)
- GateBreaker (safety ablation): pruning shared experts alone raised attack success rate to 42.2% vs 13.1% for sparse experts on Qwen1.5-MoE-A2.7B-Chat; across four models the averages were 38.8% (sparse) vs 36.6% (shared); on OpenPangu-Pro-MoE-72B shared-only pruning gave 50.2%; the authors argue shared experts matter most per-expert because they are always active (internal table/text inconsistency noted in the source) — [arXiv 2512.21008](https://arxiv.org/pdf/2512.21008)
- CD-MoE condenses MoE layers with shared experts into a small dense layer; on DeepSeekMoE-16B it keeps ~90% of average accuracy while cutting memory by 30% — [arXiv 2412.00069](https://export.arxiv.org/pdf/2412.00069)
- V4.1-Flash shared expert = 1.4 GB (0.3%, 240 tensors, stored FP8 not FP4); GLM-5.3 (753B) shared expert = 2.8B params of 743.1B; DeepSeek-V4-Flash: `n_shared_experts 1`, shared experts are "FP8 not FP4" in the raw checkpoint, "always-on shared expert (no dense-parallel branch)" — [LOCAL BASE_MODEL_SURVEY](file:///home/patrickd/glm-5.3-reap/notes/BASE_MODEL_SURVEY_2026-09-10.md); [LOCAL glm53-753b-thor-envelope](file:///home/patrickd/.claude/projects/-home-patrickd/memory/glm53-753b-thor-envelope.md); [LOCAL dspark-v4flash-180b-thor](file:///home/patrickd/.claude/projects/-home-patrickd/memory/dspark-v4flash-180b-thor.md)
- MiMo-V2.6-Pro and -Flash: `n_shared_experts: None` / "NO shared expert" — [HF config](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Pro-RL/raw/main/config.json); [LOCAL mimo-v26-flash-thor](file:///home/patrickd/.claude/projects/-home-patrickd/memory/mimo-v26-flash-thor.md)

### Inferences
- Byte value of the shared expert on V4.1-Flash: 1.4 GB / 40 layers = 35 MB per layer, i.e. the same size as ~2 routed experts per layer (18.8 MB each). Pruning it saves the equivalent of 0.5% of the routed pool at a loss DeepSeekMoE measured at +33% in loss; it is the worst byte-per-damage trade in the model.
- Because the shared expert is always read per token, it is also 35 MB of the per-token read; quantising it from FP8 to FP4 (as the routed experts already are) would save 0.7 GB resident and ~17 MB/token with the usual quantisation risk, and is the only sensible "shared-expert lever".

### Gaps
- No ablation of shared-expert removal on any >16B model (DeepSeek-V3/V4, GLM-5, Qwen3-MoE) was found.

## Key question 5: KV-cache bytes per token — MLA, DSA, KDA/linear, GQA; concrete numbers for the targets; FP8/FP4 KV savings

### Takeaway
Per token: V4.1-Flash 890 B (global, FP4 latent + CSA2 reuse; 0.11 GiB at 128k), MiMo-V2.6-Pro 51,200 B BF16 / 25,600 B FP8 (10 GA layers x 8 KV heads x 320; 6.25 / 3.13 GiB at 128k, 50 / 25 GiB at 1M), GLM-5.3 (753B, MLA 512+64 x 78 layers) 89,856 B BF16 / 51,168 B FP8 plus ~10.3 KB indexer cache (11.0 / 6.2 GiB at 128k), KDA state is context-independent (GLM-5.3-Flash: 145.56 MiB total). ## Key question 7: Does structural pruning compose additively with expert pruning, or do they interact?

### Takeaway
No paper measures layer-drop-then-expert-prune (or the reverse) on the same large MoE with the saliency recomputed between passes; the closest evidence (Unified-MoE-Compression recipes, STUN's structured-then-unstructured ordering, and this project's own measurement that quantisation damage is sub-additive and that per-lever "cost per GiB" depends on what else is already removed) says the levers interact, so ordering and recalibration matter and the budget must be planned on bytes but validated end-to-end.

### Cited Findings
- Unified MoE compression (He et al.) combines Expert Trimming (Layer Drop / Block Drop / Expert Drop) with Expert Slimming (AWQ) and reports the combined numbers in Q1 (e.g. Mixtral L8/32 + AWQ 66.1 vs L8/32 alone 67.0 vs AWQ-only not isolated here) — [arXiv 2406.02500v3](https://arxiv.org/html/2406.02500v3)
- STUN orders structured (expert) pruning before unstructured pruning and beats both Layer Drop and Expert Drop at 25% on Mixtral (70.7 vs 70.0 vs 66.0; base 71.5) — [STUN](https://arxiv.org/pdf/2409.06211)
- MoE-I2 first prunes experts with a layer-aware ratio, then low-rank-decomposes the survivors (re-calibrating between stages) — [MoE-I2](https://aclanthology.org/2024.findings-emnlp.612.pdf); C-GNN-PRUNE allocates per-layer pruning budgets from expert-activation entropy before pruning — [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/39462/43423)
- REAP's saliency is router-gate x expert-output-norm observed on a calibration pass through the full model; GRAPE (2026) argues a global (cross-layer) perspective beats per-layer pruning on DeepSeek-MoE-16B and Mixtral-8x22B — [REAP (arXiv 2510.13999)](https://arxiv.org/html/2510.13999v1); [GRAPE (arXiv 2604.06542)](https://arxiv.org/pdf/2604.06542)
- Local measurement on GLM-5.3-Flash REAP50: quantising KDA q/k/v cost -0.00230 top-1 and o_proj+MLA cost -0.00551, but both together cost -0.00673, "14% less than the sum. So 'cost per GiB' is not a property of a tensor set; it depends on what else is already quantised. Any lever priced by subtracting two arms will misprice it" — [LOCAL DECODE_MEMORY_MODEL.md](file:///home/patrickd/glm-5.3-reap/research/DECODE_MEMORY_MODEL.md)
- Local measurement: pruning is 14x more damaging per byte than quantisation on GLM-5.3-Flash; the REAP gap was corpus imbalance, and uniform per-layer allocation cost 5% — [LOCAL reap-criterion-and-corpus-audit](file:///home/patrickd/.claude/projects/-home-patrickd/memory/reap-criterion-and-corpus-audit.md)
- HOPE supersedes REAP: "REAP is HOPE with interactions zeroed; +2.8-6.1% agentic at 40-50%, same forward pass, but the off-diagonal is unrecoverable after the pass" — [LOCAL hope-supersedes-reap](file:///home/patrickd/.claude/projects/-home-patrickd/memory/hope-supersedes-reap.md)

### Inferences
- Bytes compose exactly (a dropped block removes its experts, attention and KV; a pruned expert removes 18.8-20.1 MB); quality does not. Dropping layer l changes the hidden states entering layers > l, so REAP/HOPE saliency and router statistics computed on the unpruned model are stale for every later layer; the calibration pass must be re-run on the layer-dropped model before expert pruning (the order MoE-I2 and STUN use: coarse structural step first, recalibrate, then fine step). [INFERENCE]
- Conversely, expert pruning changes each layer's Block-Influence (a layer whose experts were cut harder contributes less, so BI falls and it becomes a more attractive drop candidate): expert-prune-then-layer-drop will preferentially drop the layers you already damaged, compounding error in the same place. Layer-drop-first avoids that. [INFERENCE]
- Expect the combined damage to be at least the sum when both levers hit the same late-middle layers (the test-time-scaling collapse is a depth effect that expert pruning does not cause and layer pruning does); the sub-additivity measured for quantisation arms is not evidence that pruning composes gently.
- Practical rule for the budget: plan with additive bytes, reserve 2-3 points of quality beyond the sum of the single-lever costs, and gate the combination on the project's held-out top-1 / agentic evals rather than on either paper's number.

### Gaps
- No published experiment with layer dropping and expert pruning applied jointly to a model larger than Mixtral-8x7B, and none with saliency recomputation between stages reported.
- No data on whether REAP/HOPE saliency transfers across a layer-dropped model (would need a local run).

### Inferences — the framework (all arithmetic [DERIVED]; fit verdicts are inferences)

**Step 1 - decompose the checkpoint from headers (never the card):** routed experts E, attention A, embed/head H, shared S, router R, MTP M, vision/audio V, other X (Engram etc.).

**Step 2 - text-only weights:** W = E x keep_fraction x (L_kept / L) + (A + R) x (L_kept / L) + H + S [+ M if speculating] [+ X if not droppable]. Apply any further quantisation as a bytes/weight ratio on the tensors it touches (0.5625 for NVFP4 experts/dense; 1.0 FP8; 2.0 BF16).

**Step 3 - KV:** bytes/token from Q5 x context x concurrent sequences, plus fixed SWA windows / linear states.

**Step 4 - runtime reserve:** 12 GiB (Q6) for a single-stream pure-CUDA or vLLM server at <=32k; add ~2 GiB at 128k for attention workspace/activations [EXTRAPOLATION].

**Step 5 - verdict:** W + KV + reserve <= 117 GiB.

### Gaps
- The 12 GiB runtime reserve is an engineering estimate from local incidents, not a measured steady-state breakdown; a controlled measurement (idle -> CUDA context -> weights -> KV -> prefill at 32k/128k, each read from `/proc/meminfo` after `drop_caches`) has not been done because a server is up and co-running probes is forbidden on this box.
- Multi-sequence serving (batch > 1) multiplies the KV column; the table is single-stream.
- No measured decode-speed column: block dropping is the only lever here that also cuts per-token bytes (7.7-8.1 GB resident per block, of which top-k experts + attention are read per token); quantifying that needs the `B_tok` model from `DECODE_MEMORY_MODEL.md`, which was out of scope.
