# Layer-streamed / block-wise healing infrastructure for a non-resident 400-500B pruned MoE student on one Jetson AGX Thor

Scope: what exists (frameworks, kernels, papers) for fine-tuning a student whose frozen FP4 experts (~100 GiB after pruning) cannot sit in the 122 GiB unified memory together with activations, optimizer state and targets; memory and throughput arithmetic for a layer-streamed LoRA/router/distillation step on Thor; the router-from-cached-expert-outputs idea; and a feasibility verdict for healing a DeepSeek-V4.1-Flash REAP-55 student (the "fits" row of `structural_and_memory_budget.md`: Engram dropped, 8/40 blocks dropped, 173/384 experts kept, 103.1 GB experts + 8.5 GB other = 111.6 GB).

## KQ1. Which existing tool gets closest to "LoRA on a 500B MoE from NVMe on one 128 GB device", and what did it measure?

### Takeaway
Nothing published does LoRA on a >100B MoE streamed from NVMe on one device. The closest *measured* artefacts are (a) **Soup** (open-source, LoRA on an NF4 base streamed one decoder layer at a time from RAM or NVMe: 8B at 119.6 tok/s on a 4 GB GPU, a 36 GB "70B-shaped" store from disk at 16-17 s per step, backward verified only at 8B/14B, no MoE), (b) **SlideFormer** (DAC'26, *full-parameter* FT of Mistral-Large-123B on one RTX 4090 + 256 GB RAM + NVMe, ~45-180 tok/s class), and (c) block-wise trainers that never hold the whole model — **EfficientQAT Block-AP** (Llama-2-70B at 29.9 GB peak, 26.6 h on one A100 for 8M tokens x 2 epochs). The block-coordinate family (BAdam, LISA) reduces *optimizer* memory for full-parameter training and does not address frozen-weight residency.

### Cited Findings
- Soup keeps the frozen 4-bit base in host RAM and "feeds it to the GPU one decoder layer at a time"; for stores larger than RAM it "reads its disk tier on a background thread, through direct I/O" and can stripe across NVMe drives (`SOUP_LAYER_STREAM_STRIPE_DIRS`); `stream_source: auto` picks RAM when the store fits — [Soup README](https://github.com/MakazhanAlpamys/Soup)
- Soup measured: Llama-3.1-8B-Instruct NF4 LoRA, batch 1, seq 512, RTX 3050 Laptop 4 GB: **119.6 tok/s, 3.32 GB peak**; same setup on an H100 median 113.0 tok/s (i.e. the laptop run is bandwidth/stream-bound, not compute-bound); a 36 GB 70B-shaped NF4 store on an 8 GB RTX 5070 Laptop: cold step **16.2-17.3 s with direct I/O (110.5 s before), 9.97 s with two-drive striping**; "about 1.43 times slower than a resident run" — [Soup README](https://github.com/MakazhanAlpamys/Soup); [toknow.ai write-up](https://toknow.ai/posts/soup-layer-streaming-fine-tune-8b-4gb-laptop-gpu/)
- Soup limits: forward bit-exactness checked 0.5B-72B, **backward checked only at 8B and 14B**; v0.73.0 fixed a bug where NF4 layers above ~165 MiB gave "silently wrong gradients" while the loss curve looked normal (repair cost 4.8% throughput at 32B); no MoE, no aarch64 mention — [Soup README](https://github.com/MakazhanAlpamys/Soup)
- SlideFormer (DAC'26): single-GPU full-parameter fine-tuning with layer-granular GPU cache units, Layer-Adam on host-resident optimizer states, sliding activation checkpoints to CPU/NVMe, GPUDirect Storage; "fine-tuning >123B models on a single RTX 4090"; with 256 GB CPU memory "enabling NVMe offloading allows fine-tuning models up to 90B parameters and can fine-tune models within 24B without throughput loss"; "performance scales near-linearly with the number of NVMe drives, as I/O bandwidth becomes the primary bottleneck"; full offloading cuts CPU memory 60-80% "with a corresponding throughput degradation contained within 30-50%"; Figure 11 axes put Mistral-Large-123B at 0-180 tok/s and Qwen2.5-72B at 0-300 tok/s on the 4090 (exact bars not machine-readable) — [arXiv 2603.16428 (PDF, text extracted locally)](https://arxiv.org/pdf/2603.16428)
- SlideFormer explicitly rejects putting *parameters* on NVMe: "parameters to NVMe would shift the transfer bottleneck from PCIe to NVMe speed, severely hindering overall throughput" — it keeps params in CPU RAM and offloads only activations/optimizer states to NVMe — [arXiv 2603.16428](https://arxiv.org/pdf/2603.16428)
- EfficientQAT Block-AP: trains one transformer block at a time "under a block-wise reconstruction framework" on 4096 RedPajama samples x 2048 tokens (8.4M tokens), batch 2, 2 epochs per block; **Llama-2-70B Block-AP peak memory 29.9 GB; time on one A100-80GB: 7B 3.3 h, 13B 5.6 h, 70B 26.6 h** (E2E-QP phase ~1.5/2.9/14.3 h) — [arXiv 2407.11062](https://arxiv.org/html/2407.11062v3)
- BAdam (NeurIPS 2024): block coordinate descent with Adam; memory ~2M + 16M/D GB for an M-billion model split into D blocks; Llama-3-8B on one RTX 3090, Llama-3-70B on 4xA100-80GB; full-parameter — [arXiv 2404.02827](https://arxiv.org/abs/2404.02827)
- LISA (NeurIPS 2024): randomly freezes most middle layers each step, trains >=65B "with less or similar memory consumption as LoRA"; full-parameter on the active layers — [arXiv 2403.17919](https://arxiv.org/abs/2403.17919)
- ZeRO-Infinity: "fine-tune trillion parameter models on a single NVIDIA DGX-2 node" (16 V100s), not one GPU; its bandwidth model needs "over 70 GB/s" for parameters+gradients to exceed 50% efficiency at the smallest batch, ~4x that for optimizer states, but only "1-4 GB/s" for activation checkpoints; measured 3.0 GB/s CPU and 1.6 GB/s NVMe per GPU; prefetcher issues NVMe->CPU for operator i+3, CPU->GPU for i+2 while computing i — [ar5iv 2104.07857](https://ar5iv.labs.arxiv.org/html/2104.07857)
- NVIDIA DGX Spark (GB10, 128 GB unified, 273 GB/s — the closest Thor analogue) fine-tuning table: Llama 3.3 70B **QLoRA 759.79 peak tok/s** (seq 2048, batch 8, 64 steps), Llama 3.1 8B LoRA 6,969.59, Llama 3.2 3B full FT 13,519.54; "Peak tokens/sec calculated as (batch_size * steps * sequence_length)/ Total time to train"; the blog body quotes different (higher) numbers for the same rows, so the source is internally inconsistent — [NVIDIA blog](https://developer.nvidia.com/blog/?p=107650)
- Jetson AGX Thor (TRL+PEFT+bitsandbytes) tutorial: Qwen3.5 9B LoRA r8, 512 samples, seq 2048, 4x2 batch: ~50 GB, 215.79 s/epoch, 2.37 samples/s; Qwen3.5 27B QLoRA 4-bit: ~28 GB, 618.94 s, 0.83 samples/s; Qwen3.5 4B full SFT ~42 GB, 1.68 samples/s; "~115 GB available for training"; >27B warns bf16->4bit conversion "requires temporarily holding the original weights in RAM" — [Jetson AI Lab](https://www.jetson-ai-lab.com/tutorials/finetune-on-jetson)
- Half the Experts (the only healing-on-a-128 GB-box precedent) names its device as DGX Spark GB10, 119 GB unified at ~273 GB/s; framework, batch, sequence length, tokens/s and memory are **not reported**; healing "in under three hours" — [arXiv 2607.16721](https://arxiv.org/html/2607.16721)

### Inferences
- The 70B-class Soup datapoint is the best proxy for "streamed LoRA step cost": a 36 GB store read from disk in ~16-17 s = ~2.2 GB/s effective (4.4 GB/s if forward and backward both re-read), i.e. a step on a streamed store is NVMe-bound at small batch exactly as ZeRO-Infinity's bandwidth model predicts (needs >70 GB/s to be compute-bound at tiny batch; Thor's NVMe is 3.9 GB/s measured).
- No tool combines (i) MoE grouped experts, (ii) FP4 (MXFP4/NVFP4) frozen base, (iii) NVMe streaming and (iv) aarch64/L4T. Soup's NF4-only base and 8B/14B-verified backward make it a reference design, not a drop-in; SlideFormer is full-parameter and x86. A custom ~1-2k-line PyTorch loop (per-layer `load -> dequant -> fwd/bwd -> evict`, double-buffered from NVMe via a background thread with O_DIRECT) is the realistic path, and the block-wise (Block-AP-style) variant is simpler than the end-to-end one because it never needs the backward to cross layer boundaries.
- Thor's unified memory removes ZeRO-Infinity's CPU<->GPU tier entirely; only the NVMe tier matters, which is why SlideFormer's "params stay in RAM" rule cannot be applied to a 111.6 GB student on a 122 GiB box without partial residency (see KQ2).

### Gaps
- No measured tokens/s for any LoRA run on a >100B *MoE* streamed from NVMe on any device.
- DeepSpeed/ZeRO-Infinity and Soup on aarch64/L4T (JetPack CUDA 13) are unverified; neither project mentions Jetson.
- Unsloth's MoE offload, torchtune and Axolotl "streaming" turned up no NVMe-weight-streaming feature in the searched sources; GaLore/Q-GaLore were not fetched (they are gradient-projection methods for full-parameter training and do not address frozen-weight residency).
- The DGX Spark 70B QLoRA figure (759.8 tok/s) implies ~4 x 70e9 x 760 = 213 TFLOPS of dequantised-BF16 work on a GB10, above its plausible BF16 dense peak, so it cannot be used to calibrate MFU; treat it as an upper bound at best.

## KQ2. Memory math per layer: does a 2-layer window fit in ~100 GiB, and what batch/sequence is feasible?

### Takeaway
Yes, with a large margin. A V4.1-Flash REAP-55 layer is ~3.5 GB in FP4 (12.5 GB if its experts are dequantised to BF16); a 2-layer window plus per-layer checkpointed inputs for 64k tokens, recompute buffers, LoRA/router optimizer state and cached targets is ~50 GB, leaving room to keep roughly 20 of the 32 layers *resident* and stream only the rest. Micro-batches of 32-64k tokens (e.g. 16-32 x 2048) are what make the streamed design compute- rather than NVMe-bound (KQ5).

### Cited Findings
- Per-expert bytes on V4.1-Flash: 288.8 GB / 40 layers / 384 experts = 18.8 MB (FP4 incl. scales, ~0.53 B/param for 3 x 5120 x 2304 = 35.4M params); attention 0.14 GB/layer; shared expert 35 MB/layer; "fits" row: drop 8/40 blocks + keep 173/384 -> 103.1 GB experts + 8.5 GB other = 111.6 GB — [LOCAL structural_and_memory_budget.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/structural_and_memory_budget.md)
- NeMo Automodel keeps frozen routed experts "packed as fp4-e2m1 + e8m0 block scales" (the DeepSeek V4 Flash checkpoint format) and dequantises "on the fly inside the grouped GEMM" via `MXFP4GroupedMM`, so the bf16 weight tensor is transient; frozen experts + LoRA on attention is the documented pattern — [NeMo Automodel quantized_experts](https://docs.nvidia.com/nemo/automodel/latest/nemo-automodel/nemo_automodel/components/moe/quantized_experts)
- ZeRO-Infinity activation-checkpoint traffic needs only 1-4 GB/s (AIT = 24 x hidden x checkpoint-interval), far below its 70 GB/s parameter figure — [ar5iv 2104.07857](https://ar5iv.labs.arxiv.org/html/2104.07857)
- Sparse-logit targets cost 3 bytes per stored token-id/prob pair, 12 unique tokens per position = 36 B/token — [arXiv 2503.16870](https://arxiv.org/html/2503.16870v2)
- Thor: 128 GB LPDDR5X, 273 GB/s; the tutorial estimates ~115 GB usable for training — [NVIDIA Jetson Thor](https://www.nvidia.com/en-us/autonomous-machines/embedded-systems/jetson-thor/); [Jetson AI Lab](https://www.jetson-ai-lab.com/tutorials/finetune-on-jetson)

### Inferences (arithmetic, all [DERIVED])
Per-layer weights (REAP-55 student, 173 experts): experts 173 x 18.8 MB = **3.25 GB FP4** (dequantised BF16: 173 x 70.8 MB = **12.2 GB**); attention + shared expert + router ~0.27 GB (8.5 GB / 32) -> **~3.5 GB/layer FP4, ~12.5 GB/layer BF16**. Teacher (unpruned) layer: 384 x 18.8 MB = 7.22 GB FP4 (27.2 GB BF16).

Per-token activation bytes per layer (BF16): residual input 5120 x 2 = **10 KB**; MoE internals for 6 routed experts (gate, up, act x 2304 x 6 x 2 B) = **83 KB**; attention q/k/v/o at 8 heads x 256 ~ 12 KB -> ~105 KB/token/layer if everything is saved, **10 KB/token/layer with per-layer checkpointing** (save the layer input, recompute internals in backward).

End-to-end layer-streamed LoRA (Option A) budget for a micro-batch of N tokens, 2-layer FP4 window, 32 layers:
| item | N = 8k | N = 32k | N = 64k |
|---|---|---|---|
| window weights (2 x 3.5 GB FP4; dequant scratch for one layer 12.2 GB) | 19 GB | 19 GB | 19 GB |
| checkpointed layer inputs, 32 x 10 KB x N | 2.6 GB | 10.5 GB | 21 GB |
| recompute buffer for the active layer, 105 KB x N | 0.8 GB | 3.4 GB | 6.9 GB |
| logits, chunked (vocab ~129k x 2 B x chunk of 4k rows) | 1 GB | 1 GB | 1 GB |
| trainable params (LoRA r64 attn+shared ~105M + routers 32 x 5120 x 173 = 28M -> ~130M) x 16 B (fp32 master+grad+Adam m,v) | 2.1 GB | 2.1 GB | 2.1 GB |
| cached targets, 36 B/token (12 sampled logits) | <0.01 GB | <0.01 GB | <0.01 GB |
| CUDA context, allocator slack, OS, page cache floor | ~8 GB | ~8 GB | ~8 GB |
| **total** | **~34 GB** | **~44 GB** | **~58 GB** |
So a 2-layer window fits with 60-85 GB to spare, which is better spent on **partial residency**: at N = 64k, ~60 GB = **17 of 32 layers can stay resident** (FP4), and only ~15 layers (52 GB) are streamed per pass; at N = 32k ~20 layers resident, 12 streamed (42 GB). The whole 111.6 GB student is 10-25 GB over what fits beside training state, which is precisely the gap streaming must cover — not the whole model.

Block-wise (Option B, Block-AP-style, KQ4) budget for a corpus of N_corpus tokens held as hidden-state streams: student stream S_i and teacher stream T_i at 10 KB/token each -> **20 GB per 1M tokens** (10 GB with FP8 states); resident weights: student layer 3.5 GB FP4 (+12.2 GB dequant) + teacher layer 7.2 GB FP4 (+ per-group dequant scratch ~2 GB) ~ 25 GB; micro-batch recompute 105 KB x 8k = 0.8 GB; optimizer for one layer's trainables (~4M params) negligible. **2M tokens: ~75 GB resident, fits; 8M tokens: streams are 160 GB -> spill both streams to NVMe (sequential, see KQ5) or keep them FP8 (80 GB, fits).**

Feasible batch/sequence: sequence length is free up to a few k (attention activations are tiny because V4.1-Flash has 8 heads x 256 and a 512-channel KV latent — [LOCAL structural note]); the binding quantity is tokens per optimizer step, and the streamed design *wants* 32-64k tokens/step (KQ5), which is 16-32x the 2 x 1024 steps MAESTRO/Half-the-Experts used (so 2M tokens = only 30-60 optimizer steps). The block-wise design has no such coupling because it steps many times per resident layer.

### Gaps
- V4.1-Flash's exact FP4 scale layout is "fp4" in config; NeMo says e2m1 + e8m0 (MXFP4). The BF16 dequant scratch estimate assumes 0.53 B/param in, 2 B/param out.
- No measured training-time activation footprint for a V4.1-Flash layer exists; the 105 KB/token figure is a parameter-count estimate (DSA indexer and CSA2 reuse activations not included).

## KQ3. Backward through MXFP4/NVFP4 frozen weights on Jetson (sm_110a): what works today?

### Takeaway
No FP4 *backward* kernel is needed, and none that targets sm_110a exists: because the experts are frozen, the only backward op through them is dgrad = grad_out x W, which can run as a plain BF16 GEMM on dequantised weights (the NeMo Automodel `MXFP4GroupedMM` pattern: dequantise inside the grouped GEMM in both passes, no weight gradient). bitsandbytes' PyPI aarch64 wheels (which do list sm110 for CUDA 13) are explicitly **not compatible with L4T/JetPack** and need a source build; torchao's NVFP4 training work (closed Oct 2026) targets datacenter Blackwell; Unsloth's gpt-oss MXFP4 path uses custom backward functions written because "the MXFP4 kernels do not yet support training".

### Cited Findings
- bitsandbytes install matrix: Linux aarch64 CUDA 13.0-13.2 wheels target "sm75, sm80, sm90, sm100, sm110, sm120, sm121"; but "**NVIDIA Jetson (L4T / JetPack) — source build required.** The Linux aarch64 wheels above are built on aarch64-sbsa runners ... They are **not compatible** with the L4T runtime on Jetson devices (Orin Nano / NX / AGX, Xavier, Thor on CUDA 12)"; the mismatch "surfaces as a runtime symbol-resolution error like `Error named symbol not found in /src/csrc/ops.cu`"; options: on-device `cmake -DCOMPUTE_BACKEND=cuda -DCOMPUTE_CAPABILITY=<cc>` build, or Jetson AI Lab's prebuilt index; NF4/FP4 kernels need only CC 6.0+ — [bitsandbytes installation docs](https://huggingface.co/docs/bitsandbytes/main/en/installation)
- Jetson AI Lab's Thor tutorial installs `bitsandbytes` via pip and runs Qwen3.5-27B QLoRA (4-bit) on Thor, so a working NF4 bitsandbytes on Thor is demonstrated (wheel provenance not stated) — [Jetson AI Lab](https://www.jetson-ai-lab.com/tutorials/finetune-on-jetson)
- torchao NVFP4 training tracker (#3293) closed as completed 2026-10-07: dense + MoE NVFP4 training "done, delivered via torchtitan #4821"; MoE via "NVFP4 GroupedExperts support on Blackwell" (PR #4598); backward design = dgrad with 1x16 stochastic-rounding quant of the upstream grad + 16x16 RTNE weight quant + scaled GEMM, wgrad with random Hadamard transforms; the page names Blackwell/Hopper, **never sm_110 or sm_120** — [pytorch/ao #3293](https://github.com/pytorch/ao/issues/3293)
- Unsloth (Aug 2025): "the MXFP4 kernels do not yet support training, since the backwards pass is not yet implemented"; Unsloth "wrote custom training functions for the MXFP4 layers"; gpt-oss-20B trains "on just 14GB of VRAM" (blog returned HTTP 403 on fetch; wording from the search index) — [Unsloth gpt-oss blog](https://unsloth.ai/blog/gpt-oss)
- NeMo Automodel: frozen routed experts stay packed MXFP4; `MXFP4GroupedMM` replaces bf16 `torch._grouped_mm` and dequantises on the fly; "because the base weights are frozen, no weight gradient is produced"; LoRA on attention only is the typical case; no hardware requirement stated — [NeMo Automodel mxfp4](https://docs.nvidia.com/nemo/automodel/nemo-automodel/nemo_automodel/components/quantization/mxfp4); [quantized_experts](https://docs.nvidia.com/nemo/automodel/latest/nemo-automodel/nemo_automodel/components/moe/quantized_experts)
- Unsloth's NVFP4 docs cover inference only and require "Blackwell GPUs like RTX 50X, DGX Spark, B200, B300" — [Unsloth NVFP4](https://unsloth.ai/docs/basics/nvfp4)
- Soup's streamed NF4 backward produced "silently wrong gradients" above ~165 MiB per layer until v0.73.0; "the cause is named in the upstream library" (i.e. the quant library, not Soup) — [Soup README](https://github.com/MakazhanAlpamys/Soup)
- Local hardware facts: sm_110a has no tcgen05 but does have cp.async and FP4x2 unpack instructions — [LOCAL dspark-decode-gap-research](file:///home/patrickd/.claude/projects/-home-patrickd/memory/dspark-decode-gap-research.md); FA3 crashes on Thor, TRITON_ATTN is the working attention backend — [LOCAL dflash-thor-build](file:///home/patrickd/.claude/projects/-home-patrickd/memory/dflash-thor-build.md)

### Inferences
- The safe Thor recipe is **dequantise-once-per-layer to BF16 then plain `torch.matmul`/`torch._grouped_mm`**: 12.2 GB of BF16 scratch per student layer and ~2 GB per group of the teacher layer fit inside the KQ2 budget, the FP4 unpack is a memory-bound elementwise op (3.25 GB in, 12.2 GB out per layer: ~0.06 s at 273 GB/s), and no FP4 tensor-core or FP4-backward kernel is touched. This also sidesteps the bitsandbytes L4T ABI problem entirely (a tiny CUDA/Triton e2m1+e8m0 unpack kernel is all that is needed; the project already has FP4 unpack code in its CUDA servers — [LOCAL glm53-nvfp4-dense-overlay](file:///home/patrickd/.claude/projects/-home-patrickd/memory/glm53-nvfp4-dense-overlay.md)).
- QLoRA-style "dequant inside the GEMM" (bitsandbytes/Unsloth/NeMo) saves the 12 GB scratch but costs an FP4->BF16 dequant in forward *and* backward and, on this box, a source build; it only matters if the BF16 scratch does not fit, which KQ2 shows it does.
- The Soup gradient bug is the cautionary tale for any streamed backward: verify per-layer gradients against a resident reference on a small model (the project's own "assert served identity" rule — [LOCAL eval-orphaned-server-trap](file:///home/patrickd/.claude/projects/-home-patrickd/memory/eval-orphaned-server-trap.md) — applies to training too).

### Gaps
- Whether `torch._grouped_mm` (BF16) and Triton work on sm_110a under the JetPack CUDA-13 PyTorch build was not tested (no torch in the system Python; the vLLM container was not probed because a server is running and the memory rule forbids co-running probes — [LOCAL thor-unified-memory-oom](file:///home/patrickd/.claude/projects/-home-patrickd/memory/thor-unified-memory-oom.md)).
- No source reports NVIDIA ModelOpt QAT, torchao NVFP4 or Unsloth MXFP4 running on Jetson Thor.

## KQ4. Distillation targets without a resident teacher, and layer-local vs end-to-end KD quality

### Takeaway
Cached targets are cheap at the output (36 B/token for 12 importance-sampled logits, unbiased, matching full KD within noise in the paper's 300M-3B experiments) but expensive at the hidden-state level (10 KB/token/layer; all 32 layers of a 2M-token corpus = 640 GB), so layer-local training should compute teacher targets *on the fly by streaming the teacher layer beside the student layer* rather than caching them. Layer-local (block-wise) objectives are the only ones that make the streamed backward trivially local and have measured quality: competitive with or better than logit-KD on reasoning but worse on generation unless a short end-to-end pass follows (OverRep: local 90.2/47.1 vs logit-KD 87.1/58.1 vs local+KD 91.8/61.0 reasoning/generation RP at 4.6/36.4/7.0 h; EfficientQAT: Block-AP 8.53 ppl -> +E2E 7.68). No paper measures local-vs-global KD on a *pruned MoE*.

### Cited Findings
- Random Sampling KD: samples from the teacher's own distribution (tau = 1; uniform "causes training to diverge"), "we use 12 unique tokens"; storage "17 bits for vocabulary IDs and 7 bits for probabilities, totaling 24 bits (3 bytes) per unique token"; Table 5 at 100B tokens: full KD 10,000 TB, Top-K (300) 90 TB, theirs 3.6 TB; quality (3B student, 8B teacher, 100B tokens): Top-K-12 LM loss 2.49963 / 56.6, RS-KD-12 2.35005 / 57.5, FullKD 2.34446 / 57.5; "Top-K probabilities provide biased estimates" — [arXiv 2503.16870](https://arxiv.org/html/2503.16870v2)
- Router KD (2603.02217): token-level KL from the original MoE's next-token distribution, temperature tau, only router params trained, "gradients flow through the (soft) gating weights of the selected experts"; ~2 h for Qwen3-30B-A3B on A100-40GB, ~40 min for Mixtral-8x7B; router = ~0.04% (Qwen3) / 0.002% (Mixtral) of params; gains "substantially larger in fine-grained MoEs"; does not help "under catastrophic collapse" — [arXiv 2603.02217](https://arxiv.org/html/2603.02217v1)
- OverRep ("Train Overcomplete, Deploy Compact"): layer-wise distillation = train a retained block so its output matches the original model's hidden state after the pruned segment (Frobenius MSE); Table 6 (LLaMA3-3B, avg RP reasoning / generation / hours): 25% prune — Logit-KD 87.1/58.1/36.4 h, OverRep (local MSE) 90.2/47.1/4.6 h, OverRep-KD 91.8/61.0/7.0 h; 50% — 67.5/22.9/32.5 h, 72.3/10.7/4.6 h, 73.4/26.7/7.0 h; recovery data 120k FineWeb-Edu samples x 1024 (~123M tokens/epoch), 20 epochs; MoE case Qwen3-30B-A3B at 25%: OverRep 53.1/30.1 in 8.8 h vs LoRA 49.8/23.4 in 53.3 h on 8 GPUs, "The router is left untouched"; no local-vs-global comparison on the MoE — [arXiv 2609.06974](https://arxiv.org/html/2609.06974)
- EfficientQAT ablation (Llama-2-7B w2g64): Block-AP only avg PPL 8.53 / acc 58.99; + E2E-QP 7.68 / 60.14; the authors cite BRECQ that "block-wise training achieves faster convergence" with less data/memory, but block-wise methods "overlook cross-block interactions" — [arXiv 2407.11062](https://arxiv.org/html/2407.11062v3)
- MoE-Pruner expert-wise KD: L = L_CE + lambda x sum over layers/experts of MSE(student expert output, teacher expert output); 1000 C4 samples, 3 epochs, full-parameter, ~1 h on 16 H100; Mixtral-8x7B at 50% (unstructured) avg 67.23 -> 68.40 vs 69.16 dense (98.9%); no comparison against logit-level KD — [arXiv 2410.12013](https://arxiv.org/html/2410.12013v1)
- Half the Experts' targets are the base model's *generated responses* (SFT on 1,863 teacher-written exchanges, loss masked to the assistant turn) — no logits cache at all — [arXiv 2607.16721](https://arxiv.org/html/2607.16721)
- MAESTRO RFT: 2,000 x 1,024-token SlimOrca conversations, LoRA r16 on attention, experts + router frozen; REAP w/o RFT 77.9% -> with RFT 97.7% RP at 25% on GPT-OSS-20B — [LOCAL healing_recovery.md citing arXiv 2607.08601](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/healing_recovery.md)

### Inferences (arithmetic [DERIVED])
- Output-level cache: 12 x 3 B = 36 B/token -> **2M tokens = 72 MB, 8M = 288 MB**. Generating it needs one *teacher* prefill pass over the corpus: the unpruned teacher (288.8 GB experts + 203 GB Engram) is not resident either, so this is itself a layer-streamed forward: 40 layers x 7.4 GB = 296 GB of NVMe per pass -> 76 s per pass at 3.9 GB/s; at 64k tokens/pass, 2M tokens = 32 passes = 40 min of NVMe (compute ~2 x 16B x 2M = 64 PFLOP = 16-40 min at 26-65 TFLOPS) -> **~1 h per 2M tokens of cached teacher logits**, plus the Engram lookups (random reads into the 203 GB table at layers 1 and 14 — small per token, unmeasured).
- Hidden-state cache: 10 KB/token/layer x 32 layers = **320 KB/token -> 2M tokens = 640 GB, 8M = 2.6 TB** — does not fit the 1 TB NVMe at the token budgets that worked. Therefore block-wise training must regenerate targets per layer by co-streaming the teacher layer (7.2 GB FP4) with the student layer (3.5 GB): the teacher stream T_i and student stream S_i are each 10 KB/token and are *overwritten in place* as training advances one layer (20 GB per 1M tokens resident, or FP8).
- Student/teacher stream alignment: V4.1-Flash's student drops 8 blocks and Engram, so "layer i of the student" maps to a teacher *segment*; the OverRep/Streamline objective (match the teacher hidden state at the end of the segment) handles this directly, and the dropped-Engram mismatch at teacher layers 1 and 14 is absorbed into the first block's target.
- Quality expectation: local MSE alone recovers reasoning-type metrics as well as or better than global logit KD at a fraction of the compute, but loses on generation; the cheapest fix with measured support is a short end-to-end logit-KD/SFT polish on the cached 12-sample logits or teacher responses (OverRep-KD, E2E-QP) — which is Option A at a small token count (KQ5).

### Gaps
- No paper measures layer-local vs end-to-end KD on an expert-pruned MoE (OverRep's MoE row trains without the local-vs-global ablation; MoE-Pruner has no logit-KD arm).
- No source measures the quality cost of dropping Engram from the teacher stream, or of teacher targets generated by a streamed (bit-identical) vs resident teacher (should be none).

## KQ5. Throughput: tokens/s for a layer-streamed step on Thor vs the 2-8M-token budgets

### Takeaway
[extrapolation] An end-to-end streamed LoRA step is NVMe-bound below ~30k tokens per pass (~140-370 tok/s at 8k tokens/pass) and compute-bound above it (~600-1,500 tok/s at 10-25% MFU), so 2M tokens costs 6-16 h with Half-the-Experts-sized steps or 0.5-1 h with 32-64k-token steps (but then only 30-60 optimizer steps). The block-wise variant pays NVMe once per layer (~90 s total) and is purely compute-bound: **~0.5-1.1 h per 1M tokens at 2 epochs/block**, i.e. 2M tokens in 1-2 h and 8M in 4-9 h. Both fit a weekend; the block-wise one fits an evening.

### Cited Findings
- NVMe measured on this Thor: 3.9 GB/s direct-I/O sequential read (WD SN5000S) — [LOCAL measurement, this note]
- Thor T5000: 2070 TFLOPS FP4 sparse (NVIDIA); 517 TFLOPS FP8 dense and 1035 FP4 dense per flopper.io citing the module datasheet; BF16 dense is not listed anywhere found — [NVIDIA Jetson Thor](https://www.nvidia.com/en-us/autonomous-machines/embedded-systems/jetson-thor/); [flopper.io](https://flopper.io/gpu/nvidia-jetson-agx-thor-t5000-128gb)
- V4.1-Flash activates 16B params at decode, 8B at prefill (CSA2 reuse layers) — [LOCAL structural note citing arXiv 2609.19969](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/structural_and_memory_budget.md)
- Soup 70B-shaped 36 GB NF4 store from disk: 16.2-17.3 s per cold step with direct I/O, 9.97 s with two striped drives — [Soup README](https://github.com/MakazhanAlpamys/Soup)
- SlideFormer: NVMe "becomes the primary bottleneck", throughput "scales near-linearly with the number of NVMe drives" — [arXiv 2603.16428](https://arxiv.org/pdf/2603.16428)
- Block-AP: Llama-2-70B, 8.4M tokens x 2 epochs per block, 26.6 h on one A100 (i.e. ~175 tok/s of fwd+bwd per block-visit aggregated over 80 blocks) — [arXiv 2407.11062](https://arxiv.org/html/2407.11062v3)
- Thor LoRA tutorial rates: Qwen3.5-9B LoRA 2.37 samples/s (seq cap 2048, average sample length not given); 27B QLoRA 0.83 samples/s — [Jetson AI Lab](https://www.jetson-ai-lab.com/tutorials/finetune-on-jetson)

### Inferences (arithmetic, all [DERIVED / extrapolation])
Constants used: BF16 dense peak ~259 TFLOPS (half of the 517 FP8 figure; **assumption**); effective training MFU for a dequantised MoE with 6-of-173 grouped GEMMs, LoRA and recompute: **10-25% -> 26-65 TFLOPS** (bracket chosen because the only Thor/GB10 training datapoints are internally inconsistent or lack token counts, see KQ1 gaps). Per-token FLOPs with frozen experts = forward 2P + dgrad 2P (no wgrad on experts) = **4 x P_active**; P_active per student layer = 6 x 35.4M + 35M shared + ~100M attention ~ 320M -> 32 layers ~10.2B + lm_head 0.66B ~ **11B -> 44 GFLOP/token** end-to-end; per layer ~1.3 GFLOP/token (fwd+dgrad), 0.64 GFLOP/token teacher forward.

**Option A — end-to-end streamed LoRA + router (loss on cached logits / teacher responses):**
- NVMe per pass: full streaming reads every layer in forward and again in backward: 2 x 111.6 GB = 223 GB -> **57 s**; with 17-20 layers resident (KQ2) ~42-52 GB x 2 minus the window -> **~22-26 s**.
- Compute per pass of N tokens: N x 44 GFLOP / (26-65 TFLOPS). N = 8k: 5-14 s (NVMe-bound -> **140 tok/s full-stream, ~330 tok/s partial**); N = 32k: 22-54 s (break-even); N = 64k: 43-108 s (compute-bound -> **600-1,500 tok/s**; per-layer prefetch 0.9 s vs per-layer compute 1.3-3.2 s overlaps cleanly).
- Hours per 1M tokens: at 2k-token steps (MAESTRO/Half-the-Experts regime, 500 steps): 500 x 57 s = **7.9 h** (full stream) or 500 x 24 s = **3.3 h** (partial); at 64k-token steps: **0.2-0.5 h** but only ~16 steps per 1M tokens.
- 2M / 8M tokens: 2k-step regime 6.6-16 h / 26-63 h; 32-64k-step regime 0.5-1 h / 2-4 h. A weekend (48 h) covers 2M tokens in every regime and 8M only with >=16k-token steps or partial residency.

**Option B — block-wise (Block-AP / OverRep-style) with co-streamed teacher layer, local hidden-state MSE, LoRA + router + per-expert scalars trainable, E epochs per block:**
- NVMe: once per layer, 32 x (3.5 + 7.2) GB = 342 GB -> **88 s total per corpus visit** (independent of token count); plus, if streams spill (>4M tokens), 2 x 20 KB/token read+write per layer: 8M tokens -> 320 GB/layer -> 82 s/layer -> 44 min total.
- Compute per token per layer: teacher fwd 0.64 + E x student fwd+dgrad 1.3 GFLOP; E = 2 -> 3.2 GFLOP x 32 layers = **102 GFLOP/token** -> 1M tokens = 102 PFLOP -> **26-65 min per 1M tokens** (E = 4: 48-120 min).
- 2M tokens: **1-2.2 h**; 8M tokens: **3.5-9 h (+0.7 h NVMe spill)**. Optimizer steps are unconstrained (micro-batch 4-8k tokens -> 250-500 steps per epoch per block).
- Reference check: Block-AP did 8.4M tokens x 2 epochs over 80 Llama-2-70B blocks in 26.6 h on an A100 (~312 TFLOPS BF16 peak, full-parameter wgrad) -> the Thor estimate above (32 blocks, no wgrad, ~4x lower effective FLOPS) is in the same order, which is the point: block-wise healing of a 500B-class student is the Block-AP workload, and Block-AP has been run at 70B on one 80 GB GPU.

Then an optional **Option A polish** on 0.25-0.5M tokens of cached 12-sample logits (OverRep-KD / E2E-QP analogue): 0.8-4 h.

### Gaps
- No measured MFU for grouped-expert training on sm_110a; the 10-25% bracket is an assumption, and Triton/`_grouped_mm` performance on Thor is unknown. A 1-layer micro-benchmark (dequant + grouped GEMM fwd/dgrad on 8k tokens) would pin the whole table and should be the first experiment.
- NVMe read while the GPU is saturating the same LPDDR5X (273 GB/s shared) was not measured; contention could lower the 3.9 GB/s.

## KQ6. The router: cost of training the full 384-way router with experts frozen, and the cached-expert-outputs trick

### Takeaway
Router gradients in a hard top-k MoE flow only through the *selected* experts' soft gate weights (Router KD states this explicitly), so router training needs the selected experts' outputs, not all 384 — and in the block-wise scheme those experts are resident anyway, making the router update essentially free. Caching expert outputs to train the router *without* experts is data-infeasible at the 2-8M-token budgets (61 KB/token/layer for top-6 in BF16 -> ~2 TB per 1M tokens over 32 layers) and only works for a ~100-250k-token ExFold-scale pass; no paper does it. Router-only recovery on a 504B REAP student (GLM-5.2 keep-168, 0.016% of params) is self-reported in the wild but with no hardware or throughput disclosed.

### Cited Findings
- Router KD: "gradients flow through the (soft) gating weights of the selected experts during the forward pass, but parameter updates are restricted to the router"; the full student forward is run; ~2 h on A100-40GB for Qwen3-30B-A3B; gains concentrate in fine-grained MoEs because the routing space is large (C(128,8) ~ 1.43e12 subsets) — [arXiv 2603.02217](https://arxiv.org/html/2603.02217v1)
- ReMoE (ICML 2026): freezes "all non-router weights, such as embeddings, attention blocks, and expert FFNs, and tune only the gate parameters", with a frozen reference router alongside the trainable one; +26% expert reuse at maintained downstream performance on DeepSeek and Qwen models — [arXiv 2605.27081](https://arxiv.org/pdf/2605.27081)
- GLM-5.2-504B REAP keep-168 (0xSero, self-reported): recovery = "gate-only distillation toward the unpruned model", router gates "0.016% of params", NVFP4 routed experts, BF16 router/attention/shared; 2,000-prompt test shows loops 3.6% (full) vs 7.2% (pruned) — [HF model card](https://huggingface.co/0xSero/GLM-5.2-504B-W4A16)
- Half the Experts trains "the router matrices in full" with experts frozen (byte-identical after training) — [arXiv 2607.16721](https://arxiv.org/html/2607.16721)
- OverRep's MoE run leaves the router untouched and still recovers 53.1/30.1 RP at 25% — [arXiv 2609.06974](https://arxiv.org/html/2609.06974)
- ExFold-style closed-form routing-scalar folding is gradient-free, uses <=131k calibration tokens and is layer-streamable — [LOCAL healing_recovery.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/healing_recovery.md)
- The noaux_tc router (bias selects, unbiased sigmoid weights) has zero gradient to the selection bias — [LOCAL noaux-tc-router-formula](file:///home/patrickd/.claude/projects/-home-patrickd/memory/noaux-tc-router-formula.md)

### Inferences (arithmetic [DERIVED])
- Router gradient per token per layer: dL/dgate_e = <dL/dy, y_e> for each selected e (6 dot products of length 5120), then the sigmoid/softmax Jacobian and a 5120 x 173 outer product — ~5 MFLOP/token/layer, negligible against the 1.3 GFLOP expert fwd+dgrad. **The router costs nothing extra once the experts are being run anyway** (Options A and B both run them).
- Cached-expert-outputs variant: top-6 outputs y_e = 6 x 5120 x 2 B = **61.4 KB/token/layer** (30.7 KB FP8); 32 layers -> **1.97 MB/token -> 1.97 TB per 1M tokens** (0.98 TB FP8). The 1 TB drive holds ~0.25-0.5M tokens of it, and the cache goes stale as soon as the router's top-6 changes (which is the goal), so top-K' >= 12 candidates must be cached (2x more). Per layer at 1M tokens it is 61 GB — holdable in RAM *during* that layer's block-wise pass, where it only saves re-running the resident experts across epochs (~30% of Option B compute). Verdict: a minor optimisation inside Option B, not a standalone lever.
- With V4.1-Flash's noaux_tc-style selection, the 384-way router "full training" moves the gate *weights* (sigmoid scores) and the selection only through the weight matrix; the per-expert selection bias gets no gradient, so expect the gain mostly from re-weighting among the surviving experts, which is also what ExFold's scalar fold captures closed-form — the gradient router adds the ability to change *which* survivors are picked.

### Gaps
- No paper on "router training from cached expert outputs" was found (ReMoE, Cache-Aware Joint Router Adaptation, Sticky Routing and Router-Decoupled MoE all train routers for cache locality, not from cached outputs).
- Router KD's Appendix F.3 hyperparameters, token counts and the quantitative pruned-vs-recovered numbers were not in the fetched text; the GLM-5.2 router-KD hardware and token budget are undisclosed.

## KQ7. Feasibility verdict: healing a REAP-55 V4.1-Flash (111.6 GB student) on one Thor

### Takeaway
[extrapolation] Feasible, and in a weekend, by abandoning the end-to-end backward and healing block-wise: 2M tokens ~1-2 h, 8M tokens ~4-10 h of compute with ~90 s of NVMe per corpus visit, ~75 GB resident; the end-to-end LoRA pass the prior researchers called "custom layer-streamed backward" is also buildable (2M tokens in 3-16 h depending on step size and partial residency) but is only worth running as a short polish. What does *not* exist is any of this as software: no framework streams FP4 MoE experts from NVMe on aarch64, no FP4 backward kernel is needed or available for sm_110a, and the quality of layer-local healing on an expert-pruned MoE is unmeasured.

### Cited Findings
- (all cited above; headline numbers) Block-AP 70B on one A100: 29.9 GB, 26.6 h for 8.4M tokens x 2 epochs — [arXiv 2407.11062](https://arxiv.org/html/2407.11062v3); OverRep local-vs-global quality table — [arXiv 2609.06974](https://arxiv.org/html/2609.06974); Soup streamed-NF4 70B-shaped step 16-17 s — [Soup README](https://github.com/MakazhanAlpamys/Soup); bitsandbytes L4T incompatibility — [bitsandbytes docs](https://huggingface.co/docs/bitsandbytes/main/en/installation); NeMo MXFP4 frozen-expert dequant-in-GEMM pattern — [NeMo Automodel](https://docs.nvidia.com/nemo/automodel/nemo-automodel/nemo_automodel/components/quantization/mxfp4); 12-sample logits at 3 B each — [arXiv 2503.16870](https://arxiv.org/html/2503.16870v2); Thor NVMe 3.9 GB/s — [LOCAL measurement]; vLLM server currently resident at 105 GB and the never-co-run rule — [LOCAL thor-unified-memory-oom](file:///home/patrickd/.claude/projects/-home-patrickd/memory/thor-unified-memory-oom.md)

- Steps: B gives 250-500 optimizer steps per block per epoch at 4-8k-token micro-batches, comparable to the ~1000-step regimes that worked; A at 32k-token steps gives only 8-16 steps per 0.25-0.5M tokens, which is why it is a polish, not the main heal.
- Residual risks ranked: (1) quality of layer-local healing on expert-pruned MoE — unmeasured (OverRep shows local MSE loses generation RP by ~11 pts vs logit-KD at 25% dense depth-pruning unless followed by KD); (2) Thor training MFU and Triton/grouped-GEMM availability on sm_110a — unmeasured; (3) streamed-backward correctness (Soup's silent-gradient bug) — needs a 1-layer resident-vs-streamed gradient diff before any long run; (4) teacher fidelity without Engram — unmeasured; (5) all of it is bespoke code (~1-2k lines), no framework to lean on; the project's existing FP4 unpack and layer-wise REAP observer code are the reusable pieces.

### Gaps
