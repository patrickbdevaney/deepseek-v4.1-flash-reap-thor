# Serving performance of extreme-quantization formats for large MoE on Jetson AGX Thor (sm_110a) and comparable 128 GB-class single devices

Scope note: every number below states hardware, model, quant, runtime/version and context where the source gives them. Anything not measured on Thor is tagged **[comparable device, not Thor]**. Thor and DGX Spark share 128 GB LPDDR5X at ~273 GB/s; measured Thor decode is 1.08–1.42x slower than Spark on the same llama.cpp build, prefill ~1.9x slower (see Q2). Several NVIDIA-forum threads were only retrievable as Discourse `.md` exports (403 on HTML); hackster.io and the NVIDIA `jetson-memory-audit` skill page were 403/Cloudflare-blocked, so those two are cited from search-engine snippets only and flagged.

## Key question 1: Which runtimes have working sm_110a / Thor builds in 2026, and with which quant kernels?

### Takeaway
On Thor in 2026 the working stacks are (a) mainline llama.cpp CUDA (all GGUF types incl. IQ, but with a Blackwell IQ1_S/IQ2_S/IQ3_S correctness bug fixed only in late 2026 and an open sm_110 garbage-output issue on one hybrid MoE arch), (b) vLLM via NVIDIA's Thor containers or ARM64 nightlies (NVFP4 via FlashInfer-CUTLASS or Marlin, GPTQ/AWQ W4A16 via Marlin, MXFP4 via Marlin only, Triton paths repeatedly broken on sm_110a), and (c) TensorRT-Edge-LLM (NVFP4/INT4-GPTQ, but only ≤35B MoE models published). TensorRT-LLM is officially not supported on Thor; SGLang has no Thor-specific measured result found; ik_llama.cpp and exllamav3 have no Thor reports at all (exllamav3 ships x86_64 wheels only).

### Inferences
- The only Thor paths with public evidence of running 100B+ MoE are llama.cpp GGUF (MXFP4 gpt-oss-120b, IQ4_XS Qwen3.8-Flash-Next with an open correctness bug) and vLLM NVFP4 (Nemotron-3-Super-120B at ~10.5 tok/s, gpt-oss-120b NVFP4 at ~31 tok/s). Nobody has published IQ1/IQ2/IQ3 GGUF runs of a 300B+ model on Thor itself; all such runs are on DGX Spark.
- Because the IQ1_S/IQ2_S/IQ3_S Blackwell bug (#27902) lives in `vecdotq.cuh` generic CUDA code and the fix PR is unmerged, any Thor llama.cpp build should be validated with `test-backend-ops` on those types before trusting IQ2_S/IQ3_S outputs; IQ2_XXS/IQ3_XXS/IQ4_XS were used as passing controls.
- vLLM on Thor is effectively "Marlin W4A16 for everything that works reliably" (NVFP4 via Marlin dequant, MXFP4 via Marlin, GPTQ/AWQ via Marlin); the FlashInfer-CUTLASS NVFP4 path works for dense GEMM but MoE grouped-GEMM NVFP4 is broken or crash-prone on both sm_120 and sm_110 reports. This matches the user's own 122B Marlin crash → CUTLASS MoE + TRITON_ATTN fix.

## Key question 2: Measured tok/s for 2-bit vs 3-bit vs 4-bit on the same model — is 2-bit faster or slower?

### Takeaway
On GB10/Thor-class bandwidth, 2-bit GGUF is only marginally faster than 3-bit (3.6–5.2% on DeepSeek-V4-Flash, ~17% on GLM-5.3-Flash) despite 13–20% fewer bytes, and 1-bit is only ~5% faster than 2-bit: decode on these MoE models is not purely weight-bandwidth-bound once bytes/token fall below roughly 2–3 GiB. The win from 2-bit is fit and KV headroom, not speed. No 2- vs 3- vs 4-bit comparison on Thor itself was found.

## Key question 3: Runtime memory overhead per runtime on Tegra unified memory — how much of 122 GiB is usable?

### Takeaway
Thor reports ~122 GiB total and ~114.7–117.2 GiB MemAvailable at idle; Spark reports 121 GiB "usable". The best documented practical ceilings are 117 GiB used (llama.cpp, Spark, 97 GiB model + 131K ctx) and 119/121 GiB used with 1 GiB free (120.4 GB GLM-5.3-Flash + 64K ctx), with host wedging beyond that; vLLM recipes on Thor use `--gpu-memory-utilization` 0.58–0.85 of the unified pool. A Tegra resource-manager pool retaining freed pages after a CUDA context exits is documented by NVIDIA for JetPack < 7.2, with `drop_caches` as the fix.

### Cited Findings
- Thor reported as "122GB unified memory" (llama.cpp issue, CUDA 13.0) — [llama.cpp #27763](https://github.com/ggml-org/llama.cpp/issues/27763); a Thor stress-test log shows "Memory: about 122 GiB", "MemAvailable at start: ~117.2 GiB" / "~114.7 GiB" / "116.0 GiB", vLLM run with `--gpu-memory-utilization 0.58` + MTP — [Thor BPMP/thermal stall thread](https://forums.developer.nvidia.com/t/jetson-agx-thor-r38-4-bpmp-thermal-path-stalls-after-large-cuda-vllm-unified-memory-workload-nvfancontrol-and-thermal-kworkers-stuck-in-d-state/370477)
- That thread's root cause (NVIDIA): a lock taken in IRQ context in `host1x_intr_handle_interrupt()` racing `host1x_pollfd_poll()`; fix is a custom kernel patch to `drivers/gpu/host1x-fence/dev.c`; symptom is thermal kworkers stuck in D state after a large vLLM unified-memory workload — same thread.
- NVIDIA `jetson-memory-audit` skill (page Cloudflare-blocked; cited from search snippets): after a CUDA workload exits the resource manager "keeps freed system-memory pages in its own pool", so `cudaMemGetInfo` and `free -h` under-report; applies to JetPack < 7.2 / L4T < r39.0; fix `sudo sync && sudo sysctl -w vm.drop_caches=3` on the host — [mcpservers.org mirror](https://mcpservers.org/agent-skills/nvidia/jetson-memory-audit). ## Key question 7: Best-documented "1T-class model on a 128 GB device"

### Takeaway
No resident 1T-class model has a documented run on a 128 GB device. The largest resident, well-documented single-128 GB runs are GLM-5.3-Flash 320B (UD-IQ3_XXS 120.4 GB, 15.5 / 20.8 tok/s with MTP, 64K ctx) and DeepSeek-V4-Flash 284B (UD-IQ2_M 84.7 GiB, 17.4–19.7 tok/s, 131K ctx per slot) on DGX Spark. 1T-class models on 128 GB exist only via NVMe expert streaming at 0.7–2.1 tok/s. On Thor itself the largest documented runs are 120B-class (gpt-oss-120b, Nemotron-3-Super-120B, Qwen3.5-122B).
