# Serving DeepSeek-V4.1-Flash's Engram off the GPU-resident budget on Jetson AGX Thor

Scope: can the ~189 GiB (FP8) / ~97 GiB (MXFP4) Engram n-gram tables be served from NVMe (or any non-pool tier) at interactive batch-1 decode on a Jetson AGX Thor (122 GiB unified LPDDR5X, one PCIe Gen5 x4 M.2 slot), so that the 117 GiB envelope is left for ~99 GiB experts + ~18 GiB fixed. All local numbers below were measured on this Thor on 2026-10-17 (Linux 6.8.12-tegra, WD PC SN5000S 1 TB, with a vLLM Gemma-4-31B server co-resident at 68 GiB; CPU contention from that server makes the tail latencies pessimistic, not optimistic).

Bottom line: yes. Engram-on-NVMe is the standard, measured way DeepSeek-V4.1-Flash is served on DGX Spark (GB10, 128 GB unified, the same memory topology as Thor), and the per-token I/O cost measured here on Thor (48 concurrent row reads = 1.1-1.3 ms p50 via O_DIRECT) is ~1% of a 100 ms decode step even with no prefetch at all. Prefetch (addresses depend only on token ids) is implemented in every working recipe and removes it from the critical path. The disk path must bypass the page cache (O_DIRECT), because on unified memory every cached page is taken from the GPU pool. Engram resident at MXFP4 (97.3 GiB) leaves ~2 GiB for experts, so Engram off-pool is mandatory, not optional.

## Q1. Engram access pattern: rows per token, granularity, addressability

### Takeaway
Per token, each of the two Engram modules reads exactly 24 rows (3 n-gram orders x 8 hash heads), 48 rows total, each row 256 channels; at FP8 that is 264 B/row (256 FP8 + 8 UE8M0 scale bytes) = 12.4 KiB/token from ~48 independent random addresses, and the addresses are a pure function of token ids (a multiplicative-XOR hash of the compressed suffix n-gram, modulo a per-head prime), so they are known before the layer, and before the forward, runs.

### Cited Findings
- "We allocate 196B Engram parameters evenly across two modules. Each module uses N-gram orders {2, 3, 4}, with 8 hash heads and a total embedding dimension of 2048 per order. Each head indexes a table of approximately 16M entries, with table sizes chosen to be distinct primes. Both the embedding tables and the key/value projections use FP8 precision. The modules are placed at layers 1 and 14 (zero-indexed)" — [DeepSeek-V4.1-Flash technical report, arXiv 2609.19969, §2.4.2](https://arxiv.org/pdf/2609.19969) (quoted from pdftotext of the PDF)
- "During inference, deterministic addressing enables embeddings to be prefetched from host memory via background RDMA transfers, with prefetching for the first module overlapping computation in the first Transformer block." — [arXiv 2609.19969 §2.4.2](https://arxiv.org/pdf/2609.19969)
- "Engram lookup indices depend solely on the input token sequence. Embedding prefetch is therefore initiated for the entire local batch before each pipeline stage begins ... Embeddings are stored and fetched in FP8, with the retrieved values and scaling factors passed directly to the following GEMM." — [arXiv 2609.19969 §3.1.3](https://arxiv.org/pdf/2609.19969)
- Original Engram design: head k of order n computes z_{t,n,k} = φ_{n,k}(g_{t,n}) into a table E_{n,k} "of prime size"; φ "is implemented as a lightweight multiplicative-XOR hash"; retrieved embeddings are concatenated over all (n,k) pairs; token ids are first mapped through a surjective compression map ("a 23% reduction in the effective vocabulary size for a 128k tokenizer") — [Conditional Memory via Scalable Lookup, arXiv 2601.07372](https://arxiv.org/html/2601.07372)
- Concrete table shapes (from the llama.cpp converter): "Two tables, on layers 1 and 14, with different row counts (384,006,168 and 384,016,682) because each layer seeds its own prime sized buckets. The lookup is a prime modulo hash reading (max_ngram_size - 1) * n_heads = 24 rows per token per engram layer, so 48 per token, every token." Each table is "384,006,168 x 256"; scales are "[rows, 8], one scale per 32 columns of a single row" — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696)
- Row byte layout as read from disk: "264 bytes per row (256 fp8 plus 8 ue8m0 scale bytes), read as one contiguous read"; total rows "768,022,850"; "12 rows is the real per-rank decode load at TP=4, i.e. 6 hash heads times 2 Engram layers" — [josephdrose, joe-spark-patches dsv41/docs/fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)
- "Per processed token: 24 rows at each of two Engram layers, about 12.4 KiB across the model." — [SemiAnalysis, Engrams/Embedding Entendre Codesign](https://newsletter.semianalysis.com/p/engrams-embedding-entendre-codesign) (paywalled; visible portion)
- vLLM's hasher takes only token ids: `DeepseekV41NgramHash.forward(input_ids, token_mask=None, sequence_ids=None)`, output shape `[batch, sequence, engram_layers, hash_heads]`; hashing does not cross "document, image, or padding boundaries"; per-head `_multiplier_values`, `_offset_values`, `_prime_values` — [NeMo Automodel deepseek_v41/engram.md](https://docs.nvidia.com/nemo/automodel/nightly/nemo-automodel/nemo_automodel/components/models/deepseek_v41/engram.md)
- The 8 head rows of one n-gram cannot be co-located on disk: they land "at independent positions in 8 disjoint ranges," so any static layout that groups one n-gram "scatters every other n-gram" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)

### Inferences
- Byte arithmetic (mine, from the cited shapes): 768,022,850 rows x 264 B = 202.8 GB = 188.8 GiB (matches the 189.13 GiB the Spark recipes report). At MXFP4 (E2M1 two per byte + one UE8M0 per 32 → 128 + 8 = 136 B/row): 104.5 GB = 97.3 GiB, and the per-token read shrinks from 48 x 264 B = 12.4 KiB to 48 x 136 B = 6.4 KiB.
- Granularity: every row read is an independent random address; with a 512 B logical sector the minimum device read is 512 B (FP8 row fits in two sectors at worst because 264 B rows are not sector-aligned; josephdrose reads 1024 B per row to cover the straddle). So the device sees ~48 random 512-1024 B reads per token regardless of the row's own size — the I/O cost is latency/IOPS-bound, not byte-bound.
- Because the hash needs only the compressed token ids of the last 4 tokens, rows for position t+1 can be requested the instant token t is sampled (or, under speculative decoding, the instant the draft block is produced), which is what every working implementation does ("prefetch", "staging in prepare_inputs").

### Gaps
- The exact per-head hash constants and the compressed-vocabulary map live in the HF reference code (encoding.py / modeling); I did not read them. Not needed for the sizing question.

## Q2. NVMe serving math on Thor: link, IOPS, latency, page-cache behaviour

### Takeaway
Thor's M.2 Key M slot is PCIe Gen5 x4 (root port measured at 32 GT/s x4 locally; the shipped WD SN5000S negotiates Gen4 x4). Measured on this Thor: 48 concurrent 1 KiB O_DIRECT random reads (one token's Engram rows) cost 1.13-1.30 ms p50, 1.35-1.89 ms p95; single-read QD1 latency ~100-130 µs; the drive sustains 62k 4 KiB IOPS at 16 outstanding and 95k at 32, so the 480 IOPS needed at 10 tok/s (4,800 at 100 tok/s) is 1-2 orders of magnitude inside budget. mmap is the wrong primitive on Tegra: a default-madvise fault pulls 64 KiB of page cache per row touched (10 KiB with MADV_RANDOM) and takes 0.8 ms; O_DIRECT reads bypass the page cache entirely, which on unified memory is the only safe option.

### Cited Findings
- Thor developer kit: "M.2 Key M slot with x4 PCIe Gen5 (populated with 1TB NVMe)"; "M.2 Key E slot with x1 PCIe Gen5"; "128 GB 256-bit LPDDR5X, 273 GB/s"; "1x QSFP28 (4x 25GbE)" — [NVIDIA developer blog, Introducing Jetson Thor](https://developer.nvidia.com/blog/introducing-nvidia-jetson-thor-the-ultimate-platform-for-physical-ai/)
- Thor dropped the PCIe expansion slot of earlier AGX kits: "One is the PCIe slot, and another is the 40 pin GPIO header"; NVMe slot "is PCIe Gen 5 compatible" — [JetsonHacks, Jetson AGX Thor review](https://jetsonhacks.com/2025/09/21/nvidia-jetson-agx-thor-the-new-king-of-embedded/)
- Local (this Thor, sysfs): root port `0005:00:00.0` max_link_speed 32.0 GT/s, max_link_width 4; drive `WD PC SN5000S SDEPNSJ-1T00` current_link_speed 16.0 GT/s x4 (Gen4 drive in a Gen5 slot); `logical_block_size` 512; scheduler `none`; `read_ahead_kb` 1024; `transparent_hugepage` = always. — measured 2026-10-17 (no URL; see commands in session)
- Local measurement, O_DIRECT random reads, multi-process (each process QD1), 16 GB safetensors file as target:
  - 4 KiB, 1 proc: 9,106 IOPS, p50 99 µs, p99 579 µs
  - 4 KiB, 16 procs: 62,621 IOPS, p50 130 µs, p99 1,605 µs
  - 4 KiB, 32 procs: 95,498 IOPS, p50 158 µs, p99 1,926 µs
  - 16 KiB, 8 procs: 53,653 IOPS, 879 MB/s, p50 124 µs
  - 512 B / 4 KiB / 16 KiB at QD1 all land at p50 113-130 µs (read size below 16 KiB does not change latency)
  - (4- and 8-process runs showed anomalous p50 of 0.4-1.3 ms; attributed to CPU contention with the co-resident vLLM server; the 16/32-process runs are the clean ceiling)
- Local measurement, the Engram pattern itself (48 random 1 KiB O_DIRECT reads per token, thread pool): 8 threads p50 1.30 ms / p95 1.89 / p99 2.95 ms; 16 threads p50 1.13 / p95 1.35 / p99 2.22 ms; 48 threads p50 1.18 / p95 1.68 / p99 3.09 ms. Serial (one at a time, 48 x 512 B) p50 4.89 ms, p99 6.37 ms.
- Local measurement, mmap sparse touch of the same file: default madvise, 2,000 random 4 KiB pages faulted in 1,627 ms (0.81 ms/fault) and grew the mapping's RSS by 124 MiB = 63.6 KiB of page cache per touch; with MADV_RANDOM, 250 ms (0.125 ms/fault) and 10.4 KiB per touch; MADV_DONTNEED returned RSS to 0.
- Same measurement class on DGX Spark (GB10, NVMe, O_DIRECT, 1 KiB per row): cold gather of 6 / 12 / 24 / 48 rows = 1.07 / 1.13 / 1.22 / 1.89 ms median, p95 1.95 / 1.70 / 1.54 / 2.15 ms; "the read is latency-bound," so page-cache hit rate "barely moves it" (a 25 MiB synthetic table measured 1.12 ms vs 1.13 ms for the real 23.6 GiB shard); rejected alternatives: one task per row, sort-and-merge (random rows rarely share a 512-byte block) — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)
- Why O_DIRECT on unified memory: reads use O_DIRECT "so the reads never occupy the page cache," because "every cached page is memory the model cannot have" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)
- MiaAI-Lab SGLang row store: "one 4 KiB O_DIRECT read per row," 96 miss-servicing threads justified as "NVMe does ~112k IOPS at QD 64"; row cache default 0 GiB "because n-gram rows have ~0% reuse and RAM is GPU memory"; "Never use OFFLOAD_MODE=ram here. The Engram tables would evict the model." — [MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks)
- A page-cache failure mode on GB10 was hit in production: "a rank crash under long prompts traced to GB10 page cache the GPU driver will not evict (fixed; 13-20 GB free per node)"; the recipe lists "page-cache flushing" and "earlyoom tuned to fire before the kernel OOM killer" as root requirements — [aidenle.com](https://aidenle.com/) and [aidenle recipe](https://aidenle.com/recipes/deepseek-v4-1-flash-4x-dgx-spark)
- mmap over-read on GB10 for the analogous Qwen3.8-Flash-Next PLE table: "mmap even when well-behaved is going to cause quite a bit of over-read: likely several kilobytes of wasted reads for every ~100 bytes of useful data"; switching the lazy PLE table to direct reads raised real-text prefill "from about 300 tok/s up to around 750 or 800 tok/s on DGX Spark" — [llama.cpp PR #28136](https://github.com/ggml-org/llama.cpp/pull/28136)
- GPU page-faulting a file-mapped table is pathological: "A cold 30k-token prefill (≈480k rows) took 88 s with GPU faults alone, and 1.6 s when 64 CPU threads fault the step's rows in first" (Qwen4Exp checkpoint-mapped PLE on DGX Spark) — [vLLM PR #58439](https://github.com/vllm-project/vllm/pull/58439)
- Prior local finding on Thor memory accounting: freed CUDA memory sits in the driver page pool and is only released by `echo 3 > drop_caches`; `echo 1` reclaims nothing — [memory note thor-unified-memory-oom.md](/home/patrickd/.claude/projects/-home-patrickd/memory/thor-unified-memory-oom.md) (local, no URL)

### Inferences
- IOPS budget (explicit): decode at 10 tok/s needs 48 x 10 = 480 random reads/s; at 100 tok/s, 4,800/s. Measured ceiling on the installed Gen4 drive is 62-95k IOPS → 0.5-8% utilisation. A Gen5 x4 drive in the slot would raise the ceiling but would not change QD1 latency materially (~70-130 µs class) and so would not change the per-token cost, which is latency-bound.
- Latency budget without any prefetch (explicit): 1.2 ms per token on the critical path at a 100-200 ms step (5-10 tok/s target) = 0.6-1.2%; p99 ~3 ms = 1.5-3%. With the prefetch every recipe implements, the critical-path cost is the residual "late" wait (josephdrose: 0.41 ms when a prefetch is late, ~2% of a 33 ms Spark step; on Thor's slower step this fraction is proportionally smaller).
- Speculative decoding (DFlash-style, K draft tokens verified per step) multiplies rows per step by (K+1): 48 x 9 = 432 reads for K=8. Extrapolation from the measured 95k IOPS ceiling: ~4.5 ms if issued fully concurrently, still well under a 100 ms step, and draft-token hashes are known at draft time so this too can overlap. Not measured.
- Prefill: a P-token prompt needs ≤ 48·P row reads (less after de-duplicating repeated n-grams). Extrapolation: an 8k-token prompt = 384k reads ≈ 4-6 s at 62-95k IOPS, i.e. comparable to or smaller than the prefill compute time Thor would need for that prompt at 500-1,000 tok/s. The Spark Qwen4Exp datapoint (480k rows in 1.6 s with 64 CPU threads) suggests the achievable rate is higher than my serial-process ceiling. This is the one place where a Gen5 drive and more I/O threads pay.
- Page cache on Tegra behaves like stock Linux (measured: fault-around pulls 64 KiB per touch at default madvise, readahead 1024 KiB). It is reclaimable, but on Thor reclaim competes with the CUDA pool and the driver pool is only shrunk by a full `echo 3` pass, so an mmap'd Engram would silently grow "Cached" at ~3 MiB per decoded token (48 x 64 KiB) ≈ 30 MiB/s at 10 tok/s, tens of GiB per hour — exactly the "page cache the GPU driver will not evict" crash the Spark recipes hit. O_DIRECT (or at minimum MADV_RANDOM + periodic MADV_DONTNEED/`posix_fadvise(DONTNEED)`) is required, and a cgroup `memory.high` on the server is a cheap belt-and-braces cap.
- Disk capacity is a practical blocker today: this Thor's 1 TB NVMe has 51 GB free (838 GB used). Engram needs 97 GiB (MXFP4) or 189 GiB (FP8) of local NVMe in addition to the ~117 GiB backbone checkpoint; either a larger drive or deleting ~250 GB of existing models is required.

### Gaps
- No published fio numbers for the Thor M.2 slot were found on the NVIDIA forums or JetsonHacks (searches returned only Orin/Nano threads and a Thor "fio write fail" thread with a DRAM-less WD SN350). The local measurements above stand in for them; they are O_DIRECT psync-style reads from Python, not fio/io_uring, and were taken beside a running vLLM server, so the true ceiling is somewhat higher.
- I did not measure a Gen5 x4 drive in the slot. The forum advises a PCIe 4.0 990 Pro because the dev-kit heatsink does not fit drives with their own heatsink ([forum thread](https://forums.developer.nvidia.com/t/does-jetson-thor-dev-kit-support-samsung-ssd-9100-pro-8tb-and-will-it-work-with-included-heatsink/348094/2)).
- Whether Tegra's nvmap/driver pool interacts with page cache differently from GB10 was not found documented; the local measurement shows ordinary page-cache behaviour for file mappings, and the prior memory note shows the driver pool needs `echo 3`. Treat GB10's "page cache the GPU driver will not evict" as the expected failure mode on Thor too.

## Q3. Existing off-device Engram implementations (and which ones transfer to unified memory)

### Takeaway
There are two families. (a) Discrete-GPU + big host RAM: vLLM `cpu_offload` (pinned host + UVA, PR #56512), vLLM `disk_offload_dir` (mmap'd shards as clean page cache, PR #56757, measured only on a 1.6 TB-RAM host), SGLang `SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE`; these do nothing or actively harm on unified memory ("a 4 GiB pinned allocation cost 4.09 GiB of GPU-visible memory"). (b) Unified-memory (DGX Spark GB10) recipes that keep Engram on local NVMe and gather rows with O_DIRECT pread + prefetch: tonyd2wild/Kai vLLM patch, josephdrose joe-spark-patches (vLLM), MiaAI-Lab SGLang "Engram row store", MiaAI EXL3 2x-Spark (file-backed ParallelEngramEmbedding), exllamav3 PR #449 RowTable (reads FP8 rows from the base shards); llama.cpp PR #28696 (open) instead quantizes Engram into the GGUF and pins it to CPU with mmap (2.8 tok/s on Spark). Family (b) is the one that transfers to Thor.

### Cited Findings
- vLLM pinned-host/UVA mechanism and its non-transfer: "CUDA moves them to pinned host memory and reads them over UVA (#56512)"; "DeepSeek-V4.1-Flash's Engram n-gram tables are the largest single consumer of device memory — 47.2 GiB per rank at TP=4" — [vLLM PR #57491](https://github.com/vllm-project/vllm/pull/57491); vLLM recipe: tables "move to pinned host DRAM and are read through UVA, so the output is unchanged" via `--engram-config '{"cpu_offload":true}'`; on DGX Station GB300, "both Engram tables (189 GiB) plus 60 GiB of routed experts sit in pinned host memory" — [vLLM recipe DeepSeek-V4.1-Flash](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)
- Measured on GB10 (unified): "On GB10 the CPU and the GPU share one physical pool. Pinned host memory is the same DRAM the GPU allocates from. ... A 4 GiB pinned allocation cost 4.09 GiB of GPU-visible memory. The mechanism works. It frees zero bytes."; `EngramConfig.cpu_offload=True` "frees zero bytes on a unified pool" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)

- llama.cpp: PR #28696 (open, opened 2026-09-10) adds `deepseek41` with Engram tensors inside the GGUF ("ENGRAM_EMBD, ENGRAM_Q, ENGRAM_K, ENGRAM_WKV"); at Q8_0 the two tables are 99,611 + 99,614 MiB (~195 GiB, 41% of the 473 GiB file), at Q3_K 40,284 + 40,285 MiB (~78.7 GiB); "The tables want to be host resident rather than treated as ordinary weights"; Spark serve line `-lm mmap -ngl 99 -cmoe -ot "engram_embd.weight=CPU"`; Q2_K on GB10 runs "at 2.8 tok/s with GPU offload and 2.3 without"; the author estimates "about 0.1 ms per token for the 48 engram row reads on NVMe" (arithmetic, not measured); on-demand row reads via `TENSOR_READ_LAZY` are proposed but unimplemented — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696). llama.cpp did merge the analogous "qwen4exp: direct reads for the lazy PLE table" — [PR #28136](https://github.com/ggml-org/llama.cpp/pull/28136)
- SemiAnalysis tested mmap-on-NVMe in a vLLM fork on B200 (discrete class): "copies row IDs to the CPU, deduplicates them, gathers rows into pinned buffers, copies them back to the GPU"; "we were unable to turn on GDS"; "DRAM delivers 121 million total tokens per dollar versus 52 million for SSD" at ~125 tok/s/user; SSD "likely not worth the tradeoff" for production on B200 because it does not reduce the server's cost — [SemiAnalysis](https://newsletter.semianalysis.com/p/engrams-embedding-entendre-codesign) (paywalled; visible portion)
- Original Engram paper offload experiment (H800 + host DRAM, nano-vLLM, 100B table in a Dense-4B/8B): 9,031.62 → 8,858.28 tok/s (-1.9%) and 6,315.52 → 6,140.02 tok/s (-2.8%); described as "a conservative baseline" since every lookup crosses PCIe — [arXiv 2601.07372 §6.4](https://arxiv.org/html/2601.07372)

### Inferences
- The thing to port to Thor is josephdrose's or MiaAI's single-rank variant: an O_DIRECT row store with a packed `[rows, 264]` (or `[rows, 136]` at MXFP4) file, a thread pool that issues the 48 reads for the next position as soon as its token ids are known, and a pinned staging slot the lookup kernel dequantizes from. On Thor there is no TP, so all 24 heads x 2 layers are local (48 reads/token, not 12), which is the 48-row line of josephdrose's table (1.89 ms on Spark; 1.13-1.30 ms measured here).
- The vLLM upstream `disk_offload_dir` path (mmap, "clean page cache") is explicitly designed around a large host page cache and is the wrong fit for Thor for the page-cache reasons in Q2; the `checkpoint_mapped` approach of PR #58439 (Qwen4Exp) is the upstream pattern closest to what Thor needs, and it is not yet extended to DeepSeek-V4.1 ("for architectures without this backend (DeepSeek ...").
- The SemiAnalysis "SSD not worth it" verdict does not transfer: it is a tokens-per-dollar argument on a B200 server where SSD saves no hardware; on Thor, SSD is the only tier that exists.

### Gaps
- No report of DeepSeek-V4.1-Flash on a Jetson Thor (or any single 128 GB unified box) was found; the closest is llama.cpp Q2_K on one DGX Spark at 2.8 tok/s with Engram on CPU, and the modemguides reality-check which says a lone 128 GB machine "still cannot hold the model" and lists "ds4 Q2 with weights streamed from SSD" as experimental with no published speed ([modemguides](https://www.modemguides.com/blogs/ai-infrastructure/run-deepseek-v4-1-flash-locally-hardware-reality-check)). Thor is not mentioned anywhere.
- No implementation uses GPUDirect Storage for Engram (SemiAnalysis could not enable GDS; Spark recipes gather on CPU). Whether Tegra supports GDS/cuFile is not established here; it is not needed given CPU gather costs ~1 ms.

## Q4. Engram size reduction that is allowed: quantization and sub-tables

### Takeaway
MXFP4 Engram (97.3 GiB, 136 B/row) is a released, benchmarked format: NVIDIA's NVFP4 card reports it as lossy ("about 12% relative L2 error on the table") yet within noise on six benchmarks, and vLLM PR #61530 measures GSM8K 0.967 vs 0.966 against FP8. Nothing below 4 bits has a public result. Row-level sub-tables are not supported by any implementation and the evidence on reuse is negative for decode ("~0% reuse", "cache hit rate barely moves it"), so a hot-row resident subset should be treated as untested rather than promising.

### Cited Findings
- NVIDIA NVFP4 checkpoint: Engram tables "converted from the source FP8 to MXFP4: E2M1 values packed two per byte, with one UE8M0 scale per 32 elements"; "Unlike the expert conversion, this step is lossy (about 12% relative L2 error on the table)"; host footprint "12.2 GiB per rank at TP=4 instead of 23.6 GiB"; checkpoint "approximately 400 GiB" with MXFP4 Engram vs 492 GiB; benchmarks (MXFP4 source → NVFP4+MXFP4 Engram): GPQA Diamond 91.035 → 90.783, AA-LCR 78.563 → 79.562, SciCode 54.401 → 53.994, IFBench 76.667 → 77.867, MMMU-Pro 74.046 → 74.566, Terminal-Bench 2.1 81.60 → 81.88; needs vLLM PR #61530; "not supported in SGLang yet" — [nvidia/DeepSeek-V4.1-Flash-NVFP4 model card](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4)
- vLLM PR #61530: "The packed table halves the host memory: 12.16 GiB per rank vs 23.60 GiB for FP8"; GSM8K 5-shot on GB300 TP4: FP8 0.966 vs MXFP4-packed 0.967 ("A 0.001 accuracy gap is within noise (about ±0.5 points standard error)"); caveat: "the accuracy comparison is not isolated to the Engram table" — [vLLM PR #61530](https://github.com/vllm-project/vllm/pull/61530) (open)
- A community NVFP4-Engram variant exists: "aidendle94/DeepSeek-V4.1-Flash-NVFP4-Engram (418 GB, tables quantized to NVFP4)" — [aidenle recipe](https://aidenle.com/recipes/deepseek-v4-1-flash-4x-dgx-spark)
- llama.cpp's converter quantizes Engram to the GGUF rung (Q8_0 ~195 GiB, Q3_K ~78.7 GiB for both tables); "Q1_0 is unusable on this model"; "Q2_K is the first usable rung" (coherent at 2.8 tok/s) — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696). No perplexity/benchmark for the Q3_K Engram is given.
- Zipfian access: "a small fraction of patterns accounts for the vast majority of memory accesses"; the paper proposes to "exploit Zipfian locality to cache frequent items in HBM" with the full table in host DRAM and rare entries on "NVMe SSD" — a design proposal, not an experiment; no hot-row fraction is reported — [arXiv 2601.07372](https://arxiv.org/html/2601.07372)
- Decode-time reuse measured as negligible: row cache default `DSV41_CACHE_GIB=0` "because n-gram rows have ~0% reuse and RAM is GPU memory" — [MiaAI-Lab README](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks); a 25 MiB synthetic table (100% cache-resident) read at 1.12 ms vs 1.13 ms for the real shard, so hit rate "barely moves it" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md)
- Prefill-time reuse is real for repetitive text only: filler-text prefill rates "sit on a hot Engram row" while unique text runs 4.9-5.0k tok/s at TP4 — [MiaAI-Lab README](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks); the same effect on Qwen4Exp: a repeated-token benchmark "used ... very little PLE data" and looked 2x faster than real text — [llama.cpp PR #28136](https://github.com/ggml-org/llama.cpp/pull/28136)
- Row pruning conflicts with addressing: rows are addressed by hash mod a per-head prime, with the 8 head rows of one n-gram "at independent positions in 8 disjoint ranges" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); the Helix explainer notes "Quantizing Engram alone from FP8 to FP4 would save roughly 98 GB" but has "not run or benchmarked this model" — [Helix](https://helix.ml/blog/deepseek-v41-flash-explained)

### Inferences
- The smallest Engram with public quality evidence is MXFP4: 97.3 GiB on disk, 6.4 KiB/token read. Since the disk path is latency-bound (Q2), the byte saving buys nothing at decode; its value is halving NVMe capacity and halving prefill bytes. The task brief's internal results (MXFP4 cosine 0.9934; 6-bit indistinguishable; 4-bit +7.3% free-running loss; INT4-g32 GSM8K within noise) are consistent with NVIDIA's "lossy but within benchmark noise" characterisation.
- A hot-row cache is a prefill feature at best: decode reads 48 fresh random rows per token with ~0% short-horizon reuse, and the only published Zipf statement is about corpus-level n-gram frequency, which maps to "a resident subset would serve a large share of lookups" only if the resident subset is chosen by corpus frequency, not LRU. Nobody has published that experiment or the miss→zero quality cost; because a miss produces a zero embedding that the gate then mixes in, the degradation mode is silent. Mark untested.
- The vLLM fast path for NVFP4-Engram is not merged (#61530 open) and SGLang lacks it; a Thor server would carry its own dequant, which is trivial (48 rows x 256 ch).

### Gaps
- No publication quantifies Engram below 4 bits, nor the quality of llama.cpp's Q3_K/Q2_K Engram in isolation.
- No publication measures a frequency-selected resident subset with zero-fill misses. The parent's "not row-prunable" note is correct for static pruning (the hash still lands on the dropped row), but a frequency-ranked cache with miss→zero is a separate, untested question.

## Q5. Latency hiding: prefetch during the current forward

### Takeaway
Yes, in every working path: DeepSeek's own serving prefetches from host over RDMA overlapping block 0; vLLM's CUDA offload (#56512) prefetches; the Spark vLLM patches issue the reads in `prepare_inputs` (before the forward, needed anyway because a disk read cannot sit inside a CUDA graph); MiaAI's SGLang row store runs lookups on a side stream (-2.3 to -2.9 ms/step); josephdrose's 600 s load test logged zero misses with late arrivals costing 0.41 ms. On Thor's 100-200 ms step, a 1.2 ms read is hidden with margin to spare.

### Cited Findings
- "deterministic addressing enables embeddings to be prefetched from host memory via background RDMA transfers, with prefetching for the first module overlapping computation in the first Transformer block" — [arXiv 2609.19969 §2.4.2](https://arxiv.org/pdf/2609.19969)
- "indices for the next Engram lookup are fixed once the token sequence is known"; "the system prefetches embeddings for the Engram layer asynchronously, overlapping the PCIe transfer ... with the computation of the first block" — [arXiv 2601.07372 §6.4](https://arxiv.org/html/2601.07372)
- vLLM: "Engram prefetch and DP sharding merged in #56512"; in the disk PR, "The row gather overlapped against the decoder layers" (14,163 vs 14,330 tok/s) — [vLLM PR #56757](https://github.com/vllm-project/vllm/pull/56757)
- josephdrose: `Engram.prefetch(hash_ids)` issued from `prepare_inputs`; load test ready 79.6-82.7%, late 17-20%, missed 0; "A late arrival costs its 0.41 ms wait, about 2% of a step" — [fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); "zero prefetch misses" over 27,700 steps — [forum](https://forums.developer.nvidia.com/t/deepseek-v4-1-flash/382725)
- MiaAI: "Engram row lookups on a side stream, -2.3 to -2.9 ms/step; needs packed shards"; for prefill "the Engram rows of the whole prompt are fetched before the first chunk runs" — [MiaAI-Lab README](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks)
- tonyd2wild: lookup "moves out of the forward into prepare_inputs ... with all rows read in parallel"; staging "2-3 ms with local rows" — [tonyd2wild README](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark)
- Host-side prefetch is also what rescues file-mapped GPU access (88 s → 1.6 s for 480k rows) — [vLLM PR #58439](https://github.com/vllm-project/vllm/pull/58439)

### Inferences
- On a single-rank Thor server the natural schedule is: sample token t → compute the 48 hashes for position t+1 on CPU (microseconds) → submit 48 O_DIRECT reads to a thread pool → run the embedding + layer 0 for t+1 → join on the 24 rows for layer 1 (typically already back after ~1.2 ms) → continue; layer 14's 24 rows have ~13 layers of slack. Expected critical-path residue: the p99 tail (~3 ms measured) minus layer-0 time, i.e. ≤1-2% at 10 tok/s, ~0 in the median. Extrapolated from the measured distributions, not from a running server.
- With a DFlash/MTP draft, the hashes for all K draft positions are known at once; issuing 48(K+1) reads concurrently keeps the gather ~4-5 ms at K=8 (extrapolated from 95k IOPS), still fully hideable behind the verify step.

### Gaps
- No Thor end-to-end run exists; the hiding margin above is derived from Spark measurements plus local I/O measurements.

## Q6. Thor-specific memory tiers and alternative lookup tiers

### Takeaway
Thor exposes no memory outside the 122 GiB LPDDR5X pool; the only attachment points are one M.2 Key M PCIe Gen5 x4 (the NVMe), one M.2 Key E Gen5 x1 (Wi-Fi), QSFP28 4x25GbE, 5GbE and USB 3.2 Gen2. A second NVMe would have to use the Key E x1 lane or USB; a remote-DRAM tier over the QSFP28 ports is what DeepSeek's own "RDMA from host memory" implies, but nobody has done it from a Jetson, and the local NVMe already meets the budget with 50-100x margin, so none of these is needed.

### Cited Findings
- Thor interfaces: "128 GB 256-bit LPDDR5X, 273 GB/s"; "M.2 Key M slot with x4 PCIe Gen5"; "M.2 Key E slot with x1 PCIe Gen5"; "1x QSFP28 (4x 25GbE)"; "1x 5GBe RJ45"; "2x USB Type-A 3.2 Gen2"; "2x USB Type-C 3.1 Gen1" — [NVIDIA developer blog](https://developer.nvidia.com/blog/introducing-nvidia-jetson-thor-the-ultimate-platform-for-physical-ai/); no PCIe expansion slot — [JetsonHacks](https://jetsonhacks.com/2025/09/21/nvidia-jetson-agx-thor-the-new-king-of-embedded/)
- Local: `free -g` total 122 GiB; the root port behind the NVMe is `0005:00:00.0` at 32 GT/s x4 — measured 2026-10-17
- The Spark cluster recipes serve Engram rows over NFS as the fallback tier when local copies are absent, at 5.9-7.8 ms/step vs 2.8 ms local — [tonyd2wild README](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark); MiaAI's EXL3 recipe: misses "to local O_DIRECT instead of NFS — worth 25-50 % of prefill" — [MiaAI EXL3 README](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-EXL3-2x-DGX-Sparks)
- vLLM has an open "Mooncake-backed DeepSeek V4.1 tables" PR (#57023), i.e. a network KV/row store tier — [GitHub search](https://api.github.com/search/issues?q=engram+repo:vllm-project/vllm+is:pr)

### Inferences
- A second Gen4/Gen5 NVMe via a Key E (x1) adapter would give ~2-4 GB/s and the same ~100 µs QD1 latency class — adequate for Engram on its own, but it only matters if the primary drive's capacity (not its IOPS) is the constraint. A USB 3.2 Gen2 enclosure adds UAS latency (hundreds of µs) and is still within budget for 480-4,800 IOPS, but untested here.
- Remote DRAM over 25GbE NFS: Spark data (5.9-7.8 ms/step over NFS) says a network tier costs ~5x local NVMe per step, still ≤8% of a 100 ms Thor step; not worth the second machine.

### Gaps
- Whether Thor's QSFP28 NIC supports RoCE/RDMA (needed for the paper's "background RDMA" tier) was not established.
- No measured numbers for a Key E x1 NVMe adapter or a USB NVMe enclosure on Thor.

## Q7. Worst case: Engram resident — what is left for experts

### Takeaway
Confirmed infeasible. Engram resident at MXFP4 is 97.3 GiB; in a 117 GiB envelope that leaves 19.7 GiB, of which ~18 GiB is the fixed non-expert backbone, so ≤~2 GiB would remain for ~99 GiB of REAP-50 ~3 bpw experts and all KV/activations. Even a hypothetical 2-bit Engram (~50 GiB, no public quality evidence) would leave ~49 GiB for experts, half of what is needed. V4.1-Flash on Thor requires Engram off-pool.

### Cited Findings
- Engram sizes: FP8 "189.13 GiB" of a "475.25 GiB" checkpoint; "Backbone without Engram 286.12 GiB" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); MXFP4 halves it ("12.16 GiB per rank vs 23.60 GiB" at TP=4, i.e. 48.6 vs 94.4 GiB per table-pair-quarter → ~97 GiB total) — [vLLM PR #61530](https://github.com/vllm-project/vllm/pull/61530); llama.cpp Q3_K Engram ~78.7 GiB — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696)
- The same conclusion on the 128 GB Spark: "No such quantization exists" for a 2-bit Engram that would fit (83.4 GiB) beside the backbone; pinned host offload "frees zero bytes" — [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); MiaAI: with Engram on NVMe the GPU-resident set is "~305 GiB of MXFP4 experts plus FP8 dense weights," needing 3-4 Sparks — [MiaAI-Lab README](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks)
- A single 128 GB machine with the unmodified expert set cannot hold V4.1-Flash even with Engram on SSD: "A lone 128GB machine still cannot hold the model"; "Working runtimes keep those 189 GiB of lookup memory on NVMe" — [modemguides reality check](https://www.modemguides.com/blogs/ai-infrastructure/run-deepseek-v4-1-flash-locally-hardware-reality-check)
- Thor envelope inputs (from the task brief, unsourced here): 117 GiB usable, ~18 GiB fixed non-expert weights, ~99 GiB experts at REAP-50 + ~3 bpw.

### Inferences
- Arithmetic (explicit): 117 − 97.3 (MXFP4 Engram) = 19.7 GiB; − 18 fixed = 1.7 GiB for experts + KV + activations + CUDA context → infeasible by ~97 GiB. At FP8 Engram the deficit is ~189 GiB. At llama.cpp's Q3_K Engram (78.7 GiB): 117 − 78.7 − 18 = 20.3 GiB → still infeasible.
- With Engram off-pool the envelope is 18 + 99 = 117 GiB exactly, leaving nothing for KV, activations, pinned staging or the I/O threads' buffers; the Engram server itself needs only tens of MiB (48 x 1 KiB staging x a few slots, plus thread stacks) but zero page cache tolerance, which is why O_DIRECT is mandatory and why `vm` reclaim guards (cgroup `memory.high`, earlyoom, periodic `echo 3 > drop_caches`) belong in the recipe. The experts/fixed sizing itself is outside this note's scope; the Engram-side verdict is that it adds ~0 GiB to the resident set and ~1 ms (hidden) per token.
- Practical gate before any Thor attempt: NVMe capacity — this Thor has 51 GB free of 936 GB; a 97-189 GiB Engram file plus the backbone checkpoint needs ~250-400 GB freed or a larger drive.

### Gaps
- No public 2-bit or 3-bit Engram quality measurement exists, so "resident at ≤3 bpw" cannot be argued even in principle; and even if it existed the arithmetic above still fails.
