# Adapting REAP/HOPE expert pruning and its calibration pass to DeepSeek-V4.1-Flash-1017: the delta from the GLM-5.3-Flash pipeline

Scope: implementation-level delta list between the LOCAL GLM-5.3-Flash REAP/HOPE pipeline (`~/glm-5.3-reap/scripts/stages/s03_saliency.py`, `~/glm-5.3-reap/scripts/stream_saliency.py`) and what `deepseek-ai/DeepSeek-V4.1-Flash-1017` needs. Written 2026-10-17. Everything marked LOCAL was read from this machine; everything marked (inference) is my reasoning, not a sourced fact.

**Headline correction to the task premise.** The brief describes GLM-5.3-Flash as "single residual". It is not: the LOCAL pipeline already runs on a 4-stream mHC model (`tcfg.hc_mult` = 4, `hc_sinkhorn_iters` = 20, `Glm5NextTextHyperConnection`), and the saliency hook is already placed inside the collapsed single-stream MoE module. The hyper-connection delta for V4.1 is therefore close to zero for the *criterion*; the real deltas are (a) no HF `transformers` implementation of `deepseek_v41` exists, so calibration must run on the checkpoint's own `inference/model.py`; (b) cross-layer attention state (shared compressed KV, index keys, top-k indices, candidate pool) that the GLM "one tensor + topk_indices" streaming assumption does not cover; (c) Engram lookups at layers 1 and 14 that need the 189 GiB tables readable during calibration; (d) MXFP4 packed expert tensors and a second (vision) router bias to slice; (e) vLLM's fused router accepting only a fixed table of expert counts, which pins the legal prune points at 320/256/192/128.

## Q1. Saliency under hyper-connections: which stream carries the expert output, is REAP well-defined, and what did REAP/HOPE or anyone do for mHC models?

### Takeaway
In both GLM-5.3-Flash and V4.1 the MoE sees a single collapsed stream (A·X, "pre" mix) and writes one output back scaled by a per-token 4-vector C ("post"); because C is shared by every expert of that token, the within-layer expert ranking is invariant to it and REAP's `S_j = mean_t g_j ||f_j||` captured at the expert output is exactly as well-defined as on a single-residual model. The LOCAL hook is already at that point, and the only published mHC prunes (0xSero on V4-Flash-0731, LibertAI on V4.1-Flash-0909) did the same thing without any hyper-connection-specific adjustment; no paper treats mHC in a pruning criterion.

### Cited Findings
- V4.1 residual update (Single-Pass mHC, Eq. 6): `X_{l+1} = B_l X_l + C_l F_l(A_{l-1} X_l)`, n = 4 streams, `(A_l, B_l, C_l) = H(X_l)`; the only change vs original mHC is that input mixing uses the previous block's coefficients `A_{l-1}` so no reduction over `X_l` is needed before mixing ("negligible performance degradation"); a Mega-mHC kernel fuses residual update, input mixing and coefficient prediction, cutting activation traffic from `(3n+2)d` to `(2n+2)d` — [DeepSeek-V4.1-Flash paper, arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- Original mHC coefficient prediction (DeepSeek-V4 report): `X̂_l = RMSNorm(vec(X_l))`; `Ã_l = α^pre (X̂_l W^pre) + S^pre`, `B̃_l = α^res Mat(X̂_l W^res) + S^res`, `C̃_l = α^post (X̂_l W^post)^T + S^post`; constraints `A_l = σ(Ã_l)`, `C_l = 2σ(C̃_l)`, `M^(0) = exp(B̃_l)` then alternating column/row normalisation with `t_max = 20`; W^pre/W^post map to n_hc, W^res to n_hc² — [DeepSeek-V4 report, arXiv 2606.19348](https://arxiv.org/html/2606.19348)
- The 1017 checkpoint's reference `Block.forward` order: `attn_pre, attn_post, attn_comb = self.hc_mixes(x, self.hc_attn_fn, ...)` from the current stream; attention input `x = self.hc_pre(x, pre_mix)` where `pre_mix` is the **previous block's `ffn_pre`** (the lag); `hc_post(x, residual, attn_post, attn_comb)`; then `ffn_pre, ffn_post, ffn_comb = self.hc_mixes(x, self.hc_ffn_fn, ...)` on the post-attention stream; FFN input `x = self.hc_pre(x, attn_pre)` (this block's own attn_pre); `self.ffn(x, image_mask)`; `hc_post(x, residual, ffn_post, ffn_comb)`; `return x, ffn_pre`. Mix width `mix_hc = (2 + hc_mult) * hc_mult` = 24; the flattened 4×d vector is RMS-normalised with `norm_eps`; `hc_split_sinkhorn(mixes, hc_scale, hc_base, hc_mult, hc_sinkhorn_iters, hc_eps)` returns pre/post/comb — [DeepSeek-V4.1-Flash-1017 inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/main/inference/model.py)
- Config: `hc_mult: 4`, `hc_sinkhorn_iters: 20`, `hc_eps: 1e-06` — [DeepSeek-V4.1-Flash config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)
- GLM-5.3-Flash is ALSO an mHC model: LOCAL `mhc_reference.py` reimplements `Glm5NextTextHyperConnection` with `pre = sigmoid(...)+eps`, `post = 2*sigmoid(...)` ("range [0,2], NOT a probability"), `comb = softmax(...)+eps` then column-first Sinkhorn for `hc_sinkhorn_iters = 20`, and `apply_site = post ⊗ y + comb^T @ streams` — [LOCAL mhc_reference.py](file:///home/patrickd/glm-5.3-reap/scripts/mhc_reference.py)
- LOCAL s03 docstring: "Glm5NextTextModel.forward carries its entire inter-layer state in a single tensor plus topk_indices - mHC's four residual streams live in the hc_mult axis and are manipulated inside each decoder layer, so there is no cross-layer bookkeeping to replicate"; states are prepared as `ie.unsqueeze(2).expand(-1, -1, tcfg.hc_mult, -1)` — [LOCAL s03_saliency.py](file:///home/patrickd/glm-5.3-reap/scripts/stages/s03_saliency.py)
- LOCAL hook point: `patch_experts_for_saliency` replaces `Glm5NextTextExperts.forward`; `f_j = F.linear(cur, self.down_proj[expert_idx])  # expert output, ungated`, `g_j = top_k_weights[token_idx, top_k_pos]`, `s = g*||f||`; it asserts the MLP sees `[B, S, H]` because "mHC's hc_mult axis is consumed inside the decoder layer before the MLP" and refuses to guess a broadcast otherwise; accumulators `sum, sq, nrm, nsq, gat, gsq, cnt, hist, osum` plus the HOPE F-matrix via `fa.update(0, top_k_index[valid], S_buf[valid])` — [LOCAL stream_saliency.py](file:///home/patrickd/glm-5.3-reap/scripts/stream_saliency.py)
- REAP's reference observer hooks the **MoE block** (configs name `"DeepseekV2MoE"`, `"Glm4MoeMoE"`, `"Qwen3MoeSparseMoeBlock"`), recomputes every expert on the flattened block input (`activations[idx] = expert(flat_input)`), stores **unweighted** expert outputs and takes top-k from `router_logits`; `renormalize_router_weights` defaults to False — [CerebrasResearch/reap observer.py](https://raw.githubusercontent.com/CerebrasResearch/reap/main/src/reap/observer.py)
- REAP repo supported families: DeepSeek-V3.2 (planned), GLM-4.5-Air/4.6, Qwen3, Mixtral, Llama-4-Scout, ERNIE, Kimi-K2, Kimi-Linear, MiniMax-M2; no V4/V4.1, no mention of hyper-connections or Engram; registration via `MODEL_ATTRS` in `src/reap/model_util.py` — [CerebrasResearch/reap](https://github.com/CerebrasResearch/reap)
- 0xSero's V4-Flash-0731 REAP K160 "preserves top-6 routing, shared experts, attention, embeddings, output head, mHC, compressor, and indexer tensors"; rankings were transferred from an earlier observation run; it does not describe any mHC-specific saliency treatment — [0xSero/DeepSeek-V4-Flash-0731-REAP](https://huggingface.co/0xSero/DeepSeek-V4-Flash-0731-REAP)
- LibertAI's V4.1 REAP card defines saliency as "the mean router-weighted activation norm over the calibration set" and does not mention hyper-connections — [LibertAIDAI/DeepSeek-V4.1-Flash-REAP-256E](https://huggingface.co/LibertAIDAI/DeepSeek-V4.1-Flash-REAP-256E); [Libertai/deepseek-v41-flash-reap](https://github.com/Libertai/deepseek-v41-flash-reap)
- HOPE's F-matrix is built from the same per-token `g_i||f_i|| · g_j||f_j||` products the REAP hook already computes; the off-diagonal is the only statistic not recoverable offline — [LOCAL memory hope-supersedes-reap](file:///home/patrickd/.claude/projects/-home-patrickd/memory/hope-supersedes-reap.md)

### Inferences
- (inference) Where the expert output lands: the MoE output `y = Σ_j g_j f_j + f_shared` is a single d-vector; `hc_post` writes `C_l(t) ⊗ y` into all 4 streams (one scalar per stream, `2σ(·)` in [0,2]) and mixes the old streams with the doubly-stochastic `B_l`. Every expert of token t is scaled by the same 4-vector, so `argmin_j S_j` within a layer does not change if `||C_l(t)||` is folded in — it would only re-weight *tokens*. REAP's criterion is well-defined without modification; this is exactly why the GLM pipeline (same structure) needed no adjustment.
- (inference) The one cheap, optional addition is a `post`-weighted accumulator: `s'_t = ||C_l(t)||_2 · g_j(t) ||f_j(t)||` (4 extra floats per token, already computed by `hc_mixes`). It measures what reaches the residual rather than what leaves the expert, and matters only if the model systematically "turns down" the MoE on some token classes. Bank it alongside `sum/sq`; do not make it the default (no evidence either way, and it would break comparability with the published REAP numbers).
- (inference) Hooking level: hook *inside the Experts module after `hc_pre`*, as LOCAL does, not at the block output. The reference `Block` collapses to one stream before `ffn_norm`, so the expert input is already `[tokens, 5120]` and the LOCAL `valid`-mask 1:1 assertion will hold. The reference code has no `Glm5NextTextExperts` equivalent; the patch target becomes the `MoE.forward` / expert loop in `inference/model.py` (fp4 `linear()` path), which is a rewrite of `patch_experts_for_saliency`, not a port.
- (inference) The Single-Pass lag changes *what state crosses the layer boundary*: V4.1 passes `(x [b,s,4,d], ffn_pre [b,s,4] fp32)`; GLM passes `(x, topk_indices)`. The LOCAL `states[...]["topk"]` slot must become a `pre_mix` slot (and layer 0 needs the model's initial `pre_mix` convention). This is bookkeeping, not a criterion change.
- (inference) HOPE needs no mHC change either: F is accumulated from `S_buf` (`[rows, K]`) after the expert loop; only `K` (8→6) and `num_experts` (288→384) change (F per layer = 384² fp32 = 576 KiB; 40 layers = 22.5 MiB).

### Gaps
- No paper (REAP, HOPE, the unified-criterion family of arXiv 2606.15716, or any 2026 pruning paper found) analyses saliency under hyper-connections; the two published mHC prunes are silent on it. The "post-weighted" variant above is untested anywhere.
- The reference `kernel.py` (sigmoid / 2·sigmoid / exp+Sinkhorn) was not fetched; the V4.1 `hc_split_sinkhorn` is assumed to match the V4 report formulation quoted above (LOCAL `mhc_reference.py` matches GLM's, which uses softmax rather than exp before Sinkhorn — a minor difference to verify bit-for-bit before trusting a torch fallback).

## Q2. `sqrtsoftplus` + `noaux_tc` top-6: gate weights vs selection bias, renormalisation after pruning, bias re-fit

### Takeaway
V4.1's gate is `scores = sqrt(softplus(xW/gate_temp))`; the bias (`gate.bias`, or `gate.bias_vl` for image-span tokens) enters **only** the top-k selection, the weights are the unbiased scores renormalised to sum 1 (`norm_topk_prob: true`) and multiplied by `routed_scaling_factor 1.5`. This is the same two-tensor structure as the LOCAL `noaux_tc` note, so slicing is row-selection on `gate.weight`, `gate.bias` and `gate.bias_vl`; post-prune renormalisation is automatic (top-6 is always filled), and any bias re-fit must be a load-balancing update, not gradient descent, because the bias has zero gradient.

### Cited Findings
- Config: `n_routed_experts 384`, `n_shared_experts 1`, `num_experts_per_tok 6`, `moe_intermediate_size 2304`, `scoring_func sqrtsoftplus`, `topk_method noaux_tc`, `norm_topk_prob true`, `routed_scaling_factor 1.5`, `n_group`/`topk_group` absent, `first_k_dense_replace` absent, `swiglu_limit 10.0` — [config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)
- Reference gate: `scores = linear(x.float(), self.weight.float()) / self.gate_temp`; `sqrtsoftplus` = `F.softplus(scores).sqrt()`; `indices = (scores + bias).topk(self.topk, dim=-1)[1]` (bias affects selection only); `weights = scores.gather(1, indices)` (unbiased); `bias_vl` replaces `bias` for image-span tokens when vision is enabled; `weights /= weights.sum(...) + 1e-20` only if `norm_topk_prob and topk > 1`; `weights *= self.route_scale`; no group routing and no hash/`tid2eid` routing in this file — [inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/main/inference/model.py)
- vLLM's compiled kernel does the same: `val = val + row_bias[expert_idx]` before top-k, then `max_val -= row_bias[expert]` on output; `bias_vl` replaces `correction_bias` for image-sentinel rows; `denom = selected_sum > 0 ? selected_sum : 1; scale /= denom`; `routed_scaling_factor` multiplied in; the DSv4 fast path runs only for `topk == 6` — [vLLM csrc/moe/topk_softplus_sqrt_kernels.cu](https://raw.githubusercontent.com/vllm-project/vllm/main/csrc/moe/topk_softplus_sqrt_kernels.cu)
- V4 report: "we change the activation function that computes the affinity scores from Sigmoid(·) into Sqrt(Softplus(·))"; V4.1 paper: aux-loss-free balancing with "separate per-expert correction biases for image and text tokens", bias update speed 0.001, plus a sequence-level balance loss with weight 0.0001 — [arXiv 2606.19348](https://arxiv.org/html/2606.19348); [arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- LibertAI sliced "128 experts per layer, along with their rows in `gate.weight`, `gate.bias`, and `gate.bias_vl`"; the two biases have correlation −0.05 — [LibertAI REAP-256E card](https://huggingface.co/LibertAIDAI/DeepSeek-V4.1-Flash-REAP-256E)
- LOCAL noaux_tc note: the bias "has exactly zero gradient under straight-through topk, because it enters only through the selection"; folding the bias into the weights gave 0.125 selection agreement on real weights — [LOCAL memory noaux-tc-router-formula](file:///home/patrickd/.claude/projects/-home-patrickd/memory/noaux-tc-router-formula.md)
- LOCAL router cache: `patch_router_for_cache` stores per-token scores so "post-prune routing (selection AND the renormalised gate) becomes exactly replayable for any candidate keep-set" — [LOCAL stream_saliency.py](file:///home/patrickd/glm-5.3-reap/scripts/stream_saliency.py)
- Upstream REAP's 2026-03-11 fix renormalises top-k router logits to sum to 1 before use as weights (mean accuracy drop 1.9% vs 2.6%) — [LOCAL memory reap-logit-renorm-fix](file:///home/patrickd/.claude/projects/-home-patrickd/memory/reap-logit-renorm-fix.md)

### Inferences
- (inference) Delta vs GLM: `patch_router_for_cache` must be rewritten against the reference `Gate` class and must cache **both** biases' selections for mixed text/image batches (image-span tokens select with `bias_vl`). Store `scores` (unbiased, post-sqrt-softplus) and `indices`; replaying a keep-set then means: mask dropped experts in `scores + bias`, re-top-6, gather unbiased scores, renormalise, ×1.5. Because `norm_topk_prob` is true, the "renormalise after pruning" question is settled by the model itself — there is no REAP-style option to leave the dropped weight unassigned.
- (inference) The saliency gate `g_j` should be the weight the expert actually receives (renormalised × 1.5), which is what the LOCAL hook does via `top_k_weights`; this already matches the upstream 2026-03-11 renormalisation, so no further fix is needed. Note `g ∈ [0, 1.5]`, not [0,1] — any histogram bounds (`HIST_LO/HI`) tuned for GLM's sigmoid gates need re-checking.
- (inference) Bias re-fit after pruning: the trained bias balances load over 384 experts; after a 50% cut the surviving experts' loads skew. A no-gradient refit is possible entirely offline from the router cache: compute per-expert load under the keep-set and iterate the paper's aux-loss-free rule `b_j += γ·sign(mean_load − load_j)` (γ = 0.001 per step in the paper) until loads balance, then verify on held-out routing that selection agreement with the unpruned model is not harmed. This is a selection-only change; it cannot be folded into healing SGD (zero gradient). Treat as a gated experiment, not a default — balancing the pruned router may trade accuracy for throughput.
- (inference) `gate_temp` appears in the reference gate; its value is not in the config fields I saw. Verify it before replaying scores offline (a wrong temperature silently changes the softplus curvature and thus `g`).

### Gaps
- `gate_temp` value for the 1017 build not confirmed.
- No published result on re-fitting `noaux_tc` biases after REAP; LibertAI and 0xSero sliced without refitting.

## Q3. The shared expert: never pruned — how does it change routed-expert saliency?

### Takeaway
V4.1 adds one shared expert unweighted after the routed sum, in the default (non-fp4) dtype; it is a keep-set-invariant offset, so it does not change REAP/HOPE rankings, but it must be included in the layer-output norm used by any healing gain re-fit. GLM-5.3-Flash has the same structure, so this is not a delta.

### Cited Findings
- Reference MoE: routed experts accumulate into fp32 `y`, then `y += self.shared_experts(x)`, unweighted, after the routed sum; the shared expert is built with `dtype=None` (default dtype, not fp4); routed weights are `float4_e2m1fn_x2` with `.scale` in `float8_e8m0fnu` shaped `[out, in // 32]` — [inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/main/inference/model.py)
- "Each MoE layer has 1 shared expert and 384 routed experts" — [arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- LOCAL header scan: all 40 layers are MoE (40 × 384 = 15,360 routed experts) and "each layer also has 1 shared expert"; decode active ≈ 6×3×2304×5120×40 = 8.49 B routed + 1.42 B shared + 5.13 B attention + 1.32 B embed/head ≈ 16.4 B — [LOCAL target_models.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/target_models.md)
- Shared expert params per layer (computed from config dims, assuming `moe_intermediate_size`): 3 × 5120 × 2304 = 35.4 M; 1.42 B over 40 layers per the header scan implies the shared expert is ~1.0 × a routed expert (35.4 M × 40 = 1.42 B) — [LOCAL arithmetic in this note]
- LOCAL healing uses `osum` ("sum of g*f_j as a VECTOR ... lets P5 re-fit the healing gain from a measured output norm") — [LOCAL stream_saliency.py](file:///home/patrickd/glm-5.3-reap/scripts/stream_saliency.py)

### Inferences
- (inference) Because `f_shared(x)` does not depend on the keep-set, `argmin_p p^T F p` (HOPE) and `argmin S_j` (REAP) are unchanged. Reconstruction-error style objectives (`||y_full − y_pruned||`) are also unchanged since the shared term cancels.
- (inference) Where it matters: the LOCAL `s05_heal` gain refit scales the routed sum to restore the layer-output norm. On V4.1 the shared expert carries ~1/7 of the per-token FFN compute (1 of 7 active experts, unweighted vs routed weights summing to 1.5), so the refit target must be `||Σ g f + f_shared||`, not `||Σ g f||`, otherwise the routed gain is over-estimated. Bank `osum_shared` (one extra d-vector per layer) in the same pass.
- (inference) The shared expert is a `dense` tensor, not MXFP4, so it is a legitimate target for the NVFP4 "dense overlay" trick that worked on GLM (LOCAL memory glm53-nvfp4-dense-overlay), unlike the routed experts.

### Gaps
- Whether the shared expert's intermediate size equals `moe_intermediate_size` (2304) was inferred from the header param count, not read from a config field.

## Q4. Engram at layers 1 and 14: before or after the MoE, and does it change which experts are load-bearing?

### Takeaway
Engram is applied by `Transformer.forward` **before** block 1 and block 14 (i.e. before those blocks' attention, hence before their MoE), writing `h + gate · value` directly into all four streams with a per-stream key/gate; it is a function of token ids only, so for calibration it must be computed in the streaming loop at those two layer boundaries from the shipped FP8 tables — and it cannot be skipped, because switching it off roughly doubles perplexity.

### Cited Findings
- Reference: "Engram is not inside `Block.forward`. `Transformer.forward` calls `layer.engram(h, ...)` before `layer(h, ...)`, so its output enters before the block's attention"; `wkv` maps to `dim * (hc_mult + 1)` ("one key per hc copy plus one shared value"); gate `dot = (h * weight * key).sum(-1) * rstd * dim**-0.5`, `gate = sigmoid(copysign(sqrt(clamp_min(|dot|,1e-6)), dot))`; output `h + gate * value` "added directly to the stream"; image positions get zero gate; tables are `float8_e4m3fn` with block-32 scales, rows dequantised to bf16 on lookup — [inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/raw/main/inference/model.py)
- Config: `engram_layer_ids [1, 14]`, `engram_num_embeddings [384006168, 384016682]`, `engram_max_ngram_size 4`, `engram_vocab_size 16000000`, 8 hash heads, `engram_head_dim 256`, `engram_compressed_vocab_size 99092` — [config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)
- Paper: two Engram modules at layers 1 and 14 (zero-indexed), 196 B parameters split evenly, n-gram orders {2,3,4}, 8 hash heads, 2048 embedding dims per order, tables ≈16 M entries per head with distinct prime sizes; "tokenizer compression, multi-head hashing, context-aware gating, and multi-branch integration"; embedding tables and K/V projections in FP8 — [arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- Lookup cost: `(max_ngram_size - 1) * n_heads = 24` rows per token per Engram layer = 48 rows/token — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696); "Each token gathers 48 rows, about 12.4 KB" — [Libertai/deepseek-v41-flash-reap](https://github.com/Libertai/deepseek-v41-flash-reap)
- LibertAI calibration: tables "mmap'd — it is a gather, never resident"; `patch_engram.py` builds the two 91.5 GiB tables on `meta`; `prune_convert_mp.py` excludes Engram, which stays on disk — [Libertai/deepseek-v41-flash-reap](https://github.com/Libertai/deepseek-v41-flash-reap)
- Engram is load-bearing: "with the Engram lookups switched off in the same forward, perplexity rises to 4.1648 (code) / 9.0627 (prose)" vs 1.9094 / 6.4520 with them on — [LibertAI 1017 EXL3 card via LOCAL target_models.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/target_models.md)
- Engram tables: 183.40 GiB FP8 + 5.72 GiB E8M0 scales + 0.29 GiB wkv = 189.13 GiB, in shards 47 and 48; "The tables changed in the 1017 release. Do not reuse the Engram shards of the older deepseek-ai/DeepSeek-V4.1-Flash" — [LOCAL target_models.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/target_models.md)
- Thor measurement: 48 concurrent 1 KiB O_DIRECT reads = 1.13–1.30 ms/token p50; mmap is the wrong primitive on Thor because "each sparse touch drags 64 KiB of page cache out of the GPU pool"; pinned-host offload "frees zero bytes" on unified memory — [LOCAL memory thor-base-model-shortlist](file:///home/patrickd/.claude/projects/-home-patrickd/memory/thor-base-model-shortlist.md); [LOCAL engram_off_device_thor.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/engram_off_device_thor.md)

### Inferences
- (inference) Pipeline delta: the LOCAL `_sweep` loop (`for li in range(lo, hi): layer = _build_layer(...)`) needs a pre-hook at `li ∈ {1, 14}`: `hs = engram_li(hs, ids)` before building/running the block. Since Engram depends only on `input_ids` (hashed 2/3/4-grams over the compressed vocab) and the current streams, it can be computed **once per chunk per Engram layer** and its gated `value`/`gate` cached — or, simpler, the lookup rows (48 × 256 B = 12 KiB/token) can be gathered from shards 47/48 by offset: 131,072 tokens × 12 KiB = 1.5 GiB per chunk per layer, read once. Precomputing the hash ids for the whole corpus up front (token ids are known before the forward) lets the gather be a sorted sequential read rather than 6.3 M random touches.
- (inference) Does Engram change which experts are load-bearing in layers 1 and 14? Mechanically yes in the trivial sense that the MoE input at those layers includes the Engram correction, so routing statistics there differ from an Engram-off forward; LibertAI's 2x perplexity jump with Engram off implies the hidden states differ materially. The practical rule: **never calibrate with Engram disabled** — the saliency would describe a model that is not the model. There is no evidence that Engram makes those two layers' experts more or less prunable than others; the per-layer saliency curves will show it (LOCAL `s04b_surgery._layer_curves`).
- (inference) Storage gate: calibration requires the full 475 GiB checkpoint (backbone 286 GiB + Engram 189 GiB) on local disk, read by range. ## Q5. DSA indexer / CSA2: precision and memory during calibration; does sparse attention change routing statistics vs dense?

### Takeaway
Attention in V4.1 is *always* its own sparse form (SWA-128 + top-512 compressed positions with FP4 Q/K in the indexer); there is no "dense" alternative to calibrate against, so routing statistics measured in a faithful forward are the model's. The memory hazard is the dense indexer score tensor (`[rows, 32 heads, S, S]`): at 8192 tokens it is 4 GiB bf16 per row and 64 GiB for 16 rows — the same quadratic term that killed the LOCAL 16k GLM forward — so the indexer must be evaluated row-by-row or query-chunked. The two-level candidate stage (top-2048 blocks of 8 = 16,384 candidates) is a no-op below 16k tokens, so 8k calibration never exercises it.

### Cited Findings
- Config: `num_attention_heads 64`, `num_key_value_heads 1`, `head_dim 512`, `qk_rope_head_dim 64`, `q_lora_rank 1280`, `o_lora_rank 1024`, `o_groups 8`, `sliding_window 128`, `compress_ratios` = 0,0 then 2 (layers 2–19) then 1 (20–39), `kv_source_layer_ids [2, 8, 14, 20]`, `index_source_layer_ids [2, 8, 14, 20, 24, 28, 32, 36]`, `index_n_heads 32`, `index_head_dim 128`, `index_topk 512`, `candidate_source_layer_id 20`, `candidate_topk_blocks 2048`, `candidate_block_size 8` — [config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)

### Inferences
- (inference) Indexer memory per row at S tokens: `32 × S² × 2 B` bf16 = 4.0 GiB at 8192, 1.0 GiB at 4096 (fp32 scores double it). The reference indexer uses fp4-quantised Q/K through a `fp4_gemm` kernel; a torch fallback on Thor will materialise bf16/fp32 scores. Evaluate the indexer **one row at a time** (or in 2048-query chunks: 32 × 2048 × 8192 × 2 B = 1 GiB) and keep only `topk_idxs` (`S × 512 × 4 B` = 16 MiB/row). With that, the 8k×16 calibration never exceeds ~47 GiB (see Q6). The LOCAL 16k GLM OOM was this exact tensor at 4x size; V4.1 at 8k is safe only because of the row-chunking, not because the model is smaller.
- (inference) Streaming delta: the LOCAL per-layer loop must also carry, per chunk row, the `shared_attn` state produced by source layers: compressed KV from layers 2/8/14/20 (bf16 fallback: `S/ratio × 576 × 2 B` ≈ 4.5 MiB/row), index keys (`S/ratio × 32 × 128 × 2 B` ≈ 32 MiB/row), `topk_idxs` (16 MiB/row) and the candidate mask (no-op at 8k). These are small but they break the "one tensor + topk" invariant: layer 3 cannot run until layer 2's compressor output for that row is on hand, so the chunk-sweep order (all rows through layer L, then L+1) still works — persist per-row state dicts, as LOCAL already does for `hs`.
- (inference) Sparse vs dense routing: the question as posed has no operational meaning for V4.1 — the model has no dense-attention mode; `index_topk 512` is active from the first token beyond the 128-window. What *is* uncovered by 8k calibration is the candidate stage (needs >16,384 tokens) and decoder behaviour on long encoder prefixes, so long-context routing drift (LOCAL note: literature empty) stays unmeasured. Mitigation is the LOCAL recommendation of chunked-prefill calibration for a few 32k–64k rows, which the KV-cache-carrying reference forward supports natively via `shared_attn`.
- (inference) Precision: use the reference FP4 Q/K quantisation in the indexer during calibration if the kernel path is available, because the top-512 selection is what the served model does; a bf16 fallback changes the selected keys slightly (QAT-trained FP4 → bf16 is a precision *increase*, so the drift should be small, but it is unmeasured).

### Gaps
- No measurement of how many of the 512 selected keys differ between FP4 and bf16 indexer paths.
- No source on whether `compress_ratio 1` decoder layers (20–39) "compress" at all beyond projection; treated here as reading layer-20's cache.

## Q6. Memory per layer during a streamed calibration forward at 8192 × 16: arithmetic against 117 GiB

### Takeaway
A V4.1 layer's routed experts are 6.72 GiB MXFP4 (25.3 GiB if dequantised to bf16); the 4-stream activation for 131,072 tokens is 5.0 GiB; the only term that can blow the budget is a dense indexer score tensor evaluated for all 16 rows at once (64 GiB bf16). With row-wise indexer evaluation the peak is ~47 GiB (bf16-dequant layer) or ~28 GiB (MXFP4-resident, per-expert dequant), so **8k calibration fits with >70 GiB to spare; dropping to 4k is unnecessary**. LibertAI measured 19.4 GiB peak at 2048 × 32 with streamed experts, consistent with this.

### Cited Findings
- Dimensions used: hidden 5120, `moe_intermediate_size` 2304, 384 experts, top-6, 40 MoE layers, `head_dim` 512 single KV head, `qk_rope_head_dim` 64, 32 indexer heads × 128, `index_topk` 512, Engram 48 rows × 256 B/token — [config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json); [arXiv 2609.19969](https://arxiv.org/html/2609.19969)
- Expert storage format: "E2M1 packed 2/byte + E8M0 scales, block 1×32"; a full forward "streams 269 GiB of experts at about 0.65 GiB/s, with peak residency of 19.4 GiB"; `torch.cuda.set_per_process_memory_fraction` advised because an uncapped overrun can starve the OS — [Libertai/deepseek-v41-flash-reap](https://github.com/Libertai/deepseek-v41-flash-reap)
- LOCAL byte accounting for 1017: 475.24 GiB total = experts MXFP4 268.95 GiB + Engram 189.13 GiB + fixed floor without Engram 9.77 GiB (+ DSpark 7.39 GiB) — [LOCAL target_models.md](file:///home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/target_models.md)

### Arithmetic (computed in this session; GiB = 2^30)
Per layer, weights:
- Routed expert params/layer = 384 × 3 × 5120 × 2304 = 13.59 B (×40 = 543.6 B; matches the 552 B backbone minus attention/shared/embeddings).
- MXFP4 bytes/layer = 13.59 B × (0.5 + 1/32) = **6.72 GiB** (×40 = 268.9 GiB — agrees with the LOCAL header scan 268.95 GiB).
- bf16 dequant/layer = **25.31 GiB**; fp8 = 12.66 GiB. Shared expert bf16 0.07 GiB; attention ≈127 M params ≈ 0.24 GiB bf16; indexer ≈23 M params.

Per chunk, activations (S = 8192, B = 16, N = 131,072 tokens):
- 4-stream residual `hs` bf16 = N × 4 × 5120 × 2 B = **5.00 GiB** (single-stream equivalent 1.25 GiB). This is the chunk state that lives in the pool for the whole layer sweep; LOCAL keeps it `.cpu()` but on Thor that is the same pool.
- Tokens per expert per chunk = N × 6 / 384 = **2048** (GLM at 288/top-8: 3641 — V4.1 needs 1.78x the tokens for equal per-expert sample size).
- Grouped `gate_up` for all routed rows bf16 = N × 6 × 4608 × 2 B = 6.75 GiB if done in one shot; per-expert loop (LOCAL style) = 18 MiB. Use the loop.
- Dense indexer scores `[rows, 32, S, S]` bf16: **4.00 GiB per row**, 64 GiB for 16 rows (fp32: 8 / 128 GiB). Must be row- or query-chunked.
- Main KV latent bf16 (uncompressed) 0.14 GiB; compressed ×2 0.07 GiB; SWA-128 negligible; `topk_idxs` 16 MiB/row.
- Engram gathered rows FP8 = N × 48 × 256 B = **1.50 GiB per Engram layer** per chunk; projected output bf16 1.25 GiB.

Peaks (layer weights + hs + per-expert loop working set + indexer + 1.5 GiB misc):
| config | indexer rows/call | bf16-dequant layer | MXFP4-resident + per-expert dequant |
|---|---|---|---|
| S=8192, B=16 | 1 | **46.6 GiB** | **28.0 GiB** |
| S=8192, B=16 | 16 (naive) | 166.6 GiB — OOM | 148.0 GiB — OOM |
| S=4096, B=16 | 1 | 34.7 GiB | 16.1 GiB |
| S=8192, B=4 | 1 | 37.8 GiB | 19.2 GiB |

Reference points: GLM 8k measured 57 GiB (its 14.5 GiB layer + ~13 GiB arena + DSA scores); LibertAI 2048×32 streamed measured 19.4 GiB.

### Inferences
- (inference) 8k × 16 is feasible with ~70 GiB of headroom under the 117 GiB envelope, *provided* the indexer is chunked and the layer is swept with per-expert dequant (keep the MXFP4 codes resident, dequantise each expert's three matrices on the fly: 35.4 M params × 2 B = 68 MiB transient). Dequantising a whole layer to bf16 costs 25 GiB and 0.65 GiB/s of read bandwidth per LibertAI — on this box 3.4 GB/s read means 6.72 GiB MXFP4 per layer ≈ 2 s, ×40 layers ≈ 80 s of I/O per chunk; the compute is the bottleneck, not I/O.
- (inference) Engram at calibration adds ≤3 GiB transient per Engram layer per chunk; the tables themselves must stay off-pool (189 GiB).
- (inference) Set `torch.cuda.set_per_process_memory_fraction` as LibertAI did and keep the LOCAL `memfence.require(LAYER_COST_GIB, ...)` gate with `LAYER_COST_GIB` re-derived for V4.1 (≈30 GiB for the MXFP4-resident path, ≈50 GiB for bf16-dequant) — the GLM constant is wrong for this model in both directions.
- (inference) 4k calibration is not needed for memory; the only reason to prefer shorter rows is throughput per token, and the LOCAL ladder shows 4x length costs only +2.4% wall-time, so stay at 8k and spend the budget on more rows (384/6 routing needs ~1.8x GLM's token count per expert).

### Gaps
- The reference `fp4_gemm`/`fp4_act_quant` kernels' availability on sm_110a is unknown; LibertAI needed `patches/patch_kernels.py` on GB10. A pure-torch dequant fallback is assumed in the arithmetic.
- Actual measured peak on Thor for V4.1 does not exist; the numbers are derived, with LibertAI's 19.4 GiB as the only empirical anchor.

## Q8. The 0909 REAP-25/50 and REAP-256E/272E artifacts: how made, served, evaluated, and does 1017 break the recipe?

### Takeaway
The 256E/272E artifacts were built by LibertAI with the checkpoint's own reference implementation streamed layer-by-layer (params on `meta`, experts streamed at 0.65 GiB/s, 19.4 GiB peak), plain mean REAP (plus a text/image-balanced variant), a small calibration (2048 × 128 text rows + 256 images per `config.json`), Engram mmap-gathered, MXFP4 experts sliced bit-exactly, served on vLLM TP=2 across two GB10s; quality is text PPL +5.49% at 256 and +14.66% at 192, with vision collapsing below 272 under text-only ranking. 1017 is "a minor update" with the same architecture but new Engram tables and (presumably) new expert weights, so the *recipe* transfers unchanged while the *rankings* must be recomputed on 1017 — transferred rankings on V4 showed per-row cosine as low as 0.946.

### Inferences
- (inference) What 1017 breaks: nothing structural. The config fields, tensor names, MXFP4 layout, two router biases, Engram layer ids and DSpark layout are identical by the vendor's "same architecture" statement. What must be redone: (a) the saliency pass itself (new expert and router weights — 0xSero's transferred-ranking cosine of 0.946 on the weakest row is the warning), (b) pointing serving at the 1017 Engram shards. The LibertAI scripts (`stream_model.py`, `patch_engram.py`, `prune_experts.py`, `verify_prune.py`) are the closest existing V4.1 pipeline and are the natural donor for the "reference-implementation streaming" layer the LOCAL s03 lacks.
- (inference) Implication of the 0909 curve for 50–60% on 1017: the measured curve is super-linear (+4.1% at 29%, +5.5% at 33%, +7.1% at 37.5%, +14.7% at 50%). The only legal count past 192 is 128 (66.7%), for which no number exists; extrapolating the curvature puts it well above +30% text PPL — worse than V4-Flash's REAP50 (+26.5%) and GLM's REAP50 (+21%). Two mitigations are LOCAL-proven on GLM and unexploited by LibertAI: a balanced, much larger calibration corpus (theirs is 262k tokens, ~1/50 of ours) and the mass criterion — both should pull the 192-point below +14.7%, but there is no evidence they rescue 128.
- (inference) Vision: the caption cliff below 272 with text-only ranking, and the −0.05 correlation between `gate.bias` and `gate.bias_vl`, say vision and text use largely disjoint experts in V4.1; the LOCAL bucketed accumulators (`*_by_bucket` with a `vision` bucket) already support a per-domain retention floor, which is the principled version of LibertAI's 50/50 average. Expect the vision floor to cost text PPL (their balanced 256E: text +14.1% vs +5.5%).
- (inference) DSpark after pruning: the drafter reads the attention input of layers 37–39 of the *pruned* backbone; LibertAI kept its 3 × 128-expert pools unpruned and got 19–49 tok/s on 2× GB10 with k=5; the LOCAL V4-180B measurement (τ@0 0.815 post-REAP) indicates the head survives moderate pruning. Whether it survives 50% is unmeasured; the LOCAL GLM finding that spec-decode is a net slowdown on Thor (MoE batch cliff) may apply regardless.

### Gaps
- No downstream benchmarks (only PPL) for any pruned V4.1 build; none at all for 1017.
- The two LibertAI corpus-size statements (64.4 M vs 262 k text tokens) are unreconciled; treat 262 k (the `config.json` provenance block) as authoritative.
- "Engram 47.2 GiB/rank left on disk" (≈94 GiB total) is inconsistent with the 189 GiB FP8 tables; it may indicate an FP4 Engram or a per-rank split — unresolved.

## Consolidated delta list: GLM-5.3-Flash pipeline → V4.1-Flash-1017 (implementation order)

1. **Model code (largest delta).** No `transformers.models.deepseek_v41` exists (the local image's transformers 5.19.0 has `deepseek_v4` only; GitHub raw returns 404). Build the streaming layer on the checkpoint's `inference/model.py` + `kernel.py` + `engram.py` (61.7 kB / 23.8 kB / 8.1 kB), with LibertAI's `patch_kernels.py`/`patch_engram.py` as the donor for GB10-class hardware. Replace `fp4_gemm`/`fp4_act_quant`/`hc_split_sinkhorn` with torch fallbacks and gate each against the reference on real weights (the LOCAL `mhc_reference.py` pattern: bit-match first, then port).
2. **Layer state.** Carry `(x [B,S,4,5120], ffn_pre [B,S,4] fp32)` between layers instead of `(x, topk_indices)`; add per-row `shared_attn` state produced at KV-source layers {2,8,14,20} and index-source layers {2,8,14,20,24,28,32,36} (compressed KV, index keys, `topk_idxs`); candidate stage (layer 20) is a no-op at 8k.
3. **Engram pre-hooks** at layers 1 and 14 inside `_sweep`, gathering 48 × 256 B rows/token from shards 47/48 (precompute hash ids from `input_ids` once per corpus); tables never resident; full 475 GiB checkpoint must be on local disk (NVMe gate: 51 GB free today).
4. **Expert hook.** Re-target `patch_experts_for_saliency` to the reference MoE expert loop; apply `swiglu_limit 10.0` clamping when computing `f_j` (config sets it; the reference applies clamps only when `> 0`); keep `g_j` = renormalised × 1.5 weight; `K = 6`, `E = 384`; re-check `HIST_LO/HI` for `g ≤ 1.5`; add `osum_shared`; optional `post`-weighted accumulator.
5. **Router cache.** Re-target `patch_router_for_cache` to the reference `Gate`; store unbiased `sqrt(softplus(xW/gate_temp))` scores; record which bias (`bias` vs `bias_vl`) selected each token; verify `gate_temp`.
6. **Surgery (`s04b`).** Slice MXFP4 `float4_e2m1fn_x2` weights and `[out, in//32]` E8M0 scales by expert index (bit-exact, no requant); slice `gate.weight`, `gate.bias`, **and `gate.bias_vl`**; re-link `weight.scale` after assign-loading (46,372 tensors); set `n_routed_experts` to a vLLM-legal count (192 for 50%); decide DSpark pools (128 keep, or 64).
7. **Calibration budget.** 8192 × 16 rows fits (~47 GiB peak bf16-dequant, ~28 GiB MXFP4-resident) if the indexer is evaluated per row; re-derive `LAYER_COST_GIB`; plan ~1.8x GLM's token count for equal per-expert samples (2048 tokens/expert per 131k-token chunk).
8. **Bias refit (optional, gated).** Offline aux-loss-free load-balancing update on the pruned router from the router cache; selection-only; cannot be learned by SGD healing.
9. **Serve path.** Local vLLM nightly aarch64 image already contains `deepseek_v41` with the router compiled for SM 110; legal counts {…,128,192,256,320,384,…}; Marlin MXFP4 MoE; FlashMLA sparse attention on SM 11.0 unverified; `--enforce-eager` likely; replace UVA pinned-host Engram with the NVMe O_DIRECT row store. llama.cpp (#28696) is the unmerged fallback; SGLang absent; exllamav3 untested on Thor.
