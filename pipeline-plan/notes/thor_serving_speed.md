## Q1. Active bytes per decode step (B_tok) and resulting tok/s at Thor effective bandwidth

### Takeaway
At 192 kept experts and top-6, B_tok is **~11.1–11.7 GB with the checkpoint's native FP8 dense path** and **~7.3–8.0 GB with an NVFP4 overlay on the dense path** (2.3 vs 2.9 bpw experts only moves it by 0.64 GB — expert bits buy fit, not speed). At the ~117 GB/s our CUDA engines realise today that is **~10 tok/s (native dense) / ~15 tok/s (NVFP4 dense)**; at the 160 GB/s our best kernels sustain it is ~14 / ~21 tok/s; the 200 GB/s ceiling gives ~17 / ~26 tok/s. A llama.cpp GGUF build lands lower, ~7–11 tok/s on Thor `[EST]`, once V4.1 actually runs.

### Inferences — B_tok budget `[EST]` (192 kept experts, top-6 unchanged, 8K context)
Per-token reads: routed 8.49B params (6 of 192 per layer — pruning does not change active bytes); shared 1.42B; attention+indexer+compressor 5.13B; lm_head 0.66B (embedding is a 1-row gather); `engram.wkv` ~0.3B FP8 (read every token, easy to forget); router (192×5120 BF16 ×40) + HC F32 ≈ 0.24 GB; KV ≤ 890 B × ctx (0.007 GB at 8K, 0.11 GB at 128K, 0.89 GB at 1M — upper bound since reindex/reuse layers read only the top-512 / 16,384-candidate subset); Engram rows 12.4 KiB from NVMe (not DRAM).

| Component | native (FP8 dense ≈1.03 B/w, BF16 head) | NVFP4 dense overlay (0.62 B/w) |
|---|---:|---:|
| Routed experts @ 2.3 bpw / 2.9 bpw | 2.44 / 3.08 GB | 2.44 / 3.08 GB |
| Shared expert | 1.46 | 0.88 |
| Attention + indexer + compressor | 5.28 | 3.18 |
| lm_head | 1.32 (BF16) | 0.41 |
| engram.wkv | 0.31 | 0.19 |
| Router + HC + norms | 0.24 | 0.24 |
| KV @ 8K | 0.01 | 0.01 |
| **B_tok @ 2.3 / 2.9 bpw** | **11.06 / 11.70 GB** | **7.35 / 7.99 GB** |
| Routed-expert share of B_tok | 22–26% | 33–39% |

tok/s = BW_eff / B_tok (plus ~1–2 ms fixed glue, ignored):

| Effective BW | native 2.3 | native 2.9 | NVFP4-dense 2.3 | NVFP4-dense 2.9 | regime |
|---|---:|---:|---:|---:|---|
| 63 GB/s (unoptimised / "57–66") | 5.7 | 5.4 | 8.6 | 7.9 | first-port engine |
| **117 GB/s (both LOCAL engines today)** | **10.6** | **10.0** | **15.9** | **14.6** | realistic day-1 after porting the 0731/GLM kernels |
| 160 GB/s (LOCAL best per-kernel class) | 14.5 | 13.7 | 21.8 | 20.0 | after MoE/HC/glue work |
| 200 GB/s (≈85% of streaming; ds4-on-GB10 class) | 18.1 | 17.1 | 27.2 | 25.0 | ceiling |

- The 2.3 vs 2.9 bpw choice is worth only ~6% decode (0.64 GB of 8–12 GB). Choose bpw for quality/fit; the decode levers are the dense path (−3.7 GB with NVFP4) and kernel efficiency (117 → 160+ GB/s). NVFP4-on-FP8 dense is a *double quant* (FP8 block source → FP4), unlike the LOCAL BF16-source overlay; its quality must be re-gated (cos/flip/PPL), not assumed.
- At 2.3–2.9 bpw an expert weight byte drives 11–14 B of activation traffic without row reuse (vs 7.1 at NVFP4), so the expert GEMV needs R ≥ 8 rows per x load to stay near streaming; a scalar-decode kernel would repeat the 0731 engine's 38%-of-BW MoE.
- llama.cpp on Thor `[EST]`: scaling `[Spark]` DSV4-Flash (13B active, ~17.4–19.1 tok/s) by V4.1's ~1.26× more active bytes gives ~14–15 tok/s on Spark, ÷1.26–1.40 Thor penalty → **~10–11 tok/s**; if the ~37 ms fixed-term fit is right and V4.1 adds glue (Engram, CSA2 roles, lagged HC), ~7–9 tok/s. Band: **7–11 tok/s**, i.e. at or below the CUDA server's day-1 number and well below its NVFP4-dense ceiling.

### Gaps
- No V4.1 B_tok has been measured on any engine; the table is header arithmetic. Lesson from 0731: "ROOFLINE B_tok measured the CHECKPOINT, not the ENGINE" (+9.5%) — re-measure what the loader materialises.
- The 890 B/token KV decomposition and which layers read the full indexer cache per step are not given in the paper text fetched.
- No llama.cpp/ik_llama measurement of V4-family decode on Thor itself exists; all are `[Spark]` or discrete.

## Q2. Engram on NVMe: per-token latency, prefetch overlap, prefill IO, and integration into llama.cpp and a CUDA server

### Takeaway
Decode cost is a non-issue: 48 rows/token measured at 1.13–1.30 ms p50 (O_DIRECT, thread pool) on this Thor = ~1–2% of a 65–100 ms step even unhidden, and fully hidden by issuing the reads at sampling time. Prefill needs 48 reads per prompt token; at the measured 62–95k IOPS that caps Engram-fed prefill at ~1,300–2,000 tok/s — above any plausible Thor prefill rate, so it binds only if not pipelined. Engram is not optional: disabling it destroys quality.

### Cited Findings
- **Access pattern:** 2 modules (layers 1 and 14), orders {2,3,4} × 8 hash heads = 24 rows/layer, 48 rows/token; each row 256 FP8 + 8 E8M0 = 264 B → 12.4 KiB/token; addresses are a pure function of (compressed) token ids — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696), [josephdrose fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md), [arXiv 2609.19969](https://arxiv.org/pdf/2609.19969)
- **LOCAL Thor I/O (2026-10-17, WD SN5000S Gen4 x4 in a Gen5 slot, beside a running vLLM server):** 48 random 1 KiB O_DIRECT reads per token: 16 threads p50 1.13 / p95 1.35 / p99 2.22 ms; 48 threads p50 1.18 / p99 3.09 ms; serial 4.89 ms; 4 KiB random 62.6k IOPS @16 procs, 95.5k @32; QD1 p50 99–130 µs; mmap default faults pull 63.6 KiB page cache per touch — [LOCAL engram_off_device_thor.md](/home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/engram_off_device_thor.md)
- **Engram is load-bearing:** EXL3 2.9 bpw 1017 PPL code 1.9094 / prose 6.4520 vs "2.9 bpw with Engram off" 4.1648 / 9.0627 (unquantised 1.8749 / 6.4277) — [LibertAI 1017 EXL3 2.9bpw card](https://huggingface.co/LibertAIDAI/DeepSeek-V4.1-Flash-1017-EXL3-2.9bpw)
- **Proven prefetch designs `[Spark]`:** josephdrose `Engram.prefetch(hash_ids)` from `prepare_inputs`, "A disk read cannot be captured inside a CUDA graph", 600 s load test 0 missed, late arrivals wait 0.41 ms — [fit-and-engram.md](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); MiaAI SGLang `row_store.cpp` "O_DIRECT reads, 96-thread miss servicing, packed shards", lookups on a side stream −2.3 to −2.9 ms/step, prefill: "the Engram rows of the whole prompt are fetched before the first chunk runs" — [MiaAI-Lab](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks); tonyd2wild: staging 2–3 ms/forward with node-local rows vs 5.9–7.8 ms over NFS — [tonyd2wild](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark)
- **Prefill IO evidence:** exllamav3 100k-token prefill 2,695 tok/s with tables in RAM vs 1,686–1,719 tok/s from disk (discrete GPUs) — [exllamav3 PR #449](https://github.com/turboderp-org/exllamav3/pull/449); GPU page-faulting a file-mapped table: 30k-token prefill 88 s vs 1.6 s with 64 CPU threads pre-faulting — [vLLM PR #58439](https://github.com/vllm-project/vllm/pull/58439); direct reads instead of mmap raised a sister-architecture (PLE) prefill from ~300 to ~750–800 tok/s on Spark — [llama.cpp PR #28136](https://github.com/ggml-org/llama.cpp/pull/28136)
- **llama.cpp today:** Engram tensors live in the GGUF (Q8_0 ≈195 GiB, Q3_K ≈78.7 GiB) and are pinned to CPU with `-ot "engram_embd.weight=CPU"` via mmap; on-demand row reads via `TENSOR_READ_LAZY` proposed, unimplemented; the "0.1 ms per token" figure is arithmetic, not a measurement — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696)
- **Unified-memory traps:** pinned-host / UVA offload "frees zero bytes" on GB10 ("A 4 GiB pinned allocation cost 4.09 GiB of GPU-visible memory") — [josephdrose](https://github.com/josephdrose/joe-spark-patches/blob/main/dsv41/docs/fit-and-engram.md); freed CUDA memory sits in the driver pool until `drop_caches=3` — [LOCAL thor-unified-memory-oom.md](/home/patrickd/.claude/projects/-home-patrickd/memory/thor-unified-memory-oom.md)
- **MXFP4 Engram** (136 B/row, 97.3 GiB) is benchmarked within noise (GSM8K 0.967 vs 0.966 FP8) — [vLLM PR #61530](https://github.com/vllm-project/vllm/pull/61530), [nvidia/DeepSeek-V4.1-Flash-NVFP4](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4)

### Inferences
- **Decode `[EST]`:** at 10–25 tok/s the drive sees 480–1,200 reads/s (≤2% of measured IOPS). Schedule: sample t → hash position t+1 on CPU (µs) → submit 48 reads → embed + layer 0 → join layer-1 rows (~1.2 ms after submit, layer 0 is ~1–2.5 ms at 40 layers/65–100 ms) → layer-14 rows have 13 layers of slack. Critical-path residue ≈ p99 tail minus layer-0 time, <1% median. With DSpark verify width 6: 288 reads, hashes known at draft time → ~1.5–3 ms if issued concurrently (extrapolated from 95k IOPS), hidden behind the draft pass.
- **Prefill `[EST]`:** reads = 48 × P before de-dup. At 62–95k IOPS: ceiling 1,300–2,000 prompt tok/s, 128K prompt = 66–100 s of IO, 1M prompt = 8.5–13 min of IO. Since Thor compute prefill is expected at a few hundred tok/s (Q3), IO is hidden if chunk n+1's rows are fetched while chunk n computes; it is *not* hidden if fetched synchronously per chunk. De-dup (repeated n-grams) only helps repetitive text. io_uring at QD 64–128 may beat the thread-pool ceiling — unmeasured.
- **CUDA server integration `[design]`:** (1) repack Engram (FP8 264 B or MXFP4 136 B rows) into one contiguous file per layer, opened `O_DIRECT`; (2) `io_uring` with registered fixed buffers carved from a `cudaHostAlloc`/`cudaHostRegister` arena — on Thor that memory *is* device-visible, so the lookup kernel dequantises straight from staging (no H2D copy); (3) per row read the 512 B sector, or 1,024 B when the row straddles a sector boundary (~51% of FP8 rows; MXFP4 rows straddle less); (4) staging ring = (K+1) positions × 48 rows × 1 KiB × 2–3 slots ≈ <1 MiB; (5) completion signalled by a host flag the graph waits on via `cuStreamWaitValue32` (keeps the decode CUDA graph capturable, since "a disk read cannot be captured inside a CUDA graph"); (6) prefill: a producer thread walks the prompt one chunk ahead; (7) guards: never mmap the table, cgroup `memory.high`, `drop_caches=3` before load.
- **llama.cpp integration `[design]`:** cleanest is to treat Engram rows as a **graph input** (like `inp_embd`), not a weight: hash in the batch-prep path, fill a host-registered `[n_tokens, 48, 256]` input via the row store, and let `set_input()` hand it to the CUDA backend; the Engram gate/wkv math stays ordinary ggml ops on GPU. This removes the CPU-mmap `get_rows` (page-cache growth), keeps CUDA graphs valid, and needs no new backend op. Alternative: a `ggml_custom` op with a CPU callback — simpler to write, but it forces a graph split and host sync every Engram layer.
- **Disk capacity gate (unchanged):** 51 GB free on the 1 TB NVMe; need ≥97 GiB (MXFP4 Engram) or 189 GiB (FP8) plus the backbone — [LOCAL engram_off_device_thor.md](/home/patrickd/glm-5.3-reap/research_notes/Compressing%201T%20MoE%20for%20Thor/engram_off_device_thor.md).

### Gaps
- No io_uring / fio measurement on this Thor; the IOPS ceiling is a psync multi-process measurement taken beside a co-resident vLLM server.
- No published prefill-rate number for Engram-from-NVMe on a *single* unified-memory box.

## Q3. Prefill throughput, long-context prefill time, and KV per token

### Takeaway
V4.1's encoder-decoder halves prefill work (8B active per prompt token, decoder only replays the last 128 tokens), so prefill is unusually cheap per token; but the only measured V4.1 prefill numbers are 4-Spark clusters (~1,900–2,260 tok/s total). Extrapolated to one Thor: **~200–450 tok/s on llama.cpp-class kernels, ~300–1,000 tok/s for a custom CUDA server with tensor-core W4A16 MoE** `[EST]` → 128K prompt ≈ 5–11 min (llama.cpp) / 2–7 min (CUDA); 1M ≈ 40 min–1.5 h. KV 890 B/token is confirmed (global, FP4 latent) — 0.11 GiB at 128K, 0.83 GiB at 1M, plus a fixed SWA ring.

### Cited Findings
- **Prefill structure:** "This design allows CED to compute only the first half of the layers during the prefill phase"; CED "nearly halves prefill computation"; decoder runs only an SWA replay over the last n_win = 128 prompt tokens; "8B parameters per token during prefill"; "extending the context length 256-fold, from 4K to 1M, increases its Decode FLOPs by only 1/4"; Reuse-mode layers run "only 15 kernels during prefill and 11 during decode" — [arXiv 2609.19969](https://arxiv.org/html/2609.19969v1)
- **KV:** "global KV cache footprint (always in HBM) to 890 bytes per token, roughly 1/4 of the corresponding footprint of DeepSeek-V4-Flash"; main KV FP4 E2M1 with one E4M3 scale per 16 channels; SWA KV stays FP8; persistent (SSD/host) footprint ~1/8 of V4-Flash via SWA Bounded Replay — [arXiv 2609.19969](https://arxiv.org/html/2609.19969v1); "A full 1M-token prompt holds under 1 GB of global KV" plus a fixed 128-token window per layer — [vLLM recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)
- **Measured V4.1 prefill `[4× / 2× Spark]` (cold, unique prompt):** TensorFold TP4 1,613–1,929 tok/s (2.9K–93K tokens; 93K in 48.4 s), fleet 2,144–2,266; vLLM native 1017 TP4 1,903–2,201; TensorFold TP2 (EXL3 2.9 bpw, 2 Sparks) 2,180 at 11.6K, 2,135 at 93K (43.7 s), 2,044 at 186.8K — prefill rate is flat to slightly rising with length — [tonyd2wild](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark); MiaAI unique-text prefill 4.9–5.0k tok/s at TP4 — [MiaAI-Lab](https://github.com/MiaAI-Lab/DeepSeek-v4.1-Flash-DGX-Sparks)
- **Single-device prefill anchors:** `[Spark]` DSV4-Flash-0731 llama.cpp pp2048 448–459 tok/s (UD-IQ2_M), 411 (IQ3_XXS); a 65,868-token prompt averaged 266.6 tok/s; ~300 tok/s when launched at 131K ctx — [Classmethod](https://dev.classmethod.jp/en/articles/dgx-spark-deepseek-v4-flash-0731-llama-cpp/); Thor prefill is 1.80–2.05× slower than Spark on the same llama.cpp build — [JetsonHacks](https://jetsonhacks.com/wp-content/uploads/2025/10/SparkThorLlamaBenchmarks.html)
- **Tensor-core path on Thor:** W4A16 (NVFP4 → BF16 in smem, BF16 tcgen05 MMA) compiles for sm_110a and gave prefill +34–40% on a 512-expert MoE; block-scaled FP4 tcgen05 is refused by CuTe DSL 4.8 for sm_110a — [flashinfer PR #5882](https://github.com/flashinfer-ai/flashinfer/pull/5882); CUTLASS profiler on Thor reached 870–875 TFLOPS dense FP4 with `110a` kernels — [NVIDIA forum](https://forums.developer.nvidia.com/t/verifying-claimed-tops-performance-on-jetson-thor-cutlass-kernel-for-sm110-does-not-run-sm80-gives-very-low-performance-6-9-tflop-s/352063) (conflicts with the CuTe DSL refusal; LOCAL: tcgen05 assembles only with `-arch=sm_110a` and PTX ≥ 9.0 — [LOCAL dspark-decode-gap-research.md](/home/patrickd/.claude/projects/-home-patrickd/memory/dspark-decode-gap-research.md))
- **LOCAL custom-server prefill is the weak point:** GLM-5.3-Flash engine prefill 47.8 ms/token at chunk 32 (~21 tok/s) — [LOCAL glm53-nvfp4-dense-overlay.md](/home/patrickd/.claude/projects/-home-patrickd/memory/glm53-nvfp4-dense-overlay.md); the 0731 engine's M≥2 path suffered ~3× DRAM transactions from cold-weight coalescing in the m16 tile ("ALWAYS BENCH COLD"), fix = repack B in mma order, unbuilt — [LOCAL dsv4-0731-cuda-server.md](/home/patrickd/.claude/projects/-home-patrickd/memory/dsv4-0731-cuda-server.md)

### Inferences `[EST]`
- Prefill FLOPs ≈ 2 × 8B = 16 GFLOP/prompt-token (+ indexer/attention terms that grow sub-quadratically with CSA2). The binding term on Thor is kernel efficiency, not peak FLOPs. llama.cpp-class: Spark DSV4 at 13B active ~410–460 tok/s → V4.1 encoder-only at 8B ≈ ×1.6 → ~650–740 on Spark → ÷1.8–2.05 → **~320–410 tok/s on Thor**, minus long-context decay (Spark fell to ~270 at 66K) → band **200–450 tok/s**. 128K: 5–11 min; 1M: 40–80+ min.
- Custom CUDA server: today's engines are 10–20× below that (per-token loops, m16 coalescing defect); with a dedicated W4A16 tcgen05 grouped-GEMM for experts (expert reuse across a 512–2,048-token chunk makes it compute-bound) **300–1,000 tok/s** is plausible but unproven on sm_110a. It is a separate build item (prefill kernels ≠ decode GEMVs) and should be scheduled explicitly.
- KV is irrelevant to fit (≤0.9 GiB at 1M); long-context *decode* slowdown should be small (paper: +1/4 FLOPs from 4K→1M), unlike llama.cpp's −22% to −64% at 32K on dense-attention MoEs on Thor ([JetsonHacks Thor](https://jetsonhacks.com/wp-content/uploads/2025/10/thor-llamacpp-bench.html)). Caveat: llama.cpp PR #28696 does not implement the two-level candidate mask, so its context is "effectively capped at about 16K" — [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696).

### Gaps
- No single-device V4.1 prefill measurement exists (Spark single-node GGUF numbers are 2.3–2.5 tok/s CPU-path runs).
- Thor BF16/FP4 tensor throughput achievable by a W4A16 MoE kernel at these shapes is unmeasured; the 870 TFLOPS figure is a dense FP4 profiler number.

## Q4. Dequant format for 2.3–2.9 bpw experts on sm_110a: trellis vs IQ/K-quants vs NVFP4/MXFP4

### Takeaway
Hardware-unpacked FP4 (MXFP4/NVFP4 via `cvt.f16x2.e2m1x2`) is the only format with a proven ≥80%-of-streaming batch-1 kernel on Thor, but at 4.25–4.5 bpw it does not fit at 192 experts (271.8B expert params → 144 GB). So a sub-3-bit format is forced, and on a 20-SM-class part the per-weight decode instructions matter: LUT/codebook IQ-class (IQ2_S/IQ3_S, IQ2_K/IQ3_K) is the safer choice; trellis (IQ*_KT/QTIP/EXL3-style) has the best quality per bit but the most ALU per weight and no sm_110 kernel or measurement anywhere.

### Cited Findings
- **Fit arithmetic:** 192 × 40 × 3 × 2304 × 5120 = 271.8B expert params → 2.9 bpw = 91.8 GiB, 2.3 bpw = 72.8 GiB, MXFP4 4.25 bpw ≈ 134 GiB `[EST]`; budget plan ≈113.7 GiB at ~2.9 bpw incl. 12 GiB reserve — [LOCAL compressing-1t-moe-thor-research.md](/home/patrickd/.claude/projects/-home-patrickd/memory/compressing-1t-moe-thor-research.md)
- **HW FP4 on Thor (LOCAL):** `__nv_cvt_fp4x2_to_halfraw2` works on sm_110a; warp-per-row NVFP4 MoE GEMV went 13% → 82% of achievable (4.71×), replacing a `__constant__` nibble LUT that serialised up to 8 ways; inline fp8 scale decode was −19% ("the kernel is instruction-bound"); `mma.sync ... kind::mxf4.block_scale` needs sm_120a so Spark/RTX-50 FP4 kernels do not transfer — [LOCAL glm53-decode-gap-profile.md](/home/patrickd/.claude/projects/-home-patrickd/memory/glm53-decode-gap-profile.md), [LOCAL dspark-decode-gap-research.md](/home/patrickd/.claude/projects/-home-patrickd/memory/dspark-decode-gap-research.md)

- **`[Spark]` decode with a trellis-quantised V4.1:** vLLM full EXL3 TP4 37.8 tok/s/stream vs native MXFP4 1017 53.8 (both DSpark on; DSpark acceptance 12.4% on EXL3 vs 53% native) — [tonyd2wild](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark) (confounded by acceptance)

### Inferences `[EST]`
- Ranking for the Thor CUDA server at batch 1: (1) MXFP4 kept where it fits (bit-exact, no requant, HW unpack) — e.g. shared/attention-adjacent or the most salient experts in a mixed-precision layout; (2) a **2–3 bpw codebook format with an in-register/shared-memory LUT** (IQ3_S/IQ2_S-like grids or a 2-bit "FP2/FP3"-style scalar code + per-16/32 scale), using the same warp-per-row + R≥8 x-reuse skeleton; (3) trellis only if a microbench shows it at ≥75% of streaming. Rationale: trellis spends several integer ops + an int→float convert per weight on every one of 8.49B active weights per token; 4080 shows −7% vs IQ2_XXS with ~2.6× Thor's bandwidth per SM-count, and Thor has fewer SMs, so the ALU:byte ratio is less forgiving.
- Mixed formats are viable because only ~22–39% of B_tok is routed experts: even a 30% slower expert kernel costs ~7–12% end-to-end, less than the NVFP4 dense overlay gains. Quality (trellis ≈ +0.4–1.8% PPL at 2.9 bpw) may justify trellis for the *expert* bytes if the kernel holds ≥70% of streaming.
- For llama.cpp: prefer IQ3_XXS/IQ2_XXS/IQ4_XS (validated controls) over IQ2_S/IQ3_S until the Blackwell packed-load bug is fixed upstream; ik_llama IQ2_K/IQ3_K/IQ*_KT are untested on sm_110.

- No measured batch-1 GEMV bandwidth for any sub-3-bit format on sm_110a (none on GB10 for IQ*_KT/IQ*_K either).
- Instructions-per-weight for QTIP 3INST/IQ*_KT decode on GPU are not published in the sources found.
- Thor SM count / FP32 throughput were not re-sourced here (LOCAL note refers to "a multiple of 20 SMs").
